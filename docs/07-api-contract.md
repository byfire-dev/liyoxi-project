## 1. 一页结论

- **规模**：669 条接口，分四组、生成三份 OpenAPI 文档：商家端 167 条（V1.0 157）、运营管理后台 470 条（V1.0 426）、电脑端下载页 17 条、外部回调与探活 15 条（都不出 OpenAPI 文档；其中 5 条探活只登记、不分配 operationId）。V1.0 共 613 条。另有一份事件与任务目录：228 个事件（V1.0 发出 220 个，另有登记但不发的 7 个、预留 1 个）、34 个订阅者、18 类定时器（按主体组合 24 种）、25 个周期任务，以及数据模型里全部“非接口触发”的状态迁移各由谁承担。
- **唯一依据**：每条接口的路径、请求、响应、错误、副作用以 20 份分组文档为准；全仓通用的规则（认证、错误体、幂等、分页与计数、并发、文件、长任务、限流、再验证、版本兼容等 87 条）以[通用约定](api/00-conventions.md)为准；作者之间的分歧与技术取舍按 138 条裁决定（编号 A1–A156，中间有未使用的编号；[working/api-rulings.md](api/working/api-rulings.md)）。
- **与数据模型对齐**：返回的业务字段写明来自哪张表哪一列、或怎样算出，写入的字段写明落到哪一列，状态迁移写明对应数据模型状态机表的哪一行、守卫不满足时返回哪个错误码。写契约时发现的数据模型缺口已回写（第 6.1 节），回写后数据模型校验仍全部通过。
- **怎么得出的**：先从两套原型的 103 个画板与 PRD 整理出“页面 → 接口”的路线图和资源登记表，定通用约定；再由 20 位作者分文档写到字段级；每份文档由两位复核员分别对照“页面与数据模型”“约定与其他文档”挑错，初稿之后又修订三轮（各文档修订记录里的第二至第四轮），处理复核意见、跨文档请求与裁决。
- **校验结果**：脚本逐项核对，全部通过——路线图里每条接口都写进了文档与结构化清单；285 个领域错误码没有未定义、重名、重号或越出分段；接口引用的事件全在事件目录里；文档引用的“表.列”在校验库里都存在；路线图用到的权限点与能力点都在注册表里。复跑方法见第 9 节。
- **需要拍板的事**：113 项，按法务、财务、业务、安全与研发、产品与设计分组汇总在第 8 节，每项都有默认做法。没有回复就按默认做法实现。

## 4. 关键约定（摘要）

完整规则见[通用约定](api/00-conventions.md)，下面只列影响面最大的几条。

| 方面 | 约定 | 编号 |
| --- | --- | --- |
| 分组与认证 | 商家端 `/api/v1/m`：不透明会话令牌 + `X-Store-Id`；后台 `/api/v1/admin`：`__Host-` Cookie + 自定义头 + Origin 校验；下载页 `/api/v1/portal`：Cookie + 自定义头；回调 `/api/v1/hooks`：按渠道验签 | C1–C6 |
| 命名 | 一张表一个资源名（登记在资源登记表）；`operationId` = `<组>.<资源>[.<子资源>].<动作>`，全仓唯一，同时是幂等、限流的作用域；凭证不进路径 | C9–C16 |
| 响应与错误 | 成功 `{ code: 0, message, data }`；错误 `{ code, error, message, retryable, requestId, fieldErrors?, details? }`，端上只按符号名判断；429 只给限流 | C21–C28 |
| 数据格式 | 主键 UUID v7 字符串；金额整数分（`…Fen`）、积分整数（`…Points`）；`bigint` 出接口为字符串；时刻 ISO 8601；字典编码响应给 `DictRef`、请求收编码 | C29–C39、C85 |
| 列表与计数 | 商家端、下载页游标分页不给总数；后台页码分页带总数，大表游标加封顶近似数；页签计数统一由 `GET …/summary` 给；导出一律走异步任务 | C42–C46、C64、C83 |
| 幂等与并发 | 写接口 `required` / `natural` / `none` 三选一，状态迁移一律 `required`；结果含签名地址、激活码等的只存脱敏结果；内容编辑带 `lockVersion`；事务外调外部服务的走三段式 | C47–C54 |
| 读不写库 | GET 不写库；需要留痕的读取改为 `POST …/download-urls`、`…/playback-urls`、`/admin/pii-reveals`；试算一律 `POST …/quote` | C13、C60 |
| 授权 | 商家端按能力点、店员视图在出站时裁剪；后台按权限点注册表，再验证跟注册表走，驳回接口按 C86 豁免；按对象判权的声明 `assert-in-handler` | C55–C58、C66、C67、C86 |
| 版本 | 三份 OpenAPI 分开生成；小程序每个在役版本打标签，服务端变更须对全部在役标签兼容 | C74–C80 |

## 6. 相对数据模型与草案的变化

### 6.1 回写数据模型的改动

写契约时发现的数据模型缺口，按裁决回写到了分组文档（各分组文末“接口阶段回写”一段逐条列出），回写后 [tools/schema-check](../tools/schema-check/README.md) 仍全部通过。改了表结构或取值的只有下列三处，其余是状态机行、说明、守卫、事件、定时器与种子数据。

| 改动 | 分组 | 裁决 |
| --- | --- | --- |
| `file_object` 加列 `erased_at`（彻底删除标记）与 CHECK `ck_file_object_erased_at`；状态机补“员工彻底删除”三行，恢复按该列判断 | 06 | A141 |
| `episode_output.source` 加取值 `normalized`（规格化产物） | 10 | A142 |
| `production_record.production_tier` 的 `premium` 改为 `top` | 06 | A98 |

其余回写的主要内容：退款回调晚到时退款申请补 `pending_execution → done`（08，A102）；老板更换时为新老板建号与建成员行（02，A143）；审批期间修正识别字段给审批单升锁版本（03、04，A143）；状态历史的停留时长改为“与同一链上一行之间的一段”（01，A144）；客服工单的定时器键与补充说明事件（01、12，A144）；字典扩展属性与种子（14，A145）；授权书验真地址带版次（13，A100）；广告版本的查看方式由系统按开关写入（09，A97）；媒体任务人工重试、预告片源文件引用、可播放资产停用（06，A141）；以及第二批回写（ZIP 打包的重建与只查不建选项、媒体回调的唤醒守卫、清扫任务的步骤、协议草稿文件的释放（06、13）；31 个通知场景补登（13）；审计类别补登与执行时限定时器的存续（03）；回调收件的去重字段与差异单去重键（15、08）；商城配置的校验口径、“取消与退款驳回”原因场景、执行人与审批人分离的参数（14）；补记渠道退款遇退款闸门不回收（07，A156）；事件改名与定时器去重键的适用范围（01、02））。

### 6.2 相对草案的主要取舍

九份设计草案的接口写法不一，契约统一了 25 处，逐条见约定第 14 节。影响最大的几处：主键在接口里是 UUID v7 字符串（不是 `bigint`）；门店上下文用请求头 `X-Store-Id`（不进路径）；错误体拆出 `fieldErrors`，另加 `retryable` 与 `requestId`；签发下载地址统一为 `POST …/download-urls`，GET 不写库；三端退出登录统一为 `DELETE /<端>/sessions/current`；文本内容安全检测服务不可用时 V1.0 一律拒收（草案是先接受、排队补检，数据模型没有落点）。草案 d1–d7 不回改（A146），d8、d9 同样处理；草案与契约不一致处以契约为准。

## 1. 选型原则

1. **沿用团队已经跑通的栈**。参考工程 `timavia-liyo-project` 的服务端、小程序、契约链路与工程规范直接沿用，只在它没有覆盖的地方（运营后台前端、支付、媒体分发、部署形态）另选。
2. **够用即止**。早期请求量是个位数到几十每秒，不为假想的规模引入组件。
3. **境内可达、可备案**。小程序的合法域名必须已备案；模型、短信、存储一律用境内端点。
4. **版本精确锁定**。今天有多个常用包的 `latest` 标签指向不该安装的版本（typescript、prisma、NutUI 会直接装错，pnpm、vitest 的新大版本暂不跟进，见第 5 节），任何不带版本号的安装都可能出错。
5. **外部能力可替换**。每项外部能力经 Provider 接口接入，选型错了只换驱动。

## 3. 分层说明

### 3.2 运营后台与电脑端下载页

后台有 56 个画板，以筛选表格、“左队列 + 右详情”审核工作台、多页签详情、审批弹层为主，图表只有柱状、折线、堆叠条几种。

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **React 19 + Vite 8 + Ant Design 6 + 自建业务构件（选）** | 采用 | 团队熟悉 React；antd 6 是当前稳定线；56 个画板可归成 7 种页面骨架、约 20 个共享构件，自建成本可控 |
| antd 5 + ProComponents 2.8 | 不选 | antd 5 的维护期约 2026-11 结束；ProComponents 稳定版只支持 antd 4/5，且自 2025-07 起无新版（核实 fe-3、fe-4） |
| antd 6 + ProComponents 3 预发布版 | 不选 | 3.x 仍是预发布号，背不稳定依赖 |
| Refine | 不选 | 其 antd 适配仍锁 antd 5，支持 antd 6 的请求十个月无人回应（核实 fe-5） |
| Vue 3 中后台模板 | 不选 | 团队需另学一套；与小程序侧无法共享类型与工具习惯 |

配套选择：

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 路由 | TanStack Router | 查询参数类型化，适合筛选条件多的列表页 |
| 数据请求 | TanStack Query + openapi-fetch | 类型直接来自契约生成物 |
| 图表 | ECharts 6，自写约 30 行的 React 封装 | 不装 `echarts-for-react`：该包 2026-05 被投毒发布过恶意版本（核实 fe-8） |
| 导入导出 | 只在服务端生成，前端不引 Excel 库 | npm 上的 `xlsx` 有两个高危漏洞且无修复版，`exceljs` 已停更（核实 fe-9） |
| 大文件上传 | cos-js-sdk-v5 分块续传 | 原片与成片由剪辑师在浏览器批量上传 |
| 部署 | 与接口同源 | 不开跨域；会话 Cookie 可用 `__Host-` 前缀 |

共享构件（约 20 个）中最重要的四个：筛选表格页、队列工作台（资质审核、对公收款、广告任务、成片交付、链接核验、账号核验、下架核查、发票等 8 个以上页面同构）、确认与驳回弹层（回显 + 强制勾选 + 原因字典）、上传字段。

### 3.4 数据库

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **托管 PostgreSQL 17，一主一备（选）** | 采用 | 含支付与积分账本，单机每日导出的丢失窗口最长 24 小时不可接受；托管版自带高可用、按时间点恢复、备份保留可配。按时间点恢复的方式是克隆出新实例，可选时间窗口官方文档前后说法不一，须在控制台实测（核实 inf-1）。17 发布已两年，Prisma 7 官方支持（核实 ver-5） |
| PostgreSQL 18 | 备选 | 同样受支持；新特性本项目用不上 |
| 自建（参考工程做法） | 不选 | 备份与高可用要自己做，省下的钱每月约 400 元 |

需确认：托管实例是否提供 `btree_gist` 扩展（订阅周期不重叠的排他约束用）；不提供则退化为服务层校验加每日校验。预发用节点本地的 PostgreSQL 17 容器（[ADR-041](adr/0041-预发先行-单机预发-共用AppID.md)），这条确认改到建生产时。

### 3.5 队列与缓存

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **BullMQ 6 + 托管 Redis 7.0 标准架构（选，以验证通过为前提）** | 采用 | 团队已有经验；队列只是执行通道，任务状态都在数据库 |
| 每节点一个自建 Redis，只给本机 worker 用 | 退路 | 托管版验证不过时启用；节点重启后队列由数据库扫描重建 |
| BullMQ 6 的 PostgreSQL 后端、pg-boss | 不选 | 前者随 BullMQ 6.0.0 于 2026-07-30 才发布，官方称 Redis 后端仍是最经实战检验的选择；后者团队没用过；一年后可复评 |
| 腾讯云 Redis 集群架构 | 不采用 | 其要求 Lua 脚本里的键都来自 KEYS 数组，与 BullMQ 在脚本内拼键的写法冲突（核实 inf-2；由两份官方文档推断，未实测） |

注意事项：BullMQ 没有对腾讯云 Redis 的兼容性声明，标准架构带代理层，阻塞命令与断连重连须实测；`maxmemory-policy` 保持默认的 `noeviction`，不要按厂商建议改成 `allkeys-lru`；BullMQ 6 移除了旧的重复任务接口，本项目也不使用其调度器，周期任务登记在数据库。预发用节点本地的 Redis 7 容器（`noeviction`，开 AOF；ADR-041），托管 Redis 的实测改到建生产时。

### 3.6 对象存储、媒体与分发

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| **腾讯云 COS 私有桶 + 数据万象 + CDN（选）** | 采用 | 参考工程已在用 COS；按调研估算，各家媒体成本早期都在每月 600–800 元，差距一两百元，价格不是决定因素；数据万象的转码、打包、审核以对象存储为中心，接入最少 |
| 腾讯云点播 | 备选 | 仅当预告片要做“每个分片都签名的 HLS”时启用；其溯源水印要求视频 7 分钟以上，对短剧单集不适用（核实 cos-6） |
| 阿里云 OSS + 视频点播 | 不选 | 应用与存储应同云同地域，跨云读写按外网流量计费 |

预发先行阶段节点在阿里云、存储在腾讯云，正是上表不取的跨云形态：服务端读写对象走公网，按外网流量计费，节点回传与备份还占节点的出网带宽。代价与何时回到同云见 ADR-041。

要点：

- **四个桶**（证照类、素材类、媒体类、公开分发类），只有公开分发类挂 CDN。CDN 回源鉴权是桶级授权，把会挂 CDN 的内容单独成桶，暴露面由桶边界保证。
- **预告片出两档 MP4**（480P、720P），经 CDN 鉴权分发；HLS 多码率自适应要用工作流实现，且分片签名需验证，列为增强项（业务已确认接受两档 MP4）。业务已决定 V1.0 小程序内不播放预告片，所以预告片的转码与 CDN 鉴权分发不在 V1.0 的关键路径上，后台短剧库仍可上传预告片源文件备用。
- **成片、样片、广告不走 CDN**，用源站短时预签名地址：量小、可按业务授权即时控制。另一个原因是拟用的 CDN 鉴权模式不支持在地址上再附带查询参数，无法指定下载文件名（TypeA 见核实 cos 组额外发现，TypeD 为媒体草案作者实查；TypeB、TypeC 未核）。
- **打包下载**用数据万象异步打包（按打包前大小 0.05 元/GB），压缩包当作可丢弃的缓存。
- **流量成本**：走 CDN 约 0.36 元/GB（CDN 0.21 + 回源 0.15），源站外网下行约 0.5 元/GB。

## 4. 重点决策的取舍

### 4.1 商家端令牌：会话而非 JWT

参考工程用 JWT 双令牌与刷新轮换，已知缺陷是禁用账号后访问令牌仍有效两小时、刷新轮换不在事务里。新产品有“更换老板、移除店员后立即失效”的要求，且量级只有每请求一到两次主键查询，因此改为不透明会话令牌、会话行存数据库。会话失效后，客户端把并发的请求合并为一次静默登录，成功后各重放一次。

### 4.2 后台第二因子：TOTP 而非短信

原型画的是短信验证码。短信作为第二因子强度较弱，且让登录依赖短信通道与签名报备。默认采用密码 + TOTP，短信只用于发放一次性激活码。企业微信扫码作为可选因子延后（须小程序、企业微信、后台域名备案主体一致）。业务已确认采用 TOTP（2026-10-02）。

### 4.3 事件：出站表而非“提交后入队”

参考工程的做法是事务提交后入队、入队失败靠补偿扫描。新产品在积分扣减、付款入账之后有必须发生的后续动作（生成工单、发通知、出授权书），入队与数据库事务不原子就可能丢。改为事务内写出站事件表，由任务进程中继。

### 4.4 制作：V1.0 不建合成管线

PRD 把“AI 定制制作”列入技术方案评审，但 PRD 与原型里 V1.0 没有任何系统内合成的功能点：后台只需“上传样片和成片、按清单质检”。V1.0 只引入一个无网络的隔离容器做体检与标识写入，不转码、不合成。V1.1 的自动贴片用独立主机上的 ffmpeg 进程：先把原片与广告规格化，再做流拷贝拼接，每集不到 1 秒；云端模板合成一部 60 集约 8 元，可作替代。

## 5. 版本锁定

### 5.1 规则

1. 全部依赖写精确版本，提交锁文件，持续集成用 `--frozen-lockfile`。
2. 锁定值取“该大版本线上已发布满 7 天的最新补丁”，并配置 pnpm 的最小发布时长为 7 天。
3. 关闭依赖的安装脚本，只对白名单包放行。
4. 每月一次依赖巡检；大版本升级只在约定时点人工评估。

## 8. 成本估算

量级假设：早期数百商家、约 100 单/月、每单成片约 3GB；增长期约 10 倍。除注明者外为刊例价估算，签约前须用官方价格计算器复核。

| 项 | 早期（元/月） | 增长期（元/月） |
| --- | --- | --- |
| 应用节点（生产 2 台 + 预发 1 台） | 450–750 | 1,350–2,250 |
| 负载均衡 | 60–120 | 150–300 |
| PostgreSQL（生产双机 + 预发） | 520–620 | 1,600–2,700 |
| Redis | 约 120 | 约 340 |
| 对象存储 | 首月约 120，第 12 个月约 540 | 约 4,700（做归档后 2,500–3,500） |
| 下载与播放流量 | 210–270 | 2,100–2,800 |
| 数据万象 | 50–100 | 300–600 |
| 日志、错误监控 | 250–300 | 400–600 |
| 短信、识别、转写、模型、手机号组件 | 100–300 | 800–1,500 |
| **合计** | **约 1,900–2,700，年末升至 2,300–3,100** | **约 9,500–15,800**（下限按存储做归档后计） |

读法：早期的钱主要花在“托管数据库 + 两台节点”，比单机自建每月多约 800–1,000 元，这是 99.9% 与账务安全的底线。增长期的大头是存储与流量，取决于“成片在使用期结束后保留多久”这条待定的业务规则。计算资源在可见的未来不是瓶颈。上表是两套环境建齐后的估算。预发先行阶段沿用现有的服务器，没有托管库、托管 Redis 与负载均衡的费用，多出跨云的流量费（ADR-041）。

## 9. 明确不引入

| 不引入 | 原因 |
| --- | --- |
| 微服务、服务网格、消息中间件 | 规模不需要；订购提交要同步冻结积分，拆开就丢了单事务 |
| Elasticsearch | 短剧几十到几百部，数据库模糊匹配足够 |
| 数仓、BI 平台 | 报表为月度聚合加近 6 个月趋势，业务库直接聚合 |
| Prometheus、Grafana、自建日志栈 | SQL 探针与云日志足够 |
| Kubernetes | 两三个服务、小团队 |
| 状态机库、工作流引擎 | 状态与迁移是数据，手写迁移表更直观、可测 |
| ProComponents、Refine | 与 antd 6 不配套 |
| 前端 Excel 库 | 安全问题；导出只走服务端 |
| 小程序虚拟支付接入 | V1.0 不实现也不预留枚举；被判定时的退路见 [03](03-key-designs.md) 第 1.6 节 |
| 抖音、视频号发布接口 | 平台不开放 |

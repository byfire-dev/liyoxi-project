这 9 个画板对架构最要紧的三件事：

1. **积分账本是全系统的资金级核心**：两类积分（套餐/加购）+ 冻结 + 7 种流水类型 + 按期清零 + 过期冻结 + 人工调整审批，并且“参数/价格调整只影响之后提交的单据”，要求事务一致、幂等、规则快照。
2. **大量“到点生效 / 到点触发”的规则**：套餐调整提前 30 天排期、单剧调价定时生效、按开通日每月发放、到期日 24:00 清零、7/3/1 与 30/7/1 提醒、授权期不足自动停止订购、工单 30 分钟响应 / 24 小时方案 / 3 天自动解决。需要可靠的定时与延时任务基础设施。
3. **短剧原片是大文件媒体资产**：单集约 80–93 MB、每部 30–80 集、支持多选或 ZIP 批量上传与替换、上传后转码。需要对象存储直传（分片/断点续传）+ 异步转码流水线。

### 1.4 前端能力
- 服务端分页表格 + 多条件筛选（文本、下拉、复选开关）；空态；行内状态标签（热度/状态色）。
- 二次确认弹窗（带原因下拉与备注）；全局 toast。
- 行级按钮按状态显隐/禁用，另需叠加按钮级权限（内容运营/超管才能看到“下架”“新建”）。
- PRD 7 开头写明“所有列表支持筛选、分页和导出”（`PRD.md:737`），本画板没有画导出按钮，【推断】仍需提供。

### 1.5 原型有、PRD 没写或不一致
1. **两个不同的阈值并存**：“90 天内到期提醒”按天算（今天 09-30 → 12-29，`Dramas.txt:95`），“停止订购”按自然月算（授权至 12-25 → 09-25 起停止，`Dramas.txt:94`）。PRD 7.2-2 两个数都写了，但没说清两者口径不同。实现上是两个独立参数：最短可订授权期（Params 页，1–12 个月）与版权到期提醒天数（系统参数 30–180 天，`SysParams.txt:98`）。
2. **“停止订购”是派生状态而非剧的状态**：剧仍是“已上架”，只是不可订购（`Dramas.txt:133-134`）；Pricing 页把它当成一种状态显示（`Pricing.txt:110`）。【推断】数据模型需要 `orderable` 派生字段或 `stopOrderFrom` 日期。
3. **授权已结束的剧处于“已下架”且不可重新上架**（示例《旧时光照相馆》，授权至 09-28，`Dramas.txt:91,138-139`）。PRD 没写“授权到期自动下架”，【推断】需要到期自动下架的定时任务。
4. 列“上线中成片”“9 月订购”为统计列，PRD 7.2 未列出。
5. 题材筛选是 7 个固定值，但示例数据里出现“都市温情”这样的组合词（`Dramas.txt:91`），筛选用包含匹配（`Dramas.txt:99`）。【推断】题材应做成字典多选，存储为数组。
6. 下架原因枚举（4 项）PRD 未定义。

### 2.4 前端能力
- 多页签长表单，页签上有“有待补充项”红点（`DramaEdit.txt:43,186-192`）；右侧粘性侧栏（校验清单、积分价、日志）。

### 2.5 原型有、PRD 没写或不一致
1. **上架校验缺“改编权”**：PRD 7.2-1 写“版权允许转授权、剪辑植入与改编”（`PRD.md:758`），10.3 写要核验“信息网络传播权、转授权权、剪辑植入权与改编权”；原型版权信息只有“是否可转授权”“是否可剪辑植入”两项，校验也只查这两项（`DramaEdit.txt:79-80,196`）。字段与校验项需补齐。
2. **上架校验不含原片完整性**：5 项校验里没有“全部剧集原片已上传且转码完成”，也没有封面（`DramaEdit.txt:193-199`）。【推断】应补，否则上架后订购无法开工。
3. **已上架剧的修改即时生效、无复核**：“修改已保存，商城展示同步更新”（`DramaEdit.txt:261`）。若改动了许可/版权字段，是否需要重跑上架校验，PRD 与原型都没说。
4. **替换原片的规则 PRD 未写**：“已交付的成片不受影响，之后的样片与成片合成使用新原片；内容有实质变更的，须重新核验许可信息”（`DramaEdit.txt:148`）。意味着成片必须记录它用的是哪一版原片（原片要有版本）。
5. **ZIP 与 200MB 上限的口径**：“支持多选视频文件或上传 ZIP 压缩包，单个文件不超过 200MB”（`DramaEdit.txt:146`）。一部 60 集的 ZIP 约 5 GB（60 × 约 85 MB），【推断】200MB 指包内单个视频，ZIP 本身需另定上限并在服务端解包。
6. 剧集有“标题”“状态”“文件大小”字段，角色有“饰演者”字段，版权有效期是起止两个日期，PRD 7.2 字段表都没列。
7. 试看集数默认取系统参数 3 集、可按剧调 0–10（`DramaEdit.txt:221`），与 PRD 12.3 第 8 项待确认一致。
8. 类别说明文案“三类 其他微短剧，平台审核”（`DramaEdit.txt:309`）PRD 未写。

## 3. Plans — 套餐与积分 · 套餐管理

### 3.1 用途与 PRD 对应

### 6.5 原型有、PRD 没写或不一致
1. **调整原因是固定枚举且没有自由文本**（`Pricing.txt:78`）；但示例数据与记录里的原因是自由描述（“新剧热度高”“80 集且制作质量高”“集数少、上线较久”，`Pricing.txt:104-109`），两者对不上。【推断】需要“原因枚举 + 备注”两个字段。
2. 单剧价只校验 ≥100，没有上限，也不受等级模板约束：示例《锦绣小厨娘》是 B 级却定价 2,600，高于 A 级模板 2,000（`Pricing.txt:108`）。
3. 停止订购的剧不能调价、草稿可以先定价“上架后生效”（`Pricing.txt:124,160`），PRD 未写。
4. 生效时间选项是“立即”或某天 00:00（`Pricing.txt:78`）；PRD 只说“设置生效时间”。示例里有提前 3 天提交的记录（09-26 提交、09-29 00:00 生效，`Pricing.txt:138`），说明存在“待生效”的调价单，【推断】还需要“撤销待生效调价”的能力，原型没画。
5. 变价会主动通知选剧单里的商家（`Pricing.txt:187`）；PRD 6.7 只写了选剧单内打标，没写推送。
6. 调价没有审批；PRD 3.3 里的“改价（V1.1）须审批”指的是付款单改价，不是剧目积分价。是否需要对剧目调价加审批，由业务定。
7. 实扣公式 `S = round(P × R × (1 + T))` 与 PRD 2.4 一致；示例“2,600 × 0.9 × (1 + 20%) = 2,808”（`PointAccounts.txt:145`）可作为测试用例。

### 7.5 原型有、PRD 没写或不一致
1. **流水类型多出“加购”**：PRD 7.3-5 列的是发放、冻结、扣减、退回、清零、调整 6 种；原型有 7 种（`PointAccounts.txt:224`）。
2. **“冻结”一词两种含义**：订购/广告占用的冻结，与套餐过期时加购积分的冻结，在流水里用了同一个类型（`PointAccounts.txt:208`）。数据模型必须区分（否则“有冻结积分”筛选、“冻结积分”汇总都会算错）。
3. **发起入口不一致**：PRD 7.9-3 与 CreditAdjust 画板都说调整“在商家详情中发起”（`CreditAdjust.txt:43`）；本画板也能发起（`PointAccounts.txt:66`）。
4. **审批层级不一致**：PRD 12.3 第 4 项记录“原型按交付经理发起、交付主管审批，积分入账另经财务审批设计”；本画板是直接“提交财务审批”，CreditAdjust 的申请人里交付主管、交付经理、客服都有（`CreditAdjust.txt:121-126`），只有财务一级。
5. **按钮权限与模块权限不一致**：PRD 3.3 中“套餐与积分”模块客服、交付经理只有“查看”，但他们正是调整的发起人。说明“手动调整”必须是独立的按钮级权限点，不能跟模块的编辑权限绑在一起。
6. **补偿口径是原型新增的**：“成片交付超时 16 小时，补偿 ＋270 套餐积分（该订购应扣积分的 10%）”（`PointAccounts.txt:197`；`CreditAdjust.txt:121,123`）。PRD 没有“超时补偿 10%”这条规则。
7. **调整原因枚举**含“运营活动赠送”（`PointAccounts.txt:91`），PRD 只举了“补偿、纠错”。
8. **已过期账户不能调整**（`PointAccounts.txt:263`）PRD 未写。
9. **订购取消的退回要走财务退款单**：“方案确认阶段取消，扣除 10%（270 积分）后退回 2,430 积分，待财务审批（退款单 TK20260929001）”（`PointAccounts.txt:177`）。即积分退回与现金退款共用“退款管理”的审批与执行（与 canvas.json readme 第 7 条一致）。
10. 商家端积分明细的筛选叫“过期”（`slim/merchant/Ledger.txt:42`；PRD 6.15），后台叫“清零”，同一事实两种叫法。
11. KPI“积分余额…其中冻结”暗示余额含冻结，而账户详情里可用积分不含冻结，口径需统一。
12. PRD 6.15 说每条流水展示“所属门店”，后台流水表没有门店列，只在文字里说“门店订购时注明门店”。

- **会话式时间线**：4 种视觉样式的条目（商家/回复/备注/系统），图片缩略图与预览，图例。
- 双模式输入区（回复 / 备注切换，底色区分防误发）、图片上传、快捷回复下拉、字数限制。
- 三个弹窗（转派、处理结果、关闭），必填校验。
- 侧栏信息卡与关联业务跳转卡片（跨模块深链：订单详情、交付工单详情、广告任务、商家详情）。
- 手机号等敏感字段脱敏展示（PRD 10.2-1）。
- 【推断】商家补充消息到达时页面应能刷新（轮询即可）。

### 9.5 原型有、PRD 没写或不一致
1. **“给出处理方案”没有对应动作**：时效栏有“处理方案”用时（`ServiceDetail.txt:212`），列表有“已给出方案”（`Service.txt:155-156`），但详情页只有“回复”和“提交处理结果”，没有“标记为处理方案”的动作。系统如何判定哪条回复算“给出方案”，需要定义。
2. **后台详情没有“已解决”及“重新打开”的呈现**：状态映射只有处理中 / 待商家确认 / 已关闭（`ServiceDetail.txt:204`）；商家端可以在已解决后重新打开并回到“处理中”（`slim/merchant/TicketDone.txt:40`；PRD 6.12-5）。重新打开后的时效怎么重算、有无次数或期限限制，都没写。
3. **商家撤回的落点**：商家端撤回后“工单将关闭”（`slim/merchant/Ticket.txt:39`），对应后台关闭原因“商家撤回”；即“已关闭”既可由后台操作也可由商家触发。
4. 关闭原因 3 项、转派原因 4 项、各输入框字数上限（回复 500、关闭说明 200、转派说明 60、分配说明 100）是原型给出的。
5. **回复用“小程序订阅消息”通知**（`ServiceDetail.txt:242`）。PRD 7.11-4 只说有订阅消息模板。微信一次性订阅消息需要用户逐次授权，多轮回复能否每次都送达是技术风险（见 §11）。
6. **时间线混入其他业务域的事件**（广告任务上传新版本，`ServiceDetail.txt:193`），PRD 7.8-2 只说“关联订单与交付工单”。实现上需要按关联单号订阅领域事件。
7. 员工回复图片的数量上限没写（商家端是 ≤9 张，PRD 6.12-4）。
8. “服务经理 · 累计工单 3 个”为统计字段，PRD 未列。

### 10.2 状态机

**① 短剧 Drama.status**
```
草稿 --[上架：5 项校验全过]--> 已上架 --[下架：选原因]--> 已下架
已下架 --[重新上架：再次校验；授权已结束不可]--> 已上架
已上架 --[授权期结束：定时任务]--> 已下架（【推断】）
```
派生标志：`可订购`（已上架且剩余授权期 ≥ 最短可订授权期）；`停止订购`（自 validTo − N 个月起）；`授权已结束`。

**② 剧集原片**：`上传中 → 转码中 → 已就绪`；替换原片时回到“转码中”，完成后自动生效。

**③ 套餐调整 PlanChange / 单剧调价 DramaPriceChange**：`待生效 → 已生效`（立即生效的调价直接进入已生效）；套餐列头显示“已上架 / 调整待生效”。

**④ 积分包**：`已上架 ⇄ 已下架`。

**⑤ 积分冻结单 PointHold**
```
[提交订购 / 广告需求] 冻结中 --[资质通过并开始制作 / 剪辑师开始制作]--> 已扣减
冻结中 --[开始制作前取消 / 资质不通过且无法补正]--> 已退回（全额）
已扣减 --[制作中取消：按阶段扣 10% / 30% / 50%，经财务审批]--> 部分退回
已扣减 --[平台原因无法交付]--> 已退回（经审批）
```

**⑥ 积分账户随套餐状态**：`生效中 --[到期日 24:00：套餐积分清零 + 加购积分冻结]--> 已过期 --[续费：恢复加购积分 + 发放新一期]--> 生效中`。周期性事件：每月开通日发放、期末清零、到期前 7/3/1 天提醒。

**⑦ 积分调整单**：`待审批 --[财务通过：入账 + 通知商家]--> 已通过`；`待审批 --[财务驳回：填原因 + 通知申请人]--> 已驳回`。

**⑧ 客服工单 ServiceTicket.status**
```
[商家在小程序提交] --> 待受理 --[客服首次回复]--> 处理中
[后台登记（电话/在线客服）] --> 处理中
处理中 --[提交处理结果]--> 待商家确认 --[商家确认 / 3 天未确认自动]--> 已解决
已解决 --[商家重新打开]--> 处理中
未关闭的任意状态 --[后台关闭（重复/无效）或商家撤回]--> 已关闭（终态，不可回复）
```
时效子状态：正常 → 临近 → 响应超时（提醒负责人并升级至客服主管）。计时点：首次响应 30 分钟（只算工作时间）、处理方案 24 小时（自创建起、自然时间）、待确认 3 天自动解决（自然时间）。

### 10.4 通用组件与通用能力候选

**前端共享组件**
1. 后台框架：左侧两级菜单（带角标）、面包屑、全局搜索（商家/订单号/工单号）、消息通知铃、当前用户（9 个画板页头一致，如 `Dramas.txt:10-31`）。
2. 筛选表格：筛选栏（文本/下拉/开关/重置）+ 服务端分页 + 空态 + 导出；带计数的状态页签。
3. 状态标签与色板（热度 S/A/B/C、上架状态、工单状态、流水类型、优先级）。
4. 弹窗表单（必填校验、字数统计、汇总报错）与“原因下拉 + 说明”的二次确认弹窗。
5. KPI 卡片行；试算器（升级补差、订购积分）；权益对比矩阵。
6. 文件上传（图片/视频/PDF、多文件、ZIP、进度、断点续传）与预览（视频播放、图片、PDF）。
7. 时间线（操作日志、调价记录、公告记录、工单处理记录）。
8. 人员选择器（角色、当前负责人标记、负载数）。
9. 金额/积分格式化（¥ + 千分位 + 2 位小数；积分整数 + 千分位；＋/− 号）—— PRD 8.3-3。
10. 图表封装（本组只有柱状图）。
11. 权限指令/组件：按钮级显隐、数据范围。

**后端共享服务**
1. **积分账本服务**（冻结/扣减/退回/发放/清零/过期冻结/调整；幂等；行锁；追加写流水）。
2. **计价服务**（S＝round(P×R×(1+T))、广告计费、升级补差、取消扣除）—— 后台试算与商家端下单共用一份代码。
3. **版本化参数服务**（积分参数 + 系统参数，带变更记录与快照）。
4. **定时生效 / 延时任务调度**（见上表）。
5. **审批服务**（积分调整、退款等“发起 → 审批 → 执行”的轻量流程）。
6. **操作日志服务**（对象级日志 + 全局日志，保留 ≥3 年、不可改删，`SysParams.txt:106`；PRD 7.12-5）。
7. **通知服务**（小程序订阅消息、站内消息中心、短信、企业微信；按消息模板）。
8. **媒体服务**（直传凭证、转码、时长/画幅探测、签名播放地址、水印）。
9. **单号生成**（KF/LYX/FK/GG/JF/TZ/TK + 日期 + 序号）。
10. **工作日历与时效计算**（工作时间、节假日、调休；“工作分钟”与自然时间两种计时）。
11. **导出服务**（按筛选条件导出，小量同步、大量异步）。
12. **RBAC**（菜单 + 按钮 + 数据范围，含主管看全组）。
13. **领域事件总线**（调价 → 选剧单打标；广告任务事件 → 工单时间线；状态变更 → 通知）。

## 11. 风险与冲突（供架构设计关注）

1. **积分来源与周期的追溯**：扣减顺序“先套餐后加购”、冻结跨周期视为已使用、退回“按原来源，原周期已结束则转加购”三条规则叠加，要求冻结单记录来源拆分与所属周期；如果只存两个余额数字，退回时无法还原。
2. **“冻结”一词两义**混在同一个流水类型里（§7.5-2），不拆开会导致汇总与筛选错误。
3. **模板调价的批量联动**：改一个等级模板会同时改动 4–8 部剧的现价并让相关选剧单全部进入“积分价已变动”，且原型没有生效时间与公告（§5.5-3/4）。
4. **订阅消息送达率**：工单每次回复都靠小程序订阅消息通知商家（`ServiceDetail.txt:242`），而一次性订阅消息需用户逐次授权；多轮沟通时后续回复可能发不出去，需要站内消息中心兜底或改用其他通道。
5. **两套计时口径**（工作时间 30 分钟 vs 自然时间 24 小时 / 3 天）与节假日日历（§8.5-3），实现与测试都容易出错。
6. **当班名单缺失**（§8.5-4）：没有排班数据，轮流分配无法落地。
7. **上架校验缺项**（改编权、原片完整性，§2.5-1/2）与**已上架剧修改无复核**（§2.5-3）带来合规风险（PRD 10.3）。
8. **公告依赖 V1.1 功能**（§3.5-2）：V1.0 的套餐调整流程缺推送通道。
9. **原片版本与成片的对应**（§2.5-4）：替换原片后，旧成片要能追溯所用原片版本。
10. **存储与渲染成本**（§10.5 存储量级）：若每份定制成片都整部落盘，量级远超原片库，是 V1.0 就要面对的容量与成本问题。
11. **审批层级与权限点不一致**（§7.5-3/4/5）：影响 RBAC 权限点设计与审批服务的层级模型。
12. **两端字典不一致**（工单类型 10 vs 9、“清零” vs “过期”）：需要单一字典源。

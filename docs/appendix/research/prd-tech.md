## 0. 一页结论（对架构影响最大的事实）

1. **两条完全独立的“钱”链路**：付款单（人民币，只在开通 / 续费 / 升级套餐与加购积分时发生，微信支付 + 对公转账）与订购单（只扣积分，不付款、不开票）。【PRD §2.1、§5.3，PRD.md:116、381】
2. **积分是带批次、带有效期、带冻结的内部账本**：套餐积分按月发放、周期末清零；加购积分长期有效但套餐过期时“挂起”；先冻结、开始制作时扣减；退回时要知道“原周期是否已结束”。这必须用“账户 + 批次 + 冻结单 + 只增流水”实现，不能只存一个余额。【PRD §2.3，PRD.md:140-155】
3. **订购单是聚合，真正的状态机在“每部剧”上**：一张订购单可含多部剧，“逐部计算、分别冻结与扣减”，每部剧生成一张交付工单（JF…-1、-2），取消时“按每部剧所处阶段分别退回”。【PRD §2.4 PRD.md:159；原型 admin/OrderDetail、admin/Tickets】
4. **归属维度有两层**：套餐 / 积分 / 合同 / 发票按“经营主体”；订单 / 工单 / 渠道账号 / 素材 / 店员按“门店”。所有业务表都要同时带 `entity_id` 与 `store_id`。【PRD §6.16.1-1，PRD.md:702】
5. **大量时间驱动规则**（约 35 条，见第 4 节），且很多按“工作日 / 工作时间 + 法定节假日调休”计算，需要可靠的定时 / 延迟任务与工作日历服务。【PRD §5.2；原型 admin/SysParams】
6. **V1.0 不对接抖音 / 视频号任何接口**：发布、核验、巡检、下架全部是“人工 + 任务流 + 留证”。【PRD §6.10、§10.4】
7. **媒体是重资产**：原片、预告片（多码率 + 水印 + 防盗链）、样片（水印）、成片包（单部剧 2–5 GB，签名链接 7 天）、门店素材（视频最大 500MB、录音、文档）。【PRD §10.1、§10.2；原型 admin/Delivery 显示 3.1 GB / 5.4 GB】
8. **业务量级小、流程复杂**：原型示例为数百商家、月付款单约 200 笔、上线中剧目约 1,400 部——并发不是难点，账务正确性、状态机、审计与媒体才是。【原型 admin/Orders、admin/Payments、admin/Patrol，示例数据】
9. **V1.1 的服务商代操作 / 管理员授权 / 代发布 / 多主体** 需要在 V1.0 的身份与权限模型里预留“代理操作人（acting-as）”“付款人≠购买主体”“执行人可替换”三个扩展点。【PRD §2.10、§3.1、§6.14】

### 2.2 交付工单（11 步）【PRD §5.2，PRD.md:353-365；原型 admin/Tickets、admin/TicketDetail】

`待分配 → 方案确认 → 广告准备 → 样片制作 → 样片确认 → 批量合成 → 成片交付 → 待上线 → 上线核验 → 使用中（原型称“服务中”） → 到期下架 → 归档`

| 步 | 状态 | 负责 | 进入条件 / 动作 | 时限（可配置） | 回退 / 分支 |
|---|---|---|---|---|---|
| 1 | 待分配 | 系统、交付主管 | 订购成功且资质通过；按城市轮询自动分配或主管手动 | 2 小时（工作时间） | — |
| 2 | 方案确认 | 交付经理、商家 | 配置并推送方案；商家确认 | 1 个工作日 | 商家“联系服务经理修改”→ 方案“修改中”→ 重新推送 |
| 3 | 广告准备 | 剪辑师、商家 | 已确认广告直接复用（不耗时、不扣分）；否则走广告需求子流程 | 新制作 2 个工作日 | — |
| 4 | 样片制作 | 剪辑师、交付经理 | 制作第 1 集并质检 | 1 个工作日 | 质检不通过退回 |
| 5 | 样片确认 | 商家 | 确认或提修改意见（交付经理可代录） | 超 2 天自动提醒 | 修改 → 退回第 4 步（修改须 1 个工作日内） |
| 6 | 批量合成 | 剪辑师 | 全部剧集定制并逐集质检 | 2 个工作日 | 质检不通过退回 |
| 7 | 成片交付 | 发布专员 | 整理发布清单，4 项交付前检查，推送成片包 | 质检通过当日（原型：当日 18:00 前） | — |

| 9 | 上线核验 | 发布专员 | 核验 5 项 | 回填后 1 个工作日 | “需补充”→ 回到第 8 步，重新回填生成新核验任务 |
| 10 | 使用中 | 交付经理、发布专员 | 每周抽查；结束前 30 天生成下架任务 | 使用期内 | 巡检异常 → 通知商家 → 复查 |
| 11 | 到期下架 | 商家、发布专员 | 商家确认下架；核查并截图留证后归档 | 使用期结束后 1 个工作日 | 逾期未下架 → 升级主管 → 违约提醒 |

横向动作：催办商家（订阅消息 + 短信）、转移交付经理（在办含“服务中”一并移交）、取消（工单暂停 / 关闭）。商家端时间轴节点映射见【PRD §6.9-3】。

### 2.4 套餐订阅（主体维度）【PRD §2.2、§2.3-4、§6.15】

| 事件 | 生效时点 | 副作用 |
|---|---|---|
| 开通 | 支付成功 / 财务确认到账时 | 建立订阅周期，发放首月套餐积分，折扣与版本权益生效 |
| 每月发放 | 每月“开通日” | 发放当月套餐积分，周期内累计 |
| 续费（未过期） | 本期结束次日 | 新周期排队；到期时旧周期清零、新周期开始并发放 |
| 续费（已过期） | 续费当日起算（原型 admin/Renewals） | 立即恢复订购；加购积分解除挂起；发放新一期积分 |
| 升级 | 立即 | 补交本月剩余天数差价、补发积分差额（并入本期，期末清零）；折扣立即按新版本；到期日不变 |
| 降级 | 当前周期结束后 | 本期权益不变；生效前须移除超出的门店 / 成员 |
| 到期 | 到期日 24:00 | 套餐积分清零（`points_expire` 事件）；加购积分挂起；不能订购、不能提交广告需求、不能加购；在制订购继续交付；已上线成片不受影响 |
| 补偿延长 | 主管审批通过 | 本期与清零时间顺延，通知商家 |
| 退款 | 财务执行 | 套餐关闭，套餐积分作废 |

### 2.5 广告视频【PRD §6.4.3、§7.6-3；原型 admin/AdTasks】

`（待指派）→ 制作中 → 待确认 ⇄ 修改中 → 已确认`；已确认后仍可再次“提出修改”回到修改中（档案变更联动，计入修改次数，PRD §6.3.5-7）。

| 转移 | 触发者 | 副作用 |
|---|---|---|
| 提交需求 → 待指派 | 老板 | 冻结 `round(单价 × R)`；首次提交时签署《广告制作与交付服务协议》；生成广告制作任务 |
| 待指派 → 制作中 | 主管指派剪辑师（“开始制作”） | **冻结 → 扣减**（原型：指派即扣减）；首版 2 个工作日 SLA |
| 需求被退回（素材不全） | 剪辑师 / 交付经理 | 补充后重提，**不重复冻结** |
| 制作中 / 修改中 → 待确认 | 剪辑师上传第 N 版并推送 | 通知“广告待确认”；到期未确认自动提醒 |
| 待确认 → 已确认 | 老板 | 可在任意订购中复用，不再扣分 |
| 待确认 / 已确认 → 修改中 | 老板提修改意见 | 修改轮次 +1；超过免费次数（默认 2）时本次按 1 条扣积分（提交前弹窗）；修改须 1 个工作日内完成 |
| 任意 → 未交付退回 | 平台原因 | 退回对应积分（原型通过“积分调整：平台原因退回”实现） |

PRD 只列 4 种状态（制作中、待确认、修改中、已确认），原型多一个“待指派”。

### 2.6 资质审核【PRD §6.3.5】

`未提交 → 审核中 → 已通过 | 已驳回 →（修改后重提）审核中`；已通过后修改“资质、门店名称、门店地址、行业与品类”→ 重新进入审核中；修改其他字段无须重审。

副作用：通过 → 通知；该门店待开工订购开始制作并扣减积分；新增门店解锁订购 / 绑定账号 / 店员上传。驳回 → 通知（订阅消息，可补发短信）并展示原因。“不通过且无法补正”→ 订购取消并全额退回积分；套餐按 2.8 判断是否全额退款（原型 admin/Refunds TK20260913001）。

### 2.7 渠道账号【PRD §6.10.2】

`待核验 → 可用 | 异常`；`异常 →（重新提交截图）待核验`；`→ 已解绑`（存在交付中或上线中订单时禁止）。绑定 / 重新提交即生成账号核验任务（发布专员 1 个工作日）。只有“可用”账号可在订购时选择。

### 2.8 上线链接核验结果【PRD §6.10.1】

`核验中 → 已通过 | 需补充（附原因，可多选）→（重新回填）核验中`。通过 → 订购明细“上线中”，写入使用期起点；需补充 → 通知商家（订阅消息 + 短信）。

### 2.9 上线任务 / 下架任务

- 上线任务：`待发布 → 核验中 → 已完成`（原型 merchant/Publish）。
- 下架任务：`已生成（结束前 30 天）→ 商家已确认下架（方式：删除 / 仅自己可见）→ 已核查（截图留证，工单归档）`；分支 `逾期未下架 → 升级主管 → 违约提醒（要求 24 小时内下架）`。

### 2.10 客服工单【PRD §6.12-5、§7.8-3】

`待受理 →（客服首次回复）处理中 →（提交处理结果）待商家确认 →（商家确认或 3 天未确认）已解决`；`已解决 →（商家重新打开）处理中`；`任意未结状态 → 已关闭`（仅限重复 / 无效 / 商家撤回，须选原因并填写说明）。后台登记的电话 / 在线客服工单直接进入“处理中”（原型 admin/Service）。副作用：轮流自动分配；回复 → 订阅消息；转派 → 企业微信提醒；响应超时 → 提醒负责人并升级客服主管。

### 2.11 退款 / 取消申请

`待审批 → 待执行 → 已退款（现金）/ 已退回（积分）`；`待审批 → 已驳回`。审批、执行两步均须二次确认；已开票的付款须先开红字发票再执行。

### 2.12 发票申请

`待开票 → 已开具（电子：上传 PDF / OFD 并推送 + 发邮箱）| 已寄出（纸质：快递公司 + 运单号）`；`待开票 → 已驳回（须注明原因，商家可改后重提）`；退款场景另有 `→ 已红冲`。

### 2.13 审批类

- 积分调整：`待审批 → 已通过（入流水、通知商家）| 已驳回（通知申请人）`。
- 套餐有效期延长：`待主管审批 → 通过 | 驳回`。
- 商家归属变更（V1.1）、付款单改价（V1.1）：同构。

### 2.14 门店素材

商家端：`整理中 → 可直接使用 | 仅供参考 | 需补拍 | 需肖像授权 → 已采用`；后台：`待整理 → 已整理 → 已采用`。上传后自动转写 / 识别 / 打内容标签（异步），交付经理复核后变为“已整理”；采用 → 通知上传人；需补拍 / 需肖像授权 → 提醒上传人。

### 2.15 短剧

`草稿 →（上架校验通过）已上架 → 已下架 →（重新校验）已上架`。派生：`停止订购`（剩余授权期 < 最短可订授权期，自动）、`授权已结束`（不可再上架）。下架只影响之后的订购。

### 2.16 其他小状态机

- 成员邀请：`待接受 → 已加入 | 已撤回 | 已过期（24h）`。
- 对账日：`待对账 → 已对平 | 有差异 → 已处理差异`。
- 协议版本：`待生效 → 生效中 → 历史`。
- 套餐 / 积分包 / 积分价调整：`待生效 → 已生效`。
- 巡检：`待巡检 → 正常 | 异常 →（复查已恢复）正常`。
- 员工账号：`待启用 → 启用 ⇄ 已禁用`。
- 交付方案：`待确认 ⇄ 修改中 → 已确认`。

## 3. 精确计算规则与实现易错点

### 3.1 剧目应扣积分【PRD §2.4，PRD.md:161-170】

```
S = round( P × R × (1 + T) )      四舍五入取整
P = 剧目积分价（等级模板 + 单剧调整）
R = 套餐折扣率（基础 1、专业 0.9、旗舰 0.8，示例）
T = 顶级模型加扣比例（基础 / 专业选用时 20%，示例；不选用或旗舰版为 0）
```

- 一次订购多部剧：**逐部计算、分别冻结与扣减**；合计 = 各部 S 之和（不是对合计取整）。
- 广告：每条 `round(广告单价 × R)`，示例 50 → 专业版 45、旗舰版 40（原型 admin/PointAccounts 流水佐证）。顶级模型加扣只针对订剧。
- 超额修改：每次“按 1 条扣积分”，按修改当时的套餐折扣（原型 merchant/AdDetail：“每次按 1 条扣 45 积分”）。
- 提交时以**服务端重算**为准；积分价或折扣变动时提示重新确认【PRD §6.8-2】。
- 调价、调参“只影响之后提交的订购”；已冻结 / 已扣减按原价【PRD §2.4-1；原型 admin/Params】。

易错点【推断】：
1. 不要用二进制浮点。折扣率、加扣比例用整数（千分比 / 百分比）或十进制定点，按“先乘后除、HALF_UP”实现；各语言默认 `round` 行为不同（如银行家舍入），需统一并写单测覆盖 PRD §2.9 的 7 个示例。
2. 订购明细必须保存 P、R、T、S 的**快照**与使用的价格版本，不能事后按当前配置重算。
3. “带生效时间的调价”要求价格是时间版本化数据；选剧单需要能判断“加入时价格 ≠ 当前价格”。
4. 需要“报价校验”机制：前端提交时带上所见 S 或报价版本，服务端不一致则拒绝并返回新报价。

### 3.2 扣减顺序与冻结【PRD §2.3，PRD.md:142-155；示例 5】

- 先扣套餐积分（快到期的先用），不足再扣加购积分。示例：套餐 1,920 + 加购 1,000，应扣 2,160 → 套餐扣 1,920、加购扣 240，剩加购 760。
- 提交时冻结，开始制作时扣减；冻结中的积分不能用于其他订购。
- 可用积分 = 套餐可用 + 加购可用（不含冻结）；原型流水的“可用余额”在冻结时即减少，扣减时不再变化。

易错点【推断】：
1. 冻结单要记录“从哪些批次各冻结多少”，否则无法实现 3.4 的退回规则与清零规则。
2. 冻结 / 扣减 / 释放 / 清零 / 发放并发时要串行化到账户（行锁或乐观锁重试），所有写操作幂等（业务单号 + 动作作幂等键）。
3. 原型把“套餐过期时加购积分冻结”也记成“冻结”流水（PF03 说明）。它与“业务冻结”语义不同（前者是整体挂起、续费恢复），建议实现为账户级“挂起”状态而不是冻结单，展示上再合并。
4. 套餐积分在同一订阅周期内到期时间相同，“快到期先用”主要在升级补发、调整入账、退回入账等多批次并存时起作用；仍建议按批次建模。

### 3.3 按月发放、周期与清零【PRD §2.2-2/3、§2.3-4】

- 应付金额 = 月费 × 月数（季付 / 年付是否另有优惠待定）。
- 每月按“开通日”发放当月套餐积分；季付 / 年付同样按月发放；周期内累计有效，**周期结束时统一清零**。
- 清零时点：到期日 24:00。
- 原型周期示例：月付 09-13 至 10-12；季付 09-20 至 12-19、07-04 至 10-03；08-30 至 09-29。即 `周期止 = 起始日 + N 个月 − 1 天`。
- 月付连续续费的商家每月都清零（原型：“09-12 24:00 上期清零 −390”紧接“09-13 00:00 发放本期”）。
- 首期发放时间 = 开通时刻；后续月份与续费周期的发放时间 = 当日 00:00（原型流水）。

易错点（需业务确认，见第 10 节 Q-2）：
1. **29 / 30 / 31 日开通**：PRD 未定义短月规则。建议【推断】保存“锚定日”，每月发放日 = min(锚定日, 当月最后一天)，避免从 31 日漂移到 28 日后永久停在 28 日；周期止日同理按锚定日计算。
2. **“24:00”**：实现为“次日 00:00（Asia/Shanghai）”的开区间上界；清零任务与新周期发放任务必须有确定顺序（先清零旧周期批次，再发放新周期），且各自幂等。
3. **时区**：全部按北京时间计算业务日；数据库与服务统一时区存储（建议 UTC 存储 + 业务层按 +08:00 取日），定时任务不得依赖服务器本地时区。
4. 对公转账开通：周期起点 = 财务确认到账时刻，不是创建付款单或转账时间（原型 admin/Receipts）。
5. 已过期后续费：新周期自续费当日起算（原型）；未过期续费：自本期结束次日起算，需要支持“已支付但未生效”的排队周期，以及多次提前续费的串联。
6. 发放任务错过（宕机）必须可补偿：按“应发未发”扫描，而不是只靠定时点触发。

### 3.4 冻结跨周期与退回【PRD §2.3-2/3、§2.8】

- 冻结跨过套餐期末的积分，按提交时间视为已使用，不清零。
- 开始制作前取消、资质不通过且无法补正、平台原因无法交付：冻结或已扣积分**全额退回**。
- 退回时，原周期已结束的套餐积分**按加购积分退回**（长期有效）；原周期未结束的退回套餐积分（随本期清零，原型 admin/Refunds：“退回的 2,430 积分并入本期套餐积分，随本期 10-17 24:00 清零”）。
- 套餐已过期时退回的加购积分应处于挂起状态【推断】。

分阶段规则：

| 阶段 | 规则 | 出处 |
|---|---|---|
| 开始制作前 | 冻结全额退回 | §2.8 |
| 制作中 · 方案确认阶段 | 扣除 10%（原型默认，可配） | 原型 admin/Params |
| 制作中 · 广告准备与样片制作 | 扣除 30% | 同上 |
| 制作中 · 样片待确认 | 扣除 50% | 同上 |
| 样片已确认 ～ 上线前（批量合成 / 成片交付 / 待上线） | **PRD 与原型均未规定** | 见 Q-5 |
| 已上线 | 不退；因平台原因无法继续上线的，按剩余使用期折算退回 | §2.8 |
| 平台原因无法交付 | 全额退回 | §2.3-3 |

- 扣除比例须随阶段递增（原型校验）；扣除额 = `round(已扣 × 比例)`；按每部剧所处阶段分别核算。
- 套餐退款：开通 7 天内且未使用积分（含冻结）→ 全额退款；其他不退；加购积分任何情形不退现金。

易错点 / 漏洞【推断】：
1. **清零套利**：临到期把套餐积分冻结（下单），到期后取消，按规则“原周期已结束 → 按加购积分退回”，即把将清零的套餐积分转成长期有效的加购积分。需要业务补规则（例如商家主动取消的退回仍按原批次属性处理，或只对平台原因适用）。
2. 部分退回时，“扣除部分”落在哪个批次（套餐还是加购）未定义，影响退回后的余额结构与财务口径。
3. “按剩余使用期折算”的公式未给出（按天？分母是否为上线首日至授权期结束？）。
4. “7 天内”的起算（支付时刻起 168 小时，还是自然日）与适用范围（仅首次开通，还是续费 / 升级也适用）未定义；退款时同周期内已购的加购积分如何处理未定义。

### 3.5 升级与降级【PRD §2.2-5/6，示例 7；原型 admin/Plans、merchant/PlanPick】

```
补交金额 = (新月费 − 旧月费) × 本月剩余天数 ÷ 30
补发积分 = (新每月积分 − 旧每月积分) × 本月剩余天数 ÷ 30
示例：剩 12 天，专业 → 旗舰：补 2,400 元、补发 3,120 积分；剩 20 天，基础 → 专业：补 2,000 元、补发 2,400 积分
```

- 升级立即生效；到期日不变；折扣立即按新版本；补发积分并入当期套餐积分，期末一并清零；“此后按新版本收费和发放积分”。
- 降级：当前周期结束后生效，本期权益不变；新版本门店数 / 成员数低于现有数量的，须在生效前移除超出部分。原型把降级实现为“选择低版本 + 周期并付款，下个周期生效”。

易错点【推断】：
1. “剩余天数”口径：原型两例均为 `到期日 − 当天`（不含当天），一律按 30 天计；31 天的月份首日升级时剩余 30 天。需固定取整规则（金额到分，积分取整方式 PRD 未写）。
2. **季付 / 年付升级**：规则只说“按本月剩余天数补差”，没有说明已预付的后续月份是否补差价、后续月份按哪个版本发放。这是计费歧义（Q-3）。
3. 已提前续费（排队周期为旧版本）后再升级，排队周期如何处理未定义。
4. 升级前已冻结的订购按原折扣（冻结时已定价）。
5. 降级生效时若门店 / 成员仍超限，系统行为未定义（阻止生效？自动停用？）。

### 3.6 成片使用期与可订范围【PRD §2.4-7、§2.5】

- 使用期 = 上线首日 至 剧目授权期结束日；订购时展示“可使用至”。
- 版权续期 → 已上线成片使用期**自动顺延**，商家无须操作；授权书期限同步顺延。
- 逾期上线不顺延截止日。
- 剩余授权期 ≥ 最短可订授权期（默认 3 个月）才可展示与订购，不足时自动停止订购。
- 期望上线日最早为订购后第 7 个工作日【§6.8】。

易错点【推断】：
1. 使用期止日不要复制到订购明细后就不再更新；应引用短剧版权止日，或在版权续期时批量重算，并重排下架任务与 30 / 7 / 1 天提醒。
2. “上线首日”取商家回填并经核验的实际上线日期；双平台时取哪个账号的日期未定义。
3. 最短可订授权期 3 个月意味着使用期可能只有约 2 个多月；若使用期不足 30 天，下架任务应在上线时立即生成。
4. “剩余授权期”的月份比较要定义按自然月还是按天（如 90 天）；原型 admin/Pricing 文案写“90 天内到期”。

### 3.7 订购与配额校验【PRD §2.4、§6.8、§2.2-1、§6.16】

- 订购条件：套餐生效中、可用积分 ≥ ΣS、下单门店建档必填项齐全；新增门店须资质已通过；首店可与资质审核并行。
- 发布账号：每个平台最多 1 个，须为下单门店绑定且“可用”的账号；可同时选抖音和视频号，不加积分。
- 广告：片头、片尾各 1 条已确认广告；没有也可先订购，方案确认时再选定。
- 同一门店可多次订购同一部剧，每次都是新的定制（不能做“已购去重”）。
- 选剧单最多 50 部；商城分页 20 条。
- 门店数 / 成员数按主体合计受版本限制；成员不含老板；待接受邀请占名额；店员跨多店按人计数【推断】。
- 行业白名单：医疗、医美、药品等行业 V1.0 不开放，由字典控制。

### 3.8 工作日、工作时间与发送时段

- “N 个工作日”只计算工作时间，节假日顺延；放假安排按国务院通知导入，调休上班日按工作日计【原型 admin/SysParams】。原型示例：09-30 08:15 回填的核验任务，截止为 10-08 08:15（跨国庆）。
- “2 小时内（工作时间）”“30 分钟响应（工作时间内）”需要工作时间段内的时长累加算法。
- 订阅消息 / 短信发送时段 08:00–21:00，超出顺延至次日 08:00；验证码类不受限【原型 admin/OpsTemplates】。
- 参数修改后“之后产生的工单与提醒按新参数执行”→ 截止时间应在任务创建时固化。

### 3.9 财务口径【PRD §7.9-1、§7.10、§12.1】

- 已售未用积分按预收款（积分负债）管理；订购与广告消耗、套餐积分清零时确认收入。
- 【推断】三个版本“每元对应的积分数”不同（3,000 元 → 3,000；6,000 元 → 6,600；12,000 元 → 14,400），加购积分为 1 元 / 积分；若财务要按消耗确认收入，每个积分批次需要记录来源付款与单位对价，这是采用批次模型的另一个理由。

### 5.4 技术含义【推断】

- 微信订阅消息通常是“一次性订阅”，每次用户授权只能下发一条；而 PRD 有多条定时提醒（7 / 3 / 1 天等）。需要在关键操作点引导累积授权，并把“订阅失败 → 短信补发”做成通用能力，重要节点不能只依赖订阅消息。
- 需要统一的通知中心：模板、渠道路由、静默时段、失败补发、发送记录与成功率统计（原型 admin/OpsTemplates 展示“近 7 天发送 / 成功率”）。

### 8.2 第 9 章对数据架构的要求

1. **埋点管道**：26 个事件 + 8 个公共属性；其中 `asset_adopted`、`points_expire` 标注为“系统”事件，由服务端产生。需要统一的事件表 / 事件流，客户端与服务端事件同构。【§9.3】
2. **漏斗混合数据源**：访问 → 登录 → 详情 → 建档 → 开通 → 首单 → 成片交付 → 上线核验 → 续费；其中“成片交付”“上线核验通过”取后台状态数据，其余取埋点。【§9.2】→ 业务状态变更必须留时间戳历史（状态流水表），不能只存当前状态。
3. **时长类指标**：成片交付时长 = 开始制作到成片交付的**工作日数中位数**（原型：自积分扣减起算，不计资质未通过期间）；按时上线率；样片一次通过率 → 需要每步进入 / 完成时间、样片轮次、约定上线日与实际上线日，以及工作日历函数。【§9.1、§12.3-5】
4. **期初 / 时点类指标**：积分消耗率分母含“月初可用积分”；积分负债为时点值；升级率分母为“月初低版本生效主体数”；MRR 需按月分摊季付 / 年付 → 需要**每日 / 每月快照**（账户余额、订阅状态）或可按时点回放的流水。【§9.1、§7.10】
5. **队列类指标**：续费率 = 当月到期套餐中到期后 7 天内续费的比例 → 按到期月分组，T+7 才能出数。【§9.1】
6. **维度**：所有事实需带主体、门店、城市、品类、套餐版本、交付经理、来源渠道；V2.0 要“按门店对比效果”。
7. **口径未定**：报表指标口径是待确认项【§12.3-5】→ 报表层应与明细层解耦，口径可改而不必改业务表。
8. 【推断】V1.0 数据量小，业务库只读副本 + 汇总表 + 定时任务即可满足 V1.0 两张报表（经营概览、积分报表）与工作台今日数据；不必一开始引入独立数仓，但事件明细应按可迁移的方式存储。

| 订购取消 / 套餐退款 | 客服 | 财务 | 财务（审批与执行两步各自二次确认） |
| 积分手动调整 | 客服 / 交付经理（商家详情中） | 财务 | 系统入账 |
| 套餐有效期补偿延长 | 交付经理 | 交付主管（积分入账另经财务，原型设计，待确认 §12.3-4） | 系统 |
| 对公收款确认 | — | 财务 | 系统生效 |
| 对账差异处理（补单 / 原路退款） | 财务 | — | 财务，须填说明 |
| 付款单改价（V1.1） | 客服 | 主管 | — |
| 商家归属变更（V1.1） | — | 渠道运营 | — |

技术含义【推断】：
1. “菜单 + 按钮 + 数据范围”三级需在后端统一实现（接口权限码 + 数据范围过滤器），不能只做前端菜单控制。
2. “本人任务”是行级权限：任务表需要责任人字段（交付经理 / 剪辑师 / 发布专员）。
3. 数据范围按“本人负责的商家”过滤，转移交付经理时在办工单随之移交、已归档保留原负责人 → 责任人要落在工单上，而不是仅通过商家关联推导。
4. 矩阵与流程存在不完全对齐之处（如交付经理对“订单管理”只有查看，但原型的“套餐到期”续费跟进与补偿延长挂在订单菜单下），说明按钮权限要能独立于菜单级别授予。
5. 审批流建议抽象为统一的“申请单 + 审批节点”模型，V1.1 的改价与归属变更可直接复用。
6. 资质审核由哪个岗位负责 PRD 未明写（原型工作台把“待审核商家”归到客服视角）。

### 10.4 技术风险（资料中未明说，需要架构关注）

| 编号 | 风险 | 说明 |
|---|---|---|
| R-1 | 订阅消息可靠性 | 定时类提醒依赖用户事先授权，授权次数有限；必须有短信兜底与授权引导【推断，需按微信现行规则核实】 |

| R-3 | 支付回调与超时取消竞态 | PRD 已承认该场景并用对账兜底（§7.9-5）；实现上应在取消前主动查单，把差异降到最低 |
| R-4 | GB 级成片包在小程序内下载 | 单部剧 2–5 GB、数十到上百个文件；小程序下载接口对单文件大小与保存相册有平台限制，“打包下载”很可能需要改为“按集下载 + 复制链接到电脑端下载”等方案【推断，需核实平台限制并与产品确认】 |
| R-5 | 大文件上传 | 500MB 视频在小程序内上传需要直传 + 分片 + 断点续传，实现复杂度高于普通上传 |
| R-6 | 工作日 SLA | 依赖每年人工导入的放假安排；漏导会导致全站时效计算错误，需要缺失告警 |
| R-7 | 版权续期联动 | 版权止日变更会联动使用期、授权书、下架任务、提醒、可订状态，需要事件化处理 |
| R-8 | 小程序类目与支付合规 | 小程序内播放短剧预告片 / 样片、销售“套餐 + 积分”，可能涉及视听类目资质与虚拟支付政策【推断，需在立项前核实】 |
| R-9 | 审计与职责分离 | 财务“审批 + 执行”、超管“全部敏感操作”集中在少数账号；日志需防篡改 |
| R-10 | 多门店数据隔离 | 店员跨店、切换门店、主体共用积分；接口层若隔离不严会泄露金额 / 积分给店员 |

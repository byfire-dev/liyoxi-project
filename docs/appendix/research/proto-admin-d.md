## 1. Payments — 财务 · 收款流水

### 1.1 用途与 PRD 对应
- 套餐（开通/续费/升级）与加购积分的**收款记录**流水，可与微信支付账单核对；对公转账以财务确认到账为准（Payments.txt:42-43）。对应 PRD §7.9-1。只读页面，没有写操作。

### 1.2 展示数据
**KPI 卡（Payments.txt:45-50，统计值见 :126）**
| 指标 | 示例 | 备注 |
|---|---|---|
| 今日收款 | ¥10,000.00 · 4 笔 · 均为微信支付 | |
| 本月收款 | ¥789,800.00 · 207 笔 · 其中对公转账 3 笔 | |
| 本月退款 | ¥3,000.00 · 1 笔 · 套餐退款，已原路退回 | |
| 对账差异 | 1 笔 · 09-29 · ¥1,000.00 待处理 | 整卡为链接，跳转对账页 |

**表格列（Payments.txt:58-73）→ 实体 PaymentRecord（收款记录）**
| 列 | 字段（推断） | 示例/格式 |
|---|---|---|
| 收款时间 | paid_at | `09-30 10:02`；对公转账为财务确认到账时间（如付款单 FK2026092700006 的收款时间是 09-29 16:30） |
| 交易单号 / 银行流水号 | channel_txn_no | 微信支付 28 位数字 `4200002231202609300469120518`；对公转账 16 位 `2026092810152268`；带“复制”按钮 |
| 付款单号 | payment_order_no | `FK` + yyyymmdd + 5 位序号，如 `FK2026093000006` |
| 商家 | merchant（门店名）+ 标签 | 标签示例“已退款” |
| 付款类型 | kind | 开通 / 续费 / 升级 / 加购积分 |
| 收款方式 | pay_method | 微信支付 / 对公转账 |
| 金额 | amount | `¥` + 千分位 + 2 位小数 |
| 对账状态 | recon_status | 已对平 / 待对账（当天的记录为“待对账”，Payments.txt:118） |
| 操作 | — | 链接“付款单”跳 Orders |

表尾：`共 N 条 · 合计 ¥X · 每页 10 条`，`‹ 1 / P 页 ›`（Payments.txt:76-77）。空态文案“没有符合条件的收款记录”。

### 1.3 操作、交互与推断接口
| 操作 | 交互 | 推断接口 |
|---|---|---|

| 跳转 | 行 → 付款单；差异卡 → 对账 | 路由 |

### 1.4 前端能力
服务端筛选/分页表格、汇总行、导出 Excel、复制到剪贴板、KPI 卡、Toast、状态标签（Tag）。仅“财务、超管”可见（菜单级权限）。

### 1.5 原型有、PRD 没写或不一致
- 【明】每条收款带**对账状态**（已对平/待对账）——PRD §7.9-1 只说“可与微信支付账单核对”，未要求行级状态。【推】还应有“有差异”一态（Reconcile 才出现）。
- 【明】对公转账要记录**银行流水号**并可检索（PRD 未列字段）。
- 【明】时间筛选只有 3 个预设项；PRD §7 要求“所有列表支持筛选、分页和导出”，【推】实际需要自定义日期区间。
- 【明】“已退款”作为收款行上的标签，而不是把收款记录改状态（退款单列、不冲减，和 RptOverview 的口径一致）。
- 【明】升级补差是独立付款类型“升级”（示例 ¥2,000.00）。

## 2. Refunds — 财务 · 退款管理

### 2.1 用途与 PRD 对应
- 统一处理两类申请：**套餐退款（现金，原路退回）**与**订购取消（按阶段退回积分）**；“财务先审批、再执行，两步均须二次确认”（Refunds.txt:42-43）。对应 PRD §7.9-2、§2.8、§7.5-4、§3.3-2/3、§12.2 第 17 项；canvas readme 第 7 条明确“由客服发起，统一在‘财务 › 退款管理’审批与执行”。

### 2.2 展示数据
**KPI（:44-49）**：本月已退款（金额/笔数）、本月退回积分（积分/笔数）、审批与执行中（笔）、本月驳回（笔）。

**队列卡片（:56-64）**：商家、金额或积分、申请单号 · 关联单号、时间说明（申请于/审批通过于/驳回于/退款于/退回于）、标签（全额退款 / 部分退款 / 全额退回积分 / 按阶段退回积分 / 已驳回，:295）。

**详情 → 实体 RefundRequest（退款/退回申请）**（:157-196 示例数据）
| 字段 | 说明 / 示例 |
|---|---|

| kind | `cash` 套餐退款（原路退回）/ `pts` 订购取消（退回积分）（:155） |
| order | 关联单：付款单 `FK…` 或订购单 `LYX…` |

| 操作 | 交互细节 | 推断接口 |
|---|---|---|
| 切换视图 | Tab：待审批 / 待执行 / 已处理（已处理含已退款与已驳回），带计数（:270-282） | `GET /admin/finance/refunds?view=todo|exec|done` 读；`GET …/refunds/summary` 读 |

### 2.4 前端能力
主从分栏（队列 + 详情）、Tab 计数、描述列表、时间线、确认弹层（带强制勾选）、驳回弹层（单选 + 文本域校验）、状态标签、菜单角标联动（待审批 + 待执行，:260, :268）。按钮级权限：审批、执行、驳回（财务/超管）。

### 2.5 原型有、PRD 没写或不一致
1. 【明】**订购单状态**：执行后变为“已退回积分”，审批期间为“售后处理中 / 取消审批中”（Refunds.txt:164, :313；Orders.txt:109-110, :124）。PRD §5.3 文字只说“开始制作前取消……订单进入‘已取消’”。原型把“开始制作前取消”的 TK20260917001 也落到“已退回积分”（:184）——**“已取消”与“已退回积分”的边界需明确**。
2. 【明】**交付工单在审批期间“暂停”**、执行后“关闭”、驳回后恢复（:160, :164, :131）——PRD 未写工单暂停态。
3. 【明】**扣除比例示例值 10%**（方案确认阶段，270/2,700，:159-160）；PRD §2.8 只说“扣除比例由运营后台配置”，Params 画板分 3 档（方案确认阶段 / 广告准备与样片制作 / 样片待确认，Params.txt:101-105）且要求“随交付阶段递增”。
4. 【明】**退回去向**：退回“套餐积分”并“并入本期套餐积分，随本期于 10-17 24:00 清零”（:161-163）；PRD §2.3-3 另规定“原周期已结束的套餐积分按加购积分退回”。→ 退回必须**回到原扣减批次（来源）**，过期批次改入加购积分。
5. 【明】**套餐退款的副作用**：“套餐关闭，已发放的 3,000 套餐积分作废”（:192）。PRD §2.8 未写积分作废动作。
6. 【明】**开始制作前的取消也走财务审批**（TK20260917001，:178-186）；PRD §2.8 表述为“冻结的积分全额退回”，未强调审批；§7.5-4 说“客服发起、财务审批”。【推】若商家端允许自助取消，需决定是否绕过审批。
7. 【明】驳回原因枚举 4 项、说明上限 200 字——PRD 未列。
8. 【明】示例里审批人与执行人是同一人（方琳；演示里周航），**没有职责分离**约束。
9. 【缺】PRD §7.9-2 要求的“**线下退款须登记转账信息**”（对公转账付款的退款）在原型中没有对应表单；“**红字发票**”只有提示文案，没有红冲操作与状态；“部分退款”只有标签逻辑（:295）无样例；“已上线按剩余使用期折算退回”无样例。
10. 【明】微信支付退款单号需要落库并展示（:194）。

## 3. CreditAdjust — 财务 · 积分调整审批

### 3.1 用途与 PRD 对应
- 审批“在商家详情中发起的积分手动调整”；通过后计入积分流水并通知商家，驳回须注明原因（CreditAdjust.txt:42-43）。对应 PRD §7.9-3、§2.3-6、§7.4-5、§3.3-3。

### 3.2 展示数据
**KPI（:44-48）**：待审批（单）、本月通过（单数 · 增加 X 积分、扣减 Y 积分）、本月驳回（单）。

**表格列（:56-71）→ 实体 CreditAdjustment（积分调整单）**
| 列 | 字段 | 示例 |
|---|---|---|
| 调整单号 | no / applied_at | `TZ20260930002` · 申请于 09-30 10:15 |

| 调整 | delta（带符号）/ account_type | `+270` 套餐积分；`−1,000` 加购积分 |

## B. 状态机

**B1 退款/退回申请 RefundRequest**（Refunds.txt:207, :322-351）
```
(客服在订单详情发起) → pending 待审批
pending --审批通过[强制勾选]--> exec 待执行
pending --驳回[原因+说明]--> rejected 已驳回   （关联单恢复原状态、工单恢复）
exec --执行[强制勾选]--> done 已退款(现金) / 已退回(积分)
【推】exec → executing(微信退款处理中) → done | failed(可重试)
```
联动：发起时 订购单→“售后处理中/取消审批中”、交付工单“暂停”；done(积分) 订购单→“已退回积分”、交付工单关闭、积分流水+退回；done(现金) 付款单→“已退款”、套餐关闭、已发套餐积分作废。

**B2 积分调整单**：pending 待审批 → passed 已通过（入流水、通知商家）｜ rejected 已驳回（通知申请人）。同一商家在审期间不可重复发起（MerchantDetail.txt:738）。

**B3 开票申请**：todo 待开票 → done（电子：已开具；纸质：已寄出）｜ rejected 已驳回（商家可重新申请 → 新申请单）。【缺】已开具 → 已红冲。

**B4 日对账**：wait 待对账（账单未下载）→ ok 已对平 ｜ diff 有差异 → fixed 已处理差异。差异项：open → resolved(restore 补单 | refund 原路退款)。

**B5 收款记录对账状态**：待对账 → 已对平 ｜（有差异 → 已处理）。

**B6 付款单**（Orders.txt:82）：待支付 →（微信支付成功）已支付 ｜（30 分钟超时）已取消 ｜（对公）待确认收款 → 已支付 / 驳回；已支付 →（退款执行成功）已退款；**已取消 →（对账补单）已支付**（原型新增的逆向流转）。

**B7 订购单**（Orders.txt:109-110, :159）：待开工 → 制作中 → 待上线 → 上线中 → 已结束；另有 已取消、售后处理中、已退回积分（共 8 态）。本组画板触发的流转：售后处理中 → 已退回积分（执行）｜ 恢复原状态（驳回）。

**B8 服务商结算单**（FinSettle.txt:101-125）：（每月 3 日生成并推送）待服务商确认 → topay 待打款 → paid 已打款；待确认 → dispute 有异议 →（渠道运营核查后）topay。

**B9 服务商等级**：每月 1 日 00:00 系统按上月名下实付评定（PartnerLevels.txt:104-107）。

## G. 技术风险

1. 积分账本若不按“批次 + 单价 + 追加流水”建模，后续无法出具“按来源/折合预收款/收入确认”口径的积分报表，财税风险高。
2. 微信支付回调迟到与付款单超时取消的竞态是原型明示的真实场景；若回调处理把“已取消”订单的成功支付直接丢弃，会产生无主收款。
3. 微信退款是异步且可能失败（余额不足、超期等【外】），原型的“执行即成功”需要补“处理中/失败/重试”状态，否则账实不符。
4. 对账只演示了一种差异类型；金额不一致、平台有账单无、退款差异、跨日（23:59 支付、次日入账）等边界未设计。
5. 差异“原路退款”绕过审批流，与“退款须审批”的敏感操作规则冲突，存在内控漏洞。
6. 红字发票与线下退款无界面，已开票付款单的退款链路不完整；对公转账付款的套餐退款无法在系统内闭环。
7. 报表口径尚未确认（PRD §12.3-5）；“当月实时 + 历史结转”的双口径若不做月度快照，历史数字会因补单、退款、调整而漂移。
8. 热度等级、服务商等级、返佣比例、套餐单价都要求“按发生时的值”统计，必须在业务单据上做快照，否则调价/升降级后报表与结算单对不上。
9. 工作日/工作时间计算依赖日历维护；缺失会直接影响交付时长、SLA、首版按时率等多个指标。
10. 发票、回单、税号、银行账号属敏感数据，需加密存储与签名访问；OFD 文件无法在浏览器直接预览。
11. 财务写操作的幂等与并发（双击、重复提交、两名财务同时审批同一单）必须由后端状态机 + 乐观锁/唯一约束保证，原型仅靠前端按钮禁用。
12. 报表数据范围规则未定；若渠道运营、交付经理看到全量经营数据，会与 PRD §3.3 的数据范围原则冲突。

## H. 需要业务或架构师拍板的问题

1. “已取消”与“已退回积分”如何区分？开始制作前的取消是否必须经财务审批（商家端能否自助取消）？
2. 对账差异选择“原路退款”时，是否生成退款申请单并走“审批 → 执行”两步？是否计入退款统计？
3. 积分调整的审批层级：仅财务，还是“交付主管 → 财务”两级？延长套餐有效期的补偿由谁审批？
4. 退款/调整是否要求“申请人、审批人、执行人”职责分离？
5. 积分退回的归属与单价：回原批次（原版本单价）还是按加购积分（1 元）？过期批次的退回在积分报表里计入哪个来源？手动调整在流转恒等式里归哪一项？
6. 收入确认的精确规则：消耗与清零按批次折算单价确认？升级补发、赠送类积分单价如何取？是否需要系统出具收入确认明细（凭证级）？
7. 开票项目名称（信息技术服务费 vs 会员服务费/积分充值）与开票时点；是否支持合并/拆分开票；红字发票流程与界面。
8. 线下退款（对公转账付款）登记流程与界面是否纳入 V1.0。
9. 付款单未支付超时时长是否确定为 30 分钟；超时前是否主动关单。
10. 服务商等级门槛以哪一版为准（8 万/3 万 还是 4 万/1.5 万）；“名下实付”是否扣除退款；降级规则；结算单由系统还是渠道运营生成。
11. 报表口径最终版（续费率、升级率、加购率是否展示；交付时长的起止与剔除项；中位数还是平均数；工作日历来源）。
12. 报表的数据范围：客服、交付经理、渠道运营看全量还是仅本人/本组？V1.1 的 5 张报表菜单在 V1.0 是否隐藏？
13. 报表是否都需要月份切换、是否需要自定义区间/按周/按日；历史月是否冻结（月结转）以及冻结后发生的退款、补单如何体现。
14. 纸质发票是否需要对接快递轨迹查询，还是仅展示快递公司与运单号。
15. 导出是否需要审批或水印/留痕（财务明细、按主体积分余额属于敏感数据）。
16. 电子发票是否需要在后台/小程序内预览（PDF 可、OFD 需额外组件），以及邮件发送采用附件还是带签名的下载链接。

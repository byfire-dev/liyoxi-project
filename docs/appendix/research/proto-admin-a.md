### 1.5 原型有、PRD 没写或不一致

1. **待办视角切换**：超级管理员可切到某岗位视角；PRD 7.1 只写“按角色展示”。视角列表没有内容运营、渠道运营（`Main.txt:181`）。
2. **待办归属岗位**【明确，来自脚本】：待审核商家→客服；待确认收款、退款审批→财务；待分配工单、套餐即将到期→交付经理；待制作广告→剪辑师；待交付成片、待核验上线、待核查下架→发布专员；待处理工单→客服（`Main.txt:182`）。PRD 未写资质审核、套餐到期跟进由谁负责，也写的是“交付主管”分配工单（PRD 5.2 步骤 1）。
3. **今日数据口径不同**：PRD 7.1 列“新增商家、新开通与续费套餐、收款额、积分消耗、新增订购、上线中剧目数”；原型没有“新开通与续费套餐数”“上线中剧目数”，多了“套餐生效商家 186 / 7 天内到期 19 / 已过期未续费 6”，积分口径写作“扣减与冻结”。
4. 待办名称：原型“退款审批”，PRD“退款申请”。
5. PRD 7.1 没有的区块：近 7 日上线安排、实时动态、菜单角标、全局搜索、通知铃铛。
6. 版权到期预警示例：“12-25 结束，09-25 起已停止订购”（`Main.txt:146-147`），与“最短可订授权期 3 个月”一致；PRD 7.2 另写“到期前 90 天提醒”。
7. “数据更新于 10:30”说明今日数据是定时快照而非强实时【推断】。

### 2.4 前端能力
复杂表格（状态页签带计数、多条件筛选、服务端分页、按筛选导出、行高亮、按状态变化的行操作）；模态表单（单选卡片 + 文本域）；数据范围权限（交付经理默认只看本人，主管看本组，见 PRD 3.3）；“分配”按钮属按钮级权限（仅主管 / 超管）。

### 2.5 原型有、PRD 没写或不一致

1. **状态命名**：原型用“服务中”，PRD 5.2 步骤 10 写“使用中”；PRD 7.4(4) 又用“在办工单（含服务中）”。需统一枚举。
2. 筛选项：PRD 7.6 未列筛选条件；原型为交付经理、制作模型、发布账号平台、仅看超时与逾期。
3. 分配规则细化：按城市轮询推荐、展示各人在办量、“分配后交付经理须在 1 个工作日内完成方案确认”（`Tickets.txt:83`）。轮询的示例实现是 3 人循环（`Tickets.txt:111-112`）。
4. 已有专属交付经理的商家，工单生成时直接分配（`TicketDetail.txt:203` 日志“生成工单，分配给专属交付经理林晓”）；只有新商家进入“待分配”【推断】。
5. 待分配截止 = 工单生成后 2 小时（09:12 生成 → 11:12 截止），与 PRD 5.2 一致；待上线截止 = 约定上线日 23:59（`Tickets.txt:144`）。
6. 规模：服务中 1,392 张（140 页），处理中约 36 张（示例数据）。
7. **节假日口径在原型示例数据里不一致**：上线核验截止“10-08 08:15”（09-30 08:15 回填 + 1 个工作日，跳过国庆假期，`Tickets.txt:131`），账号核验同样顺延到 10-08（`Accounts.txt:131`）；但同为“1 个工作日”的方案确认截止却是“10-01 08:31”（`Tickets.txt:132`），样片制作、批量合成的截止落在 10-01、10-02（`Tickets.txt:138-148`），广告首版“09-30 09:18 提交 → 10-02 09:18 截止”（`AdTasks.txt:114`）也未顺延。`SysParams.txt:46` 写明“以‘个工作日’计的时效只计算工作时间，节假日顺延”，应以此为准；样片确认的“超过 2 天未处理自动提醒”按自然日计（`TicketDetail.txt:224`）。
8. 原型没有工单“已取消/已终止”状态；订购在制作中被取消或退款时工单如何结束，原型与 PRD 5.2 都没给出。

4. “使用期已结束，提醒商家当日完成下架”出现在结束次日（09-29）（`Offline.txt:142`）；PRD 要求到期当日完成下架。
5. 示例数据使用期 2026-08-07 至 2026-09-28（不足 2 个月），与“剩余授权期不少于 3 个月才能订购”矛盾；数据键名仍叫 `grace`（旧稿“宽限期”遗留）。属示例数据瑕疵，不应据此设计。
6. **同一部剧的全部成片在同一天到期**（示例 5 个任务都是《旧时光照相馆》09-28 到期）：一部热门剧授权期结束时，下架任务会集中爆发，而原型只有逐条处理，没有批量操作。

### 13.2 状态机

**(1) 交付工单**（PRD 5.2 + Tickets.txt:167 + TicketDetail.txt:168）

| 状态 | 进入触发 | 离开触发 | 截止规则 |
| --- | --- | --- | --- |
| 待分配 | 订购成功且资质通过，系统生成工单并扣减积分；商家已有专属交付经理时跳过本状态【推断】 | 主管确认分配 | 生成后 2 小时（工作时间） |
| 方案确认 | 分配完成 | 交付经理推送方案且商家在小程序确认 | 1 个工作日 |
| 广告准备 | 方案已确认 | 方案所用广告全部“已确认”（复用则系统自动完成） | 新制作 2 个工作日 |
| 样片制作 | 广告就绪；或样片被退回（商家提出、交付经理代录、质检不通过） | 剪辑师上传样片且质检通过并推送 | 1 个工作日 |
| 样片确认 | 样片推送商家 | 商家确认 → 批量合成；提出修改 → 样片制作 | 超过 2 天未处理自动提醒 |
| 批量合成 | 样片确认 | 全部剧集上传且逐集质检通过 | 2 个工作日 |
| 成片交付 | 成片质检通过 | 发布专员推送成片包与清单 | 质检通过当日（原型：18:00） |
| 待上线 | 推送成片包，生成上线任务 | 商家回填链接 | 约定上线日 23:59；次日起算逾期 |
| 上线核验 | 商家回填链接，生成核验任务 | 通过 → 服务中；需补充 → 等商家重新回填（状态归属待定） | 回填后 1 个工作日 |
| 服务中（PRD：使用中） | 核验通过，使用期起算 | 使用期结束 | 使用期至剧目授权期结束 |
| 到期下架 | 使用期结束（下架任务在结束前 30 天已生成） | 下架核查通过 | 1 个工作日 |
| 已归档 | 下架核查通过 | — | — |

缺口：没有“取消/终止”分支（制作中取消、平台原因无法交付、退款）。

**(2) 订购单**（PRD 5.3 + Orders.txt:109-110,159）：待开工、制作中、待上线、上线中、已结束、已取消、售后处理中、已退回积分。工单→订单的联动点：生成工单 → 制作中；推送成片 → 待上线；核验通过 → 上线中；下架核查通过 → 已结束。一张订单含多部剧时的聚合规则未定义。

**(3) 广告任务**：待指派 →（指派，冻结转扣减）→ 制作中 →（上传并推送）→ 待商家确认 →（确认）→ 已确认；待商家确认 →（提出修改）→ 修改中 →（上传并推送）→ 待商家确认；已确认 →（再次提出修改）→ 修改中。商家端映射：待指派、制作中 → “制作中”。

**(4) 渠道账号**：待核验 →（通过）→ 可用；待核验 →（标记异常）→ 异常 →（商家重新提交）→ 待核验；可用 →（解绑，且无交付中或上线中订单）→ 已解绑。

**(5) 链接核验任务**：待核验 → 核验通过 / 已退回补充（商家重新回填则新建任务）。

**(6) 巡检任务**：待巡检 → 正常；待巡检 → 异常 →（复查已恢复）→ 正常；异常期间可再次提醒。

**(7) 下架任务**：已生成（T-30）→ 待商家下架 → 商家已确认（待核查）→ 已核查；到期未确认或抽查仍在线 → 逾期未下架（升级主管 → 违约提醒）→ 已核查。

**(8) 数据提交（V1.1）**：待录入 → 已录入 / 已驳回（重新上传为新提交）。

**定时触发点汇总**（都需要调度器）：工单分配 2 小时超时；各环节 SLA 到期提醒与升级；样片 2 天未处理提醒；广告待确认到期提醒；约定上线日前 1 天 09:00 提醒商家；约定上线日次日提醒交付经理；使用期结束前 30、7、1 天及当日下架提醒；每周生成巡检名单；成片包链接 7 天过期；版权到期预警；工作台计数刷新。

| 下架核查 | `GET /publish/offline-tasks`、`POST …/{id}/evidences`、`POST …/{id}/pass`、`POST …/{id}/escalate`、`POST …/{id}/breach-notice` | 通过为多表事务 |
| 数据录入（V1.1） | `GET /publish/metric-submissions`、`POST …/{id}/approve`、`POST …/{id}/reject`、`GET /publish/metrics/import-template`、`POST /publish/metrics/import:validate`、`POST /publish/metrics/import:commit` | 导入带批次号 |
| 公共 | `POST /files/upload-policy`（直传凭证、分片）、`GET /files/{id}/url`（签名播放/下载）、`GET /dict/{type}`（退回/异常原因）、`GET /staff?role=`（人员下拉） | 共享服务 |

通用约束：
- 所有状态流转接口做**状态前置校验 + 乐观锁（版本号）**，避免两人同时处理同一任务。
- 与积分相关的流转（生成工单扣减、广告指派扣减、超次修改扣减、取消退回）必须与状态变更在**同一数据库事务**内，并带业务幂等键。
- 催办、提醒类接口做限频（如同一对象同一场景每日 1 次），并落提醒记录。
- 这 12 个画板里**没有审批流**（审批集中在财务与订单模块）；二次确认只出现在弹窗表单的“确认”按钮。
- 关键操作（分配、核验、驳回、下架核查、导入）写操作日志（PRD 7 开头、7.12(5)）。

9. **数据字典**：退回原因、异常类型等。
10. **操作日志**、**导入导出服务**（异步导出、导入批次）。
11. **仪表盘聚合**：待办计数、今日数据、预警、动态流。

### 13.7 需要拍板的问题

1. 一张订购单含多部剧时，订购单状态如何由多张工单聚合？
2. 链接核验退回后工单回到“待上线”还是停留在“上线核验”？双平台是否允许分别通过？两个平台上线日期不同，使用期从哪天起算？
3. 工单取消、退款、平台原因无法交付时的终止状态与积分退回联动如何设计？
4. 各时效哪些按工作日、哪些按自然小时或固定时刻？节假日是否一律顺延？
5. 广告“开始制作”的扣减时点：主管指派即扣，还是剪辑师点“开始”才扣？
6. 剪辑师、发布专员由谁指派，是否自动分配？
7. 成片 36～80 集由剪辑师经浏览器逐集上传，还是由内部制作/AI 流水线直接写入存储后在后台登记？（直接决定上传方案与制作系统边界）
8. 成片包下载形态：预打包整包，还是按集签名下载 + 可选打包？
9. 账号截图与数据截图的“识别”是否做 OCR？V1.0 是否纳入？
10. 巡检抽样规则（比例、随机方式、覆盖周期、粒度）；下架核查是全量还是抽查，是否需要批量处理。
11. 质检清单、核验清单、巡检清单是否做成可配置（数据字典或参数），以应对合规口径变化。
12. 员工侧通知走站内通知、企业微信还是两者都要。
13. 工作台数据的刷新频率与口径（快照还是实时查询）。
14. 队列页是否补充筛选、分页、历史查询与导出。

## 1. 可能改变产品形态的风险

### 1.1 支付可能被判定为“小程序虚拟支付”

**事实**

- 2026-04-01 起，小程序内售卖虚拟商品在全终端都必须接入小程序虚拟支付；不得引导用户到小程序外付款。iOS 走 Apple 支付，2026 年生效费率 12%（标准 17%），回款周期明显更长；非 iOS 端当前费率 1%（标准 10%，官方未写截止日期）。Apple 支付的单笔上限未核实，3.6 万至 14.4 万元能否付成未知。
- 官方判定看的是“非实物 + 线上交付”，不看付费方是企业还是个人。2026-03 官方客服已把面向企业的年付会员明确答复为虚拟支付行为。
- “会员套餐 + 积分充值”与官方举例“VIP 会员、充值代币”同形。唯一有利的官方口径是 2020 年的一条答复：“提供人工服务不属于虚拟支付内容”。
- 微信支付对付款人有限额，取决于商户号核准的行业类目。两个官方来源的数字不一致：较早的客服页写实物行业单笔与单日 8 万元、虚拟行业单笔 6,000 元与单日 9,000 元；2026-06 更新的客服页据摘要写虚拟额度单笔 5 万元、单日 50 万元（未逐字核读）。以商户平台里本商户号的核准记录为准。
- 小程序内展示对公转账入口没有官方明文许可，即使未被判为虚拟支付也只能通过提审确认。
- 没有查到官方的“事前书面认定”渠道。能得到官方答复的地方是微信开放社区的官方专区；有约束力的认定只发生在提审与上线后的平台处置。

**影响**：被判定后，小程序内不能用普通微信支付，也不能展示对公转账入口；改走虚拟支付则 iOS 端要付 12% 以上的渠道费，且大额能否付成未知。

**架构对策**：购买入口由服务端策略控制；V1.0 实现“线下签约、后台代建付款单、对公确认”的退路（[03](03-key-designs.md) 1.6）。

**进展（2026-10-02）：业务已开通微信支付商户号。** 这省掉了进件的等待，但不解决定性问题：是否属于虚拟支付，平台看的是小程序里所售内容的形态（非实物、线上交付），在提审与上线后判定，与有没有商户号无关（核实 mch-1）。官方客服对“已接了小程序支付的还需要接虚拟支付吗”的答复是：涉及虚拟商品购买的，需重新接入虚拟支付。若被判定，虚拟支付会另开一个新的二级商户号，现有商户号用不上。现有商户号真正起作用的前提，是产品被认定为非虚拟（人工定制服务）。

请在商户平台核对这几项：

| 核对项 | 在哪里看 | 为什么重要 |
| --- | --- | --- |
| 核准的行业类目与费率 | 账户中心 > 商户信息 > 结算信息（路径来自搜索摘要，以实际界面为准） | 0.6% 的“网络广告及推广”一类与人工服务的定位一致；1% 的虚拟业务类目带虚拟限额，且与“非虚拟”的主张矛盾 |
| 付款人单笔与单日限额 | 同上；或问微信支付客服 | 决定 1.2 万月付、3.6 万与 7.2 万年付能否用微信支付付成 |
| 商户号主体与小程序主体是否一致 | 商户平台的主体信息 | 一致时关联 AppID 最简单；不一致也可关联但要补材料 |
| 是否已关联其他 AppID | 产品中心 > AppID 账号管理 | 确认它是否已绑在参考工程的小程序上 |
| 验签模式 | 账户中心 > API 安全 | 较早开通的商户号默认是平台证书，须申请并手动开启微信支付公钥 |

另须在小程序侧确认是否被纳入“发货信息管理”：被纳入后，用户付款的资金默认冻结，须上报发货信息后才结算。本产品是否被纳入没有查到依据（核实 mch-5）。

**需要做的**

| 事项 | 负责 | 时点 |
| --- | --- | --- |
| 在微信开放社区的官方专区就支付定性提问，一并问“小程序内能否展示对公转账入口”；最终以试提审为准 | 业务 + 法务 | 第一周 |
| 按上表在商户平台核对商户号的类目、费率、限额、主体、关联与验签模式 | 财务 | 本周 |
| 主类目选“商业服务 > 广告/设计”；不选“企业管理”“工具”类 | 业务 | 注册时 |
| 评估把表述从“会员、充值、积分”改为突出“人工定制制作服务”，以及套餐与积分是否拆成两笔交易 | 产品 + 法务 | PRD 定稿前 |
| 决定被判定时走哪条退路：接入虚拟支付，或小程序内不售卖 | 业务 + 财务 | 提审前 |

### 1.2 小程序内播放短剧预告片与样片，可能被认定为微短剧小程序（业务已决定：V1.0 不播放）

**事实**

- 官方口径：涉及提供微短剧播出服务的小程序统一划归微短剧小程序，须申请“文娱 > 微短剧”类目；否则要求移除微短剧内容及分类标签。预告片是否算“播出服务”没有明文。
- 一旦该类目通过，账号内只能播放平台过审的链接，且须用官方短剧播放器（按流量资源包付费）、逐剧提审。自托管的预告片与样片都会播不出来。所以“被要求时再补类目”这条路走不通。微短剧属虚拟支付管控类目，小程序若只含管控类目，普通微信支付会被关闭。
- 视频类插件不支持影视剧类视频。
- 审核规范禁止多媒体自动播放，字面上不区分是否静音。

**业务决定（2026-10-02）**：V1.0 小程序内不播放短剧预告片，商城与短剧详情用海报加文字，前期已能满足需求。

**落实**：预告片播放开关默认关闭；PRD 6.5 的预告片模式与 6.6 的详情页顶部播放器不进 V1.0；样片默认不在小程序内播放（保存水印版到相册，或在电脑端下载页预览）；商家自己的广告视频不是短剧内容，仍可在小程序内预览。预告片的转码与分发不在 V1.0 的关键路径上。

**仍需注意**

| 事项 | 负责 | 时点 |
| --- | --- | --- |
| 即使不播放视频，商城页也要避免做成观看型产品的样子（“更新至第 N 集”、播放量、追剧式分类） | 产品 + 设计 | UI 设计时 |
| 试提审时确认纯图文的商城形态可以过审 | 研发 + 产品 | 试提审时 |
| 日后想在小程序内启用预告片之前，先核对当时的《微短剧小程序运营指引》并单独试提审 | 法务 + 产品 | 启用前 |

### 1.3 定制成片的差异度与许可口径互相矛盾

**事实**

- PRD 2.6 要求每份成片按门店重新制作画面、场景与植入，彼此内容不同；这是规避“同质化内容被限流”的前提。
- PRD 10.3 规定一类、二类剧默认只开放片头、片尾贴片。只做贴片时，两家门店的同一集约 88% 的帧完全相同（按原型样片时长推算）。
- 《微短剧发展管理办法》要求一类、二类剧按许可通过的内容播出（PRD 10.3 引第三十一条，条文原文待法务核对）；第四十六条对未按许可通过的内容播出规定“可以并处十万元以下罚款”。改动正片后播出的风险有明确罚则。
- AI 全片重制在成本上不成立：一部剧的模型成本约为一单收入的 2–15 倍（调研估算，未经一手核实）。

**影响**：对一类、二类剧，“不改正片”则成片高度雷同，“改正片”则可能违反许可。PRD 12.3 已把“深度定制的审核口径”列为待确认，但它实际上决定了产品的核心卖点能否成立。

**业务答复（2026-10-02）**：这一点在产品设计时已经预见。“每份成片内容不同”主要是为了应对平台对同质化内容的限流；业务判断是，同一个 IP 结合不同商家的定位能产生不同的创意，具体的技术手段留待后续探索。

**对架构的含义**：不为“怎么做出差异”预设实现。无论日后是贴片、改正片还是加入 AI 镜头，都落在“系统外制作、系统内登记与质检”的边界内，V1.0 的架构不受影响。系统保留三样东西：制作留痕（所用原片版本、广告版本、AI 使用声明）、差异度指标的空列、质检清单里的差异项与人工抽检。

**仍未解决的一点**：业务答复针对的是限流。许可口径是另一个问题——一类、二类剧改动正片后播出，是否违反“按许可通过的内容播出”——有明确罚则，仍须法务在 V1.0 上线前给结论。结论出来之前，系统按剧的许可类别限制可选的定制方式（PRD 7.2 第 4 条已有此规则）。

**需要做的**

| 事项 | 负责 | 时点 |
| --- | --- | --- |
| 明确一类、二类、三类剧各自允许的定制方式（尤其是能否改动正片） | 法务 + 内容 | V1.0 上线前 |
| 给出标准、高级、顶级三档“制作模型”的可验证定义（工序、是否含 AI 镜头、返工轮次） | 业务 + 内容 | PRD 定稿前 |
| 收敛商家端“写进剧情”等定制说明文案，与 V1.0 实际能力一致 | 产品 | UI 设计时 |

### 1.4 商家账号发布整部短剧处于规则灰区

**事实**

- 三类剧的节目编号由各播出平台自己审核并标注，不得使用其他平台的编号（办法第三十三条）。同一部三类剧在抖音与视频号双发时，片头烧哪家的编号没有答案；按门店改过的成片还可能被视为另一个审核版本。
- 视频号官方认可的短剧发表方式是挂载“短剧组件”，要求平台自己持有微短剧类目的小程序，且最多授权 50 个视频号。商家把整部剧当普通视频发表，规则没有明示允许或禁止。
- 抖音对单账号单日发布量是否有上限没有官方数字。另有二手资料称抖音真人短剧单集时长上限为 3 分钟（未见官方原文，是否适用于普通账号不明）；若属实，加上片头片尾贴片后接近 3 分钟的剧集会越线。
- 抖音的代发布与拉起发布页的能力都不对本产品开放；V1.1 的“服务商代发布抖音”在官方接口层面没有可行解，只剩人工登录代运营，而 PRD 10.2 规定不收集账号密码。

**影响**：PRD 2.5 的“一次性上线全部剧集”可能做不到；已发布的成片存在被平台处置的风险。

**架构对策**：许可信息按“剧 × 播出平台”建模；上线任务支持分批、跨日回填与部分上线；入库体检记录每集时长并在选剧与合成时预警；后台不预留任何抖音发布接口。

**需要做的**

| 事项 | 负责 | 时点 |
| --- | --- | --- |
| 用真实企业号实测抖音、视频号单日可发条数与合集容量 | 业务 + 交付 | 试点前 |
| 确认三类剧双平台发布是否须交付两套成片 | 法务 + 内容 | PRD 定稿前 |
| 确认商家账号直接上传整部短剧的合规路径 | 法务 | PRD 定稿前 |
| 重新评估 V1.1 抖音代发布是否保留 | 业务 | V1.1 立项前 |

### 1.5 成片交付与大文件上传受小程序能力限制

**事实**

- 小程序单次下载最大 200MB，请求并发上限 10，切到后台 5 秒未完成即中断，保存相册官方只保证 MP4。
- 一部剧的成片包为 36–80 集、约 2–5GB（原型示例）。原型的“打包下载”在小程序内做不到。
- 小程序内超过 100MB 的文件能否分块上传没有官方依据：分块读取接口的官方限制措辞是“单个文件大小上限 100M”。

**影响**：商家需要逐集保存 40–80 个视频到相册再逐个上传到抖音，耗时长、易中断，会直接影响按时上线率。

**架构对策**：电脑端下载页进入 V1.0；成片硬性规格为 H.264 MP4，单集体积目标值远低于 200MB（具体值待真机验证）；小程序内上传在真机验证前只承诺 ≤100MB。

**需要做的**

| 事项 | 负责 | 时点 |
| --- | --- | --- |
| 确认以“电脑端下载并发布”为主线、小程序逐集保存为辅 | 产品 | PRD 定稿前 |
| 统一视频上传上限（PRD 10.1 写 200MB，6.16.3 写 500MB） | 产品 | PRD 定稿前 |
| 真机验证 150MB、300MB、500MB 的分块上传（iOS、安卓各一轮） | 研发 | M0 |

### 1.6 《定制内容授权书》的“双方签章”没有对应流程

**事实**：PRD 10.5 要求授权书双方签章；原型写“正式授权书以双方签章版本为准”，但 PRD 与原型都没有双方签署的流程。只贴印章图片不构成《电子签名法》意义上的可靠电子签名。双方电子签意味着每个商家都要在电子签平台完成企业实名认证，且平台按版本、份数、实名包三部分收费。

**架构对策**：默认由平台用机构数字证书对 PDF 做数字签名，商家一方以订购时勾选协议的同意记录为凭；电子签 Provider 预留；生产环境不允许静默降级为图片章。

**需要做的**：法务确认平台单方数字签名加商家点击同意是否足够；若须双方电子签，补签署流程的原型并询价（法务 + 产品，PRD 定稿前）。

## 6. 关键路径与落地顺序

平台事项的周期以周计，是关键路径，须在建仓当天并行启动（清单见 [02](02-tech-selection.md) 第 7 节）：两个 AppID 与认证、类目、小程序备案与域名备案、两个微信支付商户号、企业微信主体核对、短信签名报备（7–10 个工作日）、云资源开通、就支付定性在开放社区官方专区提问。生产用的微信支付商户号业务已开通，只需再申请预发用的一个。

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| M0（第 1 周） | 平台事项启动，就支付定性在开放社区官方专区提问，核对商户号类目与限额；建仓并整体换名、锁版本、门禁齐全；起预发环境；完成 V1、V3–V8、V19 验证；架构定 A5 | 合并即部署到预发 |
| 第 2–3 周 | 契约骨架；事务单元、幂等、出站事件、定时器、状态迁移；api 中间件；worker 租约与扫描；小程序请求层与登录；后台外壳与权限指令；发布编排与回滚 | 预发可登录两端；一次发布零失败请求；清空预发 Redis 后周期任务照常触发；人为制造事件积压能收到告警 |
| 之后 | 按领域推进：身份与租户 → 短剧库与媒体 → 计费与支付 → 订购与交付 → 发布 → 客服 → 通知与文书 → 报表。每做完一个领域，补它的不变量检查、告警、端到端用例与真机清单 | 各领域的并发测试与回放测试通过 |
| 上线前两周 | 验证项闭环；恢复、告警、发布演练；预购手机号资源包；提审 | 发布检查表全部勾选 |

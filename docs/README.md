## 阅读顺序

1. 先读 [05](05-risks-and-open-issues.md) 第 1 节。其中 6 项风险可能改变产品形态或上线时间，需要业务、法务先行处理。
2. 再读 [01](01-architecture.md) 的“一页结论”和 [02](02-tech-selection.md) 的选型总表。
3. 负责具体领域的同事读 [03](03-key-designs.md) 对应章节；表结构看 [06](06-data-model.md) 与 [data-model/](data-model/README.md)，接口看 [07](07-api-contract.md) 与 [api/](api/README.md)。设计草案（[appendix/design](appendix/README.md)）只在需要来龙去脉时查，与 06、07 不一致处以 06、07 为准。

## 这些文档是怎么得出的

下面说的是 01–05。数据模型与接口契约的做法、校验结果与没有验证的部分，分别见 [06](06-data-model.md) 第 1、8 节与 [07](07-api-contract.md) 第 1、9 节。

1. 通读 PRD 全文与两套原型的 103 个画板，抽取实体、状态机、时间规则、通知、参数与接口。
2. 梳理参考工程的架构、66 条决策记录、部署与踩坑记录，判断哪些沿用、哪些必须新建。
3. 对 91 条会影响方案的外部结论（微信支付与虚拟支付规则、小程序能力上限、类目与资质、云服务能力、各依赖的真实版本）逐条查证一手来源：60 条成立，31 条部分成立并已按更正后的说法采用，没有被否定的。
4. 七个子系统各做一份详细设计，经对抗式评审后修订；主文档对各份设计之间的分歧给出裁决。
5. 五份主文档写成后，再由三位复核人分别对照核实记录、PRD 原文与文档之间的一致性做了一轮复核，发现的问题已修正。PRD 2.9 的 7 个计费示例与周期日期规则经重算无误。

没有做的事：没有写任何业务代码，没有跑任何业务测试（数据模型在 PostgreSQL 上真正建过表、执行过全部约束，见 [tools/schema-check](../tools/schema-check/README.md)），图表没有用渲染工具验证过，原型一侧的数字没有逐一回到原型核对。

## 约定

- 文中“核实”指附录 [fact-check.md](appendix/fact-check.md) 里有一手来源的结论；“推断”指没有一手来源、需在验证清单中确认的判断。
- 价格、限额、平台规则均为 2026-10-02 的查证结果，签约与提审前须再次核对。
- 主文档与附录草案不一致时，以主文档为准。

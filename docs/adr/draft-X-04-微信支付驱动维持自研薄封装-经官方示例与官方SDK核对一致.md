## 背景

- ADR-016 提议微信支付用 Node 内置 `crypto` 与 `fetch` 自研，不用社区 SDK，代价是“验签、解密的维护责任自担，须用官方示例与验签工具做对照测试”。它在 04 里是“提议”，X-04 的验收就是“官方示例向量通过”（计划 第 7.4 节）。
- 约束：不连真实商户号，不用任何真实商户密钥（任务书 第 5 节）；测试密钥现场生成，不入库；向量只能来自官方文档或官方 SDK，不自造“官方向量”（任务书 第 11 节第 1 项）。
- V13 要答三问：交易账单里退款行的日期口径、是否含回传数据列、是否有沙箱（计划 第 8.6 节）。本包只给官方文档层面的说法。

## 决定

微信支付驱动维持自研薄封装（`packages/services/src/providers/wechat-pay/`），按微信支付公钥模式做，同时接受平台证书；不引社区 SDK。下面五小节是 G4-A、G4-B 接着做时照用的细则。

### 1. 做法

| 项 | 做法 |
| --- | --- |
| 请求签名 | `方法\n地址（带查询串）\n时间戳\n随机串\n请求体\n`，商户 API 私钥做 RSA-SHA256；`Authorization: WECHATPAY2-SHA256-RSA2048 mchid,nonce_str,signature,timestamp,serial_no`；请求头带 `Wechatpay-Serial: PUB_KEY_ID_…` |
| 应答验签 | 2xx 的应答一律验签（含 204 的空应答），按应答头 `Wechatpay-Serial` 选公钥，并核对时间戳与本机相差不超过 5 分钟；验不过即丢弃应答、按“不可用”返回，由调用方重试。非 2xx 只读错误码，不验签（官方 Go SDK 同此；与 D2 第 10.2 节“所有应答也要验签”有出入，见状态文件偏差 11）：错误码与 Request-ID 因此是没验过签的，驱动只放行各自的写法（错误码是大写字母、数字、下划线），别的不进结果、信息与日志。账单下载的应答不带签名，靠摘要值校验（先卡 40 位十六进制的写法，再比对） |
| 应答里的单号 | 查单、退款、退款查询的应答验签之后再核对单号：与请求的不是同一个即丢弃应答，按“不可用”返回。退款查询只核对退款单号 |
| 回调入口 | 输入原始字节与四个请求头，输出判别结果。顺序照 h01 第 2.1 节：按序列号找验签身份 → 验签 → 时间戳 → 解析外层 → 解密 → 核对必需字段与取值约束。探测签名照常验签，失败结果上打 `probe` 标记 |
| 回调的取值约束 | 照 h01 第 3.1、3.2 节，不满足判“报文不全”：支付成功通知的 `trade_state` 只认 `SUCCESS`；退款通知的 `refund_status` 要与事件类型是同一个（`REFUND.SUCCESS` 配 `SUCCESS`，余类推，所以 `PROCESSING` 一律不收）；退款成功要带 `success_time`；支付金额、退款金额是正的整数分。处理事务 T1 不做业务判断，这几样由驱动拦。“事件类型与退款状态是同一个”是从官方文档 4012791906 的枚举推出来的，文档没有逐字这样写，真实通知的核对见第 5 节第 8 项 |
| 验签身份 | `PUB_KEY_ID_` 开头的序列号用微信支付公钥，其余用平台证书；两种同时配置。平台证书的序列号要与证书里的一致（大小写不计，照证书自己的序列号登记），公钥一栏不收私钥与证书，否则启动即失败。证书的有效期不查（官方 Go SDK 的验签器同此） |
| 密钥环 | 当前一把加上一把 APIv3 密钥。解密先试当前、再试上一把，返回实际解开的那把的 `kid`（写进 `webhook_event.key_version`）；重处理时按指定 `kid` 重新解密 |
| 金额 | 一律整数分。应答与通知里的金额不是安全整数即判为不合规；账单的“元”字符串定点解析，不经浮点 |
| 错误 | 返回 `ProviderResult`，不引契约的错误码。失败结果另带微信的错误码（`code`，如 `ORDER_NOT_EXIST`、`NO_STATEMENT_EXIST`）；错误信息只带状态码、错误码与微信的 Request-ID |
| 不泄密 | 请求体、`Authorization` 头、地址里的查询串、微信的错误说明都不进错误信息与日志 |
| 时钟 | 必须注入（`deps.now` 是必填的依赖），驱动里不取系统时间：请求与调起支付的时间戳、应答与回调的 5 分钟判定都用它 |
| 配置校验 | 五项成组；填了的逐项核对写法（私钥、公钥本体、两把 APIv3 密钥、并存的验签身份、回调地址）。写错在成组校验里报出字段名与一句固定的原因，不带任何值与底层报错 |

### 2. 八个方法与官方现行文档的对照

地址与字段逐个核对过（文档编号见“理由”第 1 项）。与任务书 第 10 节的表不同、或表里没写的：

| 方法 | 微信接口 | 与任务书的表不同或补充的 |
| --- | --- | --- |
| `createJsapiOrder` | `POST /v3/pay/transactions/jsapi` | 无。`time_expire` 写成北京时间的 RFC 3339 |
| `signMiniProgramPay` | 本地 | 无 |
| `queryByOutTradeNo` | `GET /v3/pay/transactions/out-trade-no/{no}?mchid=…` | 查询串要带 `mchid`。订单不存在是 404 `ORDER_NOT_EXIST` |
| `closeOrder` | `POST …/out-trade-no/{no}/close`，请求体 `{mchid}` | 成功是 204、没有包体。**现行文档没有给“订单已支付”的专用错误码**（只列了通用的 `INVALID_REQUEST`、`TRADE_ERROR` 等）。所以三态这样定：204 是已关；连不上、超时、5xx、429 是可重试；其余 4xx 回查一次订单，回查到已支付或转入退款即“已支付”，回查到已关闭即“已关”，否则照关单接口的拒绝返回 |
| `createRefund`、`queryRefund` | `POST /v3/refund/domestic/refunds`；`GET /v3/refund/domestic/refunds/{out_refund_no}` | 退款单不存在是 404 `RESOURCE_NOT_EXISTS`。回调地址可不传（不传按商户平台上配的） |
| `applyTradeBill` | `GET /v3/bill/tradebill?bill_date=…&bill_type=ALL` | 不传 `tar_type`，账单不压缩。应答是 `hash_type`（固定 SHA1）、`hash_value`、`download_url`（5 分钟内有效）。当日没有账单是 400 `NO_STATEMENT_EXIST`（返回 `null`）；`STATEMENT_CREATING` 按可重试 |
| `downloadBill` | `GET download_url` | 请求要签名，应答不带签名、不验签；下载地址只认微信支付的主、备域名 |
| `fetchTradeBill`（W0-19 的接口方法） | 申请加下载 | 当日没有账单时返回空文本 |
| `verifyAndDecryptNotification` | 本地 | 驱动另给 `verifyNotification`（判别结果）与 `reopenResource`（按 `kid` 重新解密） |

`types.ts` 的 `wechatPay` 接口没有改。比接口多出来的方法先放在驱动的类型 `WechatPayDriver` 上，由 G4-A 按“只增”提进接口（提进接口要同时改未配置实现、替身与样例入参，不在本包允许的目录里）。

### 3. 账单格式（官方文档 4013071246，`bill_type=ALL`）

| 项 | 官方文档的说法 |
| --- | --- |
| 结构 | 第一行明细表头（27 列）；每行一条明细；一行汇总表头（7 列）；一行汇总数据。字段用英文逗号分隔，明细与汇总的每个字段前有一个反引号 |
| 金额 | 单位元、两位小数。手续费：收款为正、退款为负 |
| 收款行 | 交易状态 `SUCCESS`；退款单号两列写 `0`，退款状态留空 |
| 退款行 | 交易状态 `REFUND`（付款码支付的撤销是 `REVOKED`）；应结订单金额与订单金额写 `0.00` |
| 退款状态 | `SUCCESS`、`PROCESSING`、`FAIL`、`CHANGE`。**与接口、通知里的取值不同**（接口是 `SUCCESS`、`CLOSED`、`PROCESSING`、`ABNORMAL`） |
| 转义 | 商品名称、商户数据包、设备号里的特殊字符会被转义（逗号变成反斜杠加空格等，收款行与退款行的规则略有不同）。解析保留转义后的原文，不还原 |
| 早期格式 | 少数商户的账单没有“应结订单金额”“代金券金额”两列。本实现遇到缺列即报错，不猜 |

解析按表头的列名取值，不按位置；“用户标识”一列（openid）不取。

### 4. V13 三问在官方文档里的说法（待真实账单复核）

| 问 | 官方文档的说法 | 对方案的影响 |
| --- | --- | --- |
| 退款行的日期口径 | “交易时间”指支付成功时间或**发起退款成功时间（不是退款成功时间）**；“退款发起成功就会出账，出账后退款状态不会更新”（4013071246）。交易账单“以交易的支付成功时间或商户退款受理成功时间判断”归日；账单是日切后的数据快照，之后的变化不再反映（4013071215）。即：退款行只在受理日的账单里出现一次，状态是出账那一刻的 | 与 D2 第 8.2 节、08 分组第 2.8 节现在的做法相容：退款不按日对齐，行的状态不是成功就不改本库。“成功日再出一行”在文档层面不会发生；`wx_bill_line` 不以退款单号做唯一键的写法留着无害 |
| 是否含回传数据列 | 含。三种账单都有“商户数据包”一列，对应下单的 `attach`；下单文档也写明它“会体现在交易账单”（4012791897） | `wx_bill_line.attach` 可以填。我方的回传数据只有 base64url 与点号，不受转义影响 |
| 是否有沙箱 | 本次查的 27 份现行文档（清单见“理由”第 1 项）里没有沙箱或仿真环境的说明（逐份搜过“沙箱”“仿真”“sandbox”）；接口域名只有主、备两个正式域名 | 按“没有沙箱”准备：预发用独立商户号小额实付（D7 第 10.7 节）。向微信支付确认随 E5 |

三问都只是文档层面的结论。G4-A、G4-B 用预发商户号的真实账单复核后关闭 V13。

### 5. 交给 G4-A、G4-B 的事项

| # | 事项 |
| --- | --- |
| 1 | 接入：在 `providers/index.ts` 留的位置调 `createWechatPay(settings, deps)`；`deps.now` 必填，给内核的时钟；把多出来的方法提进接口。驱动自己在发请求的方法入口调外呼前钩子，工厂的 `withBeforeCall` 也会包一层：二选一，别调两次 |
| 2 | 变量：`loadEnv` 里还没有任何 `WXPAY_*`（W0-19 状态文件偏差 1：要先有一个 `gate-change` PR 放开键数）。五项成组的建议名：`WXPAY_MCHID`、`WXPAY_CERT_SERIAL`、`WXPAY_PRIVATE_KEY_FILE`、`WXPAY_API_V3_KEY_FILE`、`WXPAY_PUBLIC_KEY_ID`。驱动另要：微信支付公钥本体（建议 `WXPAY_PUBLIC_KEY_FILE`）、小程序 AppID（取 `wechat` Provider 的）、支付回调地址（由接口域名拼出，或 `WXPAY_NOTIFY_URL`）。可选：退款回调地址、上一把 APIv3 密钥及两把的版本号、平台证书。名字由 G4-A 登记时定 |
| 3 | 关单：用预发商户号实测“对已支付的订单调关单”返回什么（状态码与错误码），核对第 2 节的三态 |
| 4 | 回调框架用驱动的 `verifyNotification`（判别结果，带解密后的资源原文），不用接口方法 `verifyAndDecryptNotification`：后者只分通与不通，归一后的结果不带商户号与 AppID。判别结果映射到 `WEBHOOK_*`：验签失败与探测 → `WEBHOOK_SIGNATURE_INVALID`；时间戳 → `WEBHOOK_TIMESTAMP_SKEWED`；身份查不到 → `WEBHOOK_KEY_NOT_FOUND`；解密失败 → `WEBHOOK_DECRYPT_FAILED`；报文不全 → `WEBHOOK_PAYLOAD_INVALID`。**处理函数自己要核对的**：`resource.mchid`、`resource.appid` 属于本系统（不属于记 `ignored` 并告警，h01 第 3.1 节），驱动只把字段给出来。状态与事件类型的约束驱动已经拦了（第 1 节“回调的取值约束”） |
| 5 | 账单：复核 V13 三问；按真实账单核对退款状态的取值、早期格式是否存在、转义后的回传数据 |
| 6 | 平台证书的下载与自动更新不在本包。要用平台证书时由配置给出。证书的有效期驱动不查，到期前由配置换下；要查得另给验签身份表接上时钟 |
| 7 | 对账（G4-B）不要只凭 `fetchTradeBill` 返回空文本就认定当日没有交易：`NO_STATEMENT_EXIST` 来自没验过签的 4xx 应答。当日本库有成功收款而账单为空，开差异 |
| 8 | 用预发商户号的真实退款通知核对“事件类型与 `refund_status` 是同一个”“成功必带 `success_time`”（第 1 节“回调的取值约束”）。对不上时驱动会判“报文不全”、微信会重发，退款结果由 `rf.poll` 与对账兜底，不会丢；但要先改驱动再上线 |
| 9 | `parseTradeBill` 只把文本解析成行：不核对汇总行的笔数、金额与明细之和，“有表头没有汇总行”也算解析成功（`summary` 为 `null`）。这两样对账时当异常处理 |
| 10 | 时间戳正好相差 300 秒：本实现与 h01 是通过，官方 Go SDK 是拒绝（见“理由”事实表第 4 项）。要不要对齐随 h01 的勘误一并定 |
| 11 | 换微信支付公钥：两把并存时另一把放进 `platformCertificates`（验签身份表两种都认），请求头里带的公钥 ID 只有一个。官方文档没有写换公钥的流程，用到时先向微信支付核对 |

## 理由

1. **官方文档的示例**（`__fixtures__/official-docs.json`，各条写明网址与文档更新时间，取于 2026-10-05）：请求签名串两例（带请求体 4012365336、不带请求体 4012365334）、调起支付签名串一例（4012365341）、应答验签串两例（4013053420、4013053249），本实现构造的串与文档逐字节一致；文档用公开的测试商户私钥算出的三个签名值，本实现签出的结果与之逐字节相等（私钥不入库，由 `pnpm wxpay:vectors` 现场从文档取）；平台证书文档给的公钥、签名与应答，本实现验签通过，改动任一字节即失败。

## 放弃的备选

| 备选 | 为什么不选 |
| --- | --- |
| `wechatpay-axios-plugin`、`wechatpay-node-v3` | 同 ADR-016：前者带 axios，后者久未更新。自研部分经上面的核对与官方实现一致 |
| 关单只认 204 与特定错误码 | 现行文档没有给“订单已支付”的错误码，靠记忆里的旧码不可靠；回查订单状态不依赖错误码 |
| 把官方 SDK 的测试密钥入库当向量 | 会被密钥扫描拦下；为它加放行是放松门禁，不在工作包 PR 里做 |
| 用官方 Java SDK 在容器里加密来产出向量 | 多一套工具链。Go SDK 已覆盖签名、验签、解密与通知解析；Java 的加密向量现场取回核对即可 |

## 代价

1. 验签、解密与安全更新的维护责任自担（同 ADR-016）。微信支付改签名规则或加密算法时，先重跑 `pnpm wxpay:vectors` 与官方 SDK 的新版本核对。
2. `cross-check.json` 的核对要 Docker 与外网，不进 CI；CI 里只拿入库的公钥、签名、密文再验一遍。升级 Node 的大版本后手工重跑一次。
3. 关单的三态里，“4xx 后回查”多一次请求；真实接口对已支付订单的返回还没有实测（第 5 节第 3 项）。
4. 本包体量超过了甲类一个 PR 约 600 行的上限（复审之后：驱动源码 1,328 行，其中非空非注释 1,030 行；替身净增 270 行）。没有拆，提交按机制分开；拆不拆、怎么拆由业主定，定之前本包记为阻塞（`docs/plan/status/X-04.md` 的“阻塞原因”与偏差 1）。

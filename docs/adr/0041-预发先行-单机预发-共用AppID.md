## 背景

## 决定

先只建一套环境，叫预发；生产建好之前它暂时兼作生产，两套最终仍分开。预发是单机：库与 Redis 是节点本地的容器，不上负载均衡。预发与生产共用一个 AppID，这个 AppID 由狸有戏接替参考工程。生产在预发初步稳定后新建，届时回到 01 第 11 节与 D7 第 7.2 节的参考设计。

关于 O3 的两点补充（会话的说明，不是业主的结论）：

- 业主的原话是“预发和生产，先使用同一套环境，也就是都用预发这套环境”。这句话可以读成“预发在这段时间里就当生产用”。O3 的默认比它保守：建生产之前不发正式版、不接真实商家。两者有出入，所以列为待业主定，不写成已定。

**内容域为什么这样建议（建议 9）。**

- 单独设内容域的理由只有一条：`dl`、`f` 承载的是商家与员工上传的文件，万一某个对象被浏览器当成页面执行，它与后台不同站，拿不到也改不了后台的 Cookie（D5 第 3.4 节；D7 第 4.15 节）。两份草案都写了退路：独立域要另行备案，赶不上时退到主域子域（D7 第 7.7 节同）。
- 预发用主域子域的理由：另注册域名要重新备案，周期以周计，会卡 M3；按 O3 的默认，建生产之前预发没有真实商家；退路是原文认可的做法。
- 代价一：内容域与后台同站，“同站”这一层隔离不起作用。隔离改由原文已有的四项承担：后台与接口的 Cookie 用不带 `Domain` 的 `__Host-` 前缀（D5 第 3.4 节；02 第 3.2 节已是此做法）；入库时改写 `Content-Type` 并加 `Content-Disposition: attachment`（D5 第 3.4、3.7 节，必做项）；后台写请求校验来源并带自定义头、不开跨域（D7 第 5.1 节）；内嵌预览只放行登记表允许的类型（D5 第 3.7 节）。
- 代价二：它与 `timavia.com` 下的其他站点（公司官网、`api.timavia.com`）也同站。那些站点若设了作用于整个主域的 Cookie，浏览器访问内容域时会带上；它们是否这样设，没有核实。
- 生产为什么倾向另注册：生产是新建的，域名本来就要新配，用独立域名没有迁移成本；生产建得晚，备案来得及。不另注册也可以，生产沿用主域子域，代价同上。

### 4. 预发单机的落地形态

本节是落实第 1–3 节的做法。日志、密钥文件、发布通道属建议 7（会话建议）；镜像仓库属建议 6。细节由 G2-D 的环境包任务书展开（W0-31 交）：计划第 7.5 节写“预发的形态以本文为准”，W0-31 会照本节写。本节里的数值（六个容器的内存上限、`/work` 上限、镜像保留个数）与做法（宿主机 nginx 的要点、发布通道）是会话建议与没有实测的起始值，合并本 PR 不算业主确认；业主有不同意见的，最晚在 W0-31 开工前提出。

环境包 ⑤ 的开工条件（会话建议）：W1-22 合并；E1–E3 与 E4 的预发各项到位；参考工程已停用、机器已腾出（已办，开工前再核对一次：进程没有复活、开机恢复清单仍为空、它的两个容器仍是停止状态）；镜像仓库已建。“E4 的预发各项”指计划第 4.1 节 E4 明细里的预发节点一行（现成的，已腾出）；镜像仓库在明细里另有一行，上面单列了。E4 的其余预发资源不卡 ⑤ 开工：预发另三个桶、数据万象、CDN 与读域名最晚 G3-A 的真实存储驱动包开工前；云监控、拨测与告警接收群卡环境包 ⑦。

预发的 `secure` 桶要不要在 ⑤ 之前开好（会话建议，由 W0-31 写环境包任务书时落定）：建议要。预发一起来就有两处用到它：合并即部署里“合并后自动上传小程序”一步要取预发的构建产物，D7 第 8.5 节第 1 步把这份产物放预发 `secure` 桶的 `ci/` 前缀，单环境阶段照旧从那里取；worker 的每日备份也写这个桶的专用前缀（第 4.4 节）。所以建议 1 把 `lyx-stg-secure` 与能写它的子账号密钥的最晚时点提到 ⑤ 开工前。到时没开好也不挡 ⑤ 开工：自动上传一步先不启用，备份走未配置实现并告警落库（第 4.4 节），两处记入外部验证台账，桶到位后补。

#### 4.3 入口与 TLS（建议 5）

- 宿主机 nginx 终止 TLS。三个预发域名各一个站点，转到 `127.0.0.1:8080`。只新增独立的站点配置文件，不改已有的站点。重载 nginx 会波及公司官网与 `api.timavia.com` 的站点：每次改动先做配置检查，并先经业主同意。
- 原样透传 `Host`。gateway 靠它按域名隔离接口面，改写了就失效。
- 请求体上限：宿主机 nginx 默认 1MB，小于 gateway 的 2MB（回调 1MB），会先一步拒掉。三个站点的上限设成不小于 gateway 的值。
- 安全响应头只由 gateway 与 api 设，宿主机这一层不再加（D7 第 7.2 节记过重复 HSTS 的坑）。
- 客户端 IP：宿主机 nginx 是最外层的自有代理，站在负载均衡的位置，由它覆盖写 `X-Forwarded-For`。gateway 的 `set_real_ip_from` 填宿主机 nginx 进容器的来源地址。这个地址取决于 Compose 网络的网段，网络重建后会变；一旦对不上，所有请求的来源都变成网桥地址，限流、白名单、审计里的 IP 全部失真。所以 Compose 网络用固定网段，部署时用接口契约里的 `GET /admin/debug/client-ip`（`admin.debug.clientIp.get`，a01 第 3.85 节；身份草案 D4 写作 `/admin/sys/debug/client-ip`，以契约为准）实测后写进模板与 `TRUSTED_PROXY_CIDRS`。api 的可信代理跳数仍为 1。
- 证书：预发三个域名的放宿主机 nginx，签发办法由环境包定（会话建议用能自动续期的免费证书；它的签发方是否被微信支付回调与小程序端接受，待核）。`*.liyoxi.timavia.com` 的通配证书盖不住再下一级的 `*.stg.liyoxi.timavia.com`，预发要单独签。`ops.cert_check` 查六个域名的剩余天数：节点上的三个，加腾讯云上的 `dl`、`f`、`media` 三个读域名。
- DNS：三个预发域名解析到预发节点的公网 IP。生产的三个域名建生产时再解析。

#### 4.4 PostgreSQL 17 与备份（建议 3）

- 数据放宿主机卷。四个角色照 D7 第 7.5 节：`lyx_app`、`lyx_migrator`、`lyx_archiver`、`lyx_readonly`。`btree_gist`、`pg_trgm` 两个扩展自己装。
- 备份用 worker 的周期任务 `backup.pgdump`，管道照 D7 第 7.8 节不变：导出 → 公钥加密 → 流式上传。目标从异地备份桶改为 `lyx-stg-secure` 桶的专用前缀；保留期照 D7 第 7.8 节，由桶的生命周期规则执行。解密私钥不上服务器。
- 相对 D7 少了三样：没有任意时间点恢复，最多丢 24 小时；没有主备；没有“备份桶单独一把只写密钥”的隔离，worker 的密钥对 `secure` 桶可读可删，靠该桶的版本控制兜底。备份在腾讯云、库在阿里云，算是异地。
- 真实存储驱动接通之前（G3-A 合并前），预发库里只有可重建的测试数据。备份目标没配置时照 ADR-039 走未配置实现，告警落库。
- 恢复演练在预发只做两步：逻辑备份解密后导入空库；在桶里删一批对象再从历史版本恢复（D7 第 7.8 节恢复演练第 3、4 步）。克隆实例、快照比对、单号流水处理随生产。

#### 4.5 Redis 7（建议 4）

- 一个容器，队列、限流、缓存同用，api 可直接入队，用法与托管方案相同。它不是 D7 第 7.3 节那条“每节点自建、只给本机 worker 用”的退路。
- 不备份。清空后由 PostgreSQL 自愈（D7 第 7.3 节）。
- 同机还留着参考工程已停的 Redis 容器。做“清空 Redis”演练时认准容器；键前缀 `lyx:{env}:` 照用，是第二道保险。

#### 4.6 密钥文件（建议 7，会话建议）

- 逐项一个文件：放在节点上一个只有属主能进的目录里，文件权限 0400，属主是容器内的运行用户；只读挂载到容器的 `/run/secrets/`；环境变量里只出现 `*_FILE` 路径。
- D7 第 7.5 节的兜底是“节点上的文件加云盘加密”两半。这里采用“节点上的文件”这一半；这台服务器的系统盘有没有加密，没有核实。没加密的话，快照与镜像里都带着明文密钥。
- `loadEnv` “敏感项只认 `*_FILE`、给明文即启动失败”的规则不变。不用 `env_file`：它的内容会进容器配置，`docker inspect` 读得到，过不了 D7 第 10.6 节第 17 项。调度会话最初的说法是“环境文件”，这里收正为逐项文件。
- 密钥文件由业主本人写入，或由业主本人从自己的机器传到节点。会话不经手密钥的值；参考工程 `.env` 里的值不经会话转手到节点（结论 4）。
- 分挂照 D5 第 3.7 节不变：api 只挂 `signer`、`sts-issuer` 两把对象存储密钥，`worker` 那把只挂给 worker，mediatool 一把都没有。`lyx_migrator` 的口令单列，只在迁移那一步挂给一次性迁移容器。单机上这只是减小暴露面：节点被攻破，文件全在。
- 对象存储的三把子账号密钥为狸有戏新建。跨云拿不到实例角色，这三把是长期密钥。缓解（会话建议）：只在节点上用的 `worker`、`sts-issuer` 两把，在访问策略里限定来源 IP 为节点的公网 IP。

#### 4.7 镜像与发布通道（建议 6、建议 7，会话建议）

- 镜像由 CI 构建并推到镜像仓库。节点只拉取，不在节点上构建。
- PostgreSQL 17 与 Redis 7 两个官方镜像的来源：原设计里库与 Redis 是托管的，节点只拉自己的四个镜像；改成本地容器后多出这两个。境内节点直接从公共镜像站拉官方镜像是否可行，没有核实。会话建议由 CI 按固定摘要转存到同一个镜像仓库，节点只从该仓库拉；仓库清单相应加两个，或并入现有命名空间。随建议 6 待业主定。
- 通道用 SSH：专用的发布用户，登录后只能执行 `infra/deploy/node-step.sh`，不给终端与端口转发，只许密钥登录。这就是 D7 第 8.2 节写的兜底通道。发布用的密钥对由业主生成，公钥放到节点的发布用户下，私钥与镜像仓库的凭证由业主录入 CI 密文。
- 02 第 3.9 节把“对公网开放 SSH”列在不选一栏。预发先行阶段接受它，收窄靠上面三条；CI 执行机的出口地址不固定，按来源 IP 收不紧。
- 发布顺序照 D7 第 8.2 节，去掉摘流：拉镜像 → `check-env` → 预置静态资源 → 迁移 → 换 worker → 重启 api 与 gateway。节点步骤串行执行，`weapp-uploader` 不与迁移同时跑（内存，第 4.2 节）。重启期间有短暂中断。持续探测脚本照跑，记录中断时长与失败数，不要求为 0。
- 划一条线：节点初始化、改宿主机 nginx、装 systemd 单元这类人工动服务器的事，每一步先经业主同意，谁来执行见第 4.10 节。“合并即部署”是 CI 的自动动作，启用这条流水线时由业主同意一次。

#### 4.8 日志、监控与告警（建议 7、结论 8 的补充）

- 日志：容器的 `json-file` 驱动加轮转（D7 第 7.4 节的默认是每个服务 20MB × 5，按盘量调）。不进云日志，达不到 180 天的保留。5xx 率与 P95 读 gateway 的访问日志算，办法由环境包定。
- 错误上报：预发用 SaaS，不变（D7 第 16 节 Q10）。
- 主机指标：云监控与拨测的账号沿用是业主已定的（结论 8）。节点在阿里云，主机基础指标用阿里云自带的云监控，外部拨测哪家都行，这两句是会话的补充。
- 告警：企业微信群机器人要等企业微信注册并建群（建议 13、E18）。之前告警只落库（计划第 4.1 节 E18 的“没到位时怎么办”）。

#### 4.9 环境标识、小程序版本与试提审

- 环境名：单环境阶段就是 `stg`。`APP_ENV=stg`、桶 `lyx-stg-*`、键前缀 `lyx:stg:`、单号前缀 `T`、只在预发注册的 `stg.pay.autorefund` 都照原设计。将来的生产是新建的 `prod`，不是把 `stg` 改名。这与 O3 的默认配套：预发库里没有真实商家与真实资金。
- 小程序在单环境阶段只有一个接口域名（预发），构建时注入。开发版、体验版都连预发。合并到 main 后，由预发节点上一次性的 `weapp-uploader` 容器上传到这个 AppID，不打标签。
- 送审的那次上传打 `weapp-v*` 标签，单环境阶段只有这一次打。这一步随 G2-D 的环境包 ⑨ 交（它出最小可提审版本）。打了标签，送审中的版本才受 `contract:compat` 保护；审核结束后把标签登记进 `retired.json`。约定 C77 写的“上传生产 AppID 的那一步”在同一个 AppID 下读作“上传送审或发布候选版本的那一步”。
- 试提审（V2）指向预发（补 1，待业主确认）。预发是合并即部署、会做演练的环境，而审核以天计。提审到出结果期间预发要守的约束（会话建议）：不做会重置或放大数据的操作与演练（恢复演练导入、清空 Redis、P95 基线的放大数据）；合并即部署要么暂停，要么只放行对送审版本兼容的变更（D7 第 8.5 节第 6 条的兼容要求照用）；审核用的测试主体与数据保持可用。
- 这个结论的代表性受预发配置影响：预发的价目按 D7 第 10.7 节配成 0.01–1.00 元、只对白名单主体可见，`stg.pay.autorefund` 十分钟后自动退款。审核账号不进白名单就看不到价目，进了看到的是一分钱的套餐。会话建议：审核用的测试主体进白名单；送审期间价目与自动退款怎么处理，出包前请业主定。
- 建生产之后：业主的结论是用小程序自带的版本区分环境（原话：开发版、审核版、线上版）。会话的默认做法是运行时按版本类型选接口域名，开发版、体验版连预发，正式版连生产；这个映射是会话的建议，随 O4 的结论定。它成立的前提是审核人员用的版本取到的是“正式版”，否则审核看到的是预发。验不过的退路：送审包与正式包在构建时固定指向生产（D7 第 7.1 节原来的退化方案）。
- 机制在建生产的拆包时定稿，并守 D7 第 3.2 节：不得让送审版本与线上版本表现不同。按版本类型选的只是连哪套后端。

## 理由

1. 业主手里有一台现成的机器和一个已认证、已备案的 AppID。M0、M1 不依赖环境，预发最早 M2 才用，先建一套小的够用。
2. 共用 AppID 省掉第二套认证、备案与类目（ADR-034 的代价栏写过这笔周期）。代价是第 5.3 节那张表。
3. 预发不是账务的正式环境。02 第 3.4 节不选自建库的理由是“丢失窗口最长 24 小时不可接受”，对没有真实资金的预发可以接受。前提是 O3 的默认。
4. 单节点前面放负载均衡没有冗余意义，只多一处配置与费用。
5. gateway 仍听 8080、镜像四个不变、环境名仍是 `stg`、密钥仍按 `*_FILE` 读：建生产时应用侧不用改，只换外面一圈。

## 背景

- V12 要验的是：`@react-pdf/renderer` 用真实授权书长文本时，中文换行与分页是否正常；不通过的退路是模板 PDF 贴字（05 第 5 节；计划 第 8.6 节）。签名后的表现不在本条，归 G5-B。
- 约束：字体只能是随 server 镜像分发的静态 TTF，生产机没有系统中文字体（D7 第 7.4 节）；渲染只读 `snapshot`，页脚印编号、版次、内容指纹、验真二维码（D6 第 3.5.1、3.5.3 节）；文件不足 1MB（D6 第 3.6 节）。
- 法务的条款文本没到（E8）。样张用自拟的占位长文本，每页标“占位，非法务定稿”。
- 验证工程在 `spikes/license-pdf`，独立工程。版本：`@react-pdf/renderer` 4.9.0（内含 textkit 7.0.1、layout 5.2.0、fontkit 2.0.4、pdfkit 0.20.1），`react` 19.3.0，Node 24。

## 决定

授权书 PDF 继续用 `@react-pdf/renderer` 4.9 渲染，不走贴字退路。字体取随镜像分发的三个 Noto 静态 TTF；中文换行用并段回调，不用 D6 写的逐字回调；渲染前检查缺字，发现即暂停该版出件并提示具体缺字，修正资料或字体后重试。

下面六小节是G5-B照做的细则。第4节缺字出件策略按业主2026-10-30的明确决定更新；原验证工程的替字样张与通过记录保留为历史。

### 1. 渲染库

维持 `@react-pdf/renderer` 4.9，不走贴字退路。`react` 用 19.3.0：渲染库的对等依赖接受 19。

### 2. 字体

| 文件 | 字体与字重 | 用在哪 | 注册的字体族名 |
| --- | --- | --- | --- |
| `NotoSerifSC-Regular.ttf` | Noto Serif SC（宋体）常规 400 | 正文 | `LyxSerifSC` |
| `NotoSerifSC-Bold.ttf` | Noto Serif SC（宋体）粗体 700 | 正文里加粗的小标题、要素表表头 | `LyxSerifSC` |
| `NotoSansSC-Bold.ttf` | Noto Sans SC（黑体）粗体 700 | 标题、条款标题 | `LyxSansSC` |

- 放在 `infra/docker/server/fonts/`，入库；来源、版本、校验和、许可见该目录的 [README](../../infra/docker/server/fonts/README.md)。W1-22 把它们连同两份许可文本拷进 server 镜像。
- 按字重分别 `Font.register`。字体目录由环境变量给出（验证工程用 `LYX_PDF_FONT_DIR`；正式的变量名由 W1-22、G5-B 定）。
- 来源是 Google Fonts 的静态 TTF，不是思源的官方发行：Adobe 与 `notofonts/noto-cjk` 的官方发行都没有静态 TTF（只有 OTF 与可变字体）。两者同源，许可相同（SIL OFL 1.1）。

### 3. 换行

- 不用 D6 第 3.5.3 节写的 `word => Array.from(word)`。它能让中文折行，但每个折行处的行尾会多出一个连字符“-”。
- 改用并段回调（`spikes/license-pdf/src/linebreak.ts`）：把文字切成不可拆的小段，段与段之间插一个空串。空串被排版引擎当成宽度为 0 的间隔，在间隔处折行不补连字符。

| 规则 | 做法 |
| --- | --- |
| 行首禁则 | 句号、逗号、顿号、分号、冒号、问号、叹号、右引号、右括号、右书名号、省略号、破折号并进前一段 |
| 行尾禁则 | 左引号、左括号、左书名号、货币符号并进后一段 |
| 西文与数字 | 24 个字符以内的一串不拆（金额、日期、短编号保持完整）；更长的先在 `/ ? & = . _ - :` 等分隔符之后拆，仍过长的逐字拆 |
| 空格 | 文字里的普通空格先换成不换行空格，并进前一段。不换的话，引擎的兜底算法优先在空格处折行，一行里有空格就会提前折行 |
| 对齐 | 左对齐，不用两端对齐。版心宽度取字号的整数倍（10.5pt × 46 字），纯汉字的行左右都齐 |

### 4. 缺字

- 随附字体没收的字，渲染库不报错，而是换用不嵌入的 Helvetica 来画：显示成错误的拉丁符号并压住后面的字。这种文件不能出。
- 规矩：渲染前按三个字体 `cmap` 的交集逐字检查 `snapshot` 与条款文本。验证工程曾把没收的字换成“〓”并列进报告；这是X-03历史验证做法，不作为正式出件策略。
- 业主2026-10-30已定：缺字即暂停该版出件，提示具体缺字，修正资料或字体后重试；不得替换成“〓”继续出件或把该版标ready。字体修正后按原重试规则重渲同一不可变版次；资料修正由W5-07更正重出生成新版，不回写旧snapshot。W5-07负责实现与反例验证，来源见[业主清单§3.2](../plan/owner-checklist.md)。2026-10-05整体看样通过的历史范围不变，本次决定不表示正式实现、真实签名或签后V12已验。
- 出件后的自检：文件里的字体名只应是随附的三个。出现别的字体名即说明有字回退。
- 控制字符：验证工程的缺字检查放过了换行符、回车、制表符（`src/coverage.ts` 的 `needsGlyph`），而这三种字符进了 `Text` 同样会引入不嵌入的 Helvetica（第 5 节第三行）。实测：短样张的门店名里各加一个，文件里都多出 Helvetica，缺字清单为空。`snapshot` 的字段里带这三种字符时不会被换掉，只靠出件后的自检拦住（渲染命令查到随附字体之外的字体名即以退出码 1 失败，不会悄悄出件）。G5-B 渲染前先把字段里的控制字符规范掉（去掉或换成空格）。

### 5. 模板写法

这几条是渲染库 4.9.0 的实际行为逼出来的，都有用例固定（`spikes/license-pdf/test/engine-facts.test.ts`）。

| 规矩 | 不这样做会怎样 |
| --- | --- |
| 页脚这类带渲染回调的内容：用 `View` 带 `render`，行高写在回调返回的 `Text` 自己身上 | `Text` 带 `render`，或返回的 `Text` 靠继承取行高：每重排一遍行高就被再乘一次字号，字被排到页面外面。回调照常被调用，页数也对，只是页脚没印出来 |
| 行高与字号写在同一个样式里 | 只写行高、字号靠继承：行高按默认的 18pt 算，不按继承来的字号 |
| `Text` 里不用换行符，多行就用多个 `Text` | 换行符在字体里没有字形，文件里会多出一个不嵌入的 Helvetica |
| 条款标题设 `minPresenceAhead` | 标题会单独留在页尾 |
| 要素表一行一个不拆的 `View`，每行自带四边框；同意记录与落款放在一个不拆的块里 | 表格在页间断开时缺边框；落款单独落到一页上 |
| 加粗片段的开头不放标点 | 禁则只在同一个文字片段内生效，片段交界处可以折行 |

### 6. 页数与页脚怎么核对

总页数取页脚渲染回调拿到的值，并与文件里的页对象数互相印证。“每页都有页脚”不能只看回调有没有被调用（见第 5 节第一行），要从文件里把文字读回来核对。验证工程为此手写了最小的读取（`src/pdftext.ts`，只用 Node 自带的 zlib，不引库），渲染命令与用例都照此核对。G5-B 的用例可以沿用。

## 理由

实测结果。证据：`spikes/license-pdf/out/` 的三份 PDF、`report.json`、`report.container.json`；命令输出见 [PR #14](https://github.com/byfire-dev/liyoxi-project/pull/14) 的评论；第 1–3 条另由按路径触发的工作流 `.github/workflows/spike-license-pdf.yml` 在 CI 上重跑（不是必过检查），产物 `license-pdf-out` 是那次运行渲染出的样张与报告。下表的数字取自入库的两份报告，另有来源的单独注明。

| 验收（任务书 第 7 节） | 结果 |
| --- | --- |
| 1 三份样张渲染成功 | 通过。短 1 页、70,046 字节；长 4 页、166,514 字节；极端 6 页、141,790 字节 |
| 2 分页稳定 | 通过。72 条用例全绿：页数落在区间内；同一份 `snapshot` 渲染两次页数相同；每页都印了编号、版次、内容指纹、页码 |
| 3 只靠随附字体 | 通过。`node:24-slim` 容器里系统字体文件数为 0，按锁文件只装生产依赖，三份页数与本机一致，字节数也相同。linux/arm64 原生与 linux/amd64 模拟各跑过一遍 |
| 4 体积与耗时 | 通过。最大 166,514 字节，远小于 1MB。本机（`report.json`，darwin/arm64）：首次渲染 84–148 毫秒，同一进程再次渲染 21–72 毫秒，进程内存峰值 240–285MB。容器里（`report.container.json`，linux/arm64）：首次 120–193 毫秒，再次 24–92 毫秒，内存峰值 204–251MB。内存主要是三个字体读进内存。linux/amd64 模拟那一遍更慢（首次 389–534 毫秒，内存峰值 274–320MB），结果没有入库，只在 PR #14 的验收证据评论里，仅作参考 |
| 5 字体合规 | 通过。3 个静态 `.ttf`，目录里有许可文本，`README.md` 写了来源、版本与校验和 |
| 6 看样 | 通过。业主 2026-10-05 确认看样通过。这是整体结论：业主没有逐条给出任务书 第 8 节七条的“可以 / 不可以”，本文不替业主逐条填。会话的预查见下表 |
| 7 结论入 ADR | 本文，取号 ADR-042；台账 V12 与计划 第 8.6 节已同步 |

## 放弃的备选

| 备选 | 为什么不选 |
| --- | --- |
| 模板 PDF 贴字（V12 的退路） | 渲染的技术核对与业主看样都通过，不需要。什么情况下回到它见“代价”第 5 项 |
| D6 第 3.5.3 节的 `word => Array.from(word)` | 行尾多出连字符；标点会落在行首 |
| 两端对齐 | 行里有长西文串时字距被拉开；左对齐加整数倍版心已经够齐 |
| 思源官方发行的 OTF 或可变字体 | 渲染库只支持 TTF 与 WOFF，不支持可变字体（D7 第 7.4 节）。本包没有重验这一条 |
| 只放两个文件（宋体常规、黑体粗体） | 正文里就没有同款的加粗。法务文本常要把提示性条款加粗 |
| 加一个后备字体来补缺字 | 本包不做：任务书限定至多 3 个字体文件，再加一个镜像也更大；官方也没有一个收全 6 万多字的静态 TTF。技术上可行，留给 G5-B 评估：渲染库支持按字回退的字体栈（`@react-pdf/layout` 5.2.0 里 `fontFamily` 可以写成数组，`@react-pdf/textkit` 7.0.1 的 `pickFontFromFontStack` 逐字挑字体）。这一条是读渲染库的代码得出的，没有实跑；哪款字体能补上扩展 B 区以后的字与表情符号也没有验 |
| 构建镜像时按固定地址与校验和下载字体 | 任务书的默认是入库。业主没有单独答复这一条；三个字体已随 PR #14 合并入库，按现状算定。以后要改只动 W1-22，已经进了 git 历史的那一份拿不掉 |
| 装解析 PDF 的库来做自动核对 | 任务书不允许新增。手写的最小读取够用 |

## 代价

1. 仓库与 server 镜像各多 40,163,236 字节（约 38.3 MiB）的字体。
2. 已知限制：

| 限制 | 影响与对策 |
| --- | --- |
| 扩展 B 区及以后的生僻字大多没收，表情符号全没收 | 被授权方名称、门店名、经办人姓名、发布账号名出现缺字时暂停该版出件并提示具体缺字，修正资料或字体后重试；正式出件不得沿用历史验证的“〓”替字，见“决定”第4节 |
| 禁则只在同一个文字片段内生效 | 模板里加粗片段的开头不放标点 |
| 标点不做挤压 | 全角标点连用时显得松。业主看样通过（整体结论），没有单独就这一条表态 |
| 行宽不是两端对齐 | 含西文、数字、弯引号的行右边不齐。长样张的 52 个满行里 24 行左右都齐，其余差距都在两个字以内；极端样张里一长串标点或长西文串整体折到下一行时差距更大，最多 11 个字 |
| 24 个字符以上的西文串会被拆开 | 长网址、内容指纹在分隔符或任意字符处折行，不加连字符 |
| 换行回调是全局注册的 | 同一个进程里所有用这个渲染库出的 PDF 都用同一套换行规则 |
| 第 5 节的几条依赖渲染库 4.9.0 的行为 | 升级渲染库前先跑 `engine-facts.test.ts`，失败就回头看本条 |
| 进程内存峰值两三百兆 | worker 的内存配额要算上这一块 |
| 渲染库带进一个预发布版的传递依赖 | `@react-pdf/reconciler` 2.0.0 把 `scheduler` 钉在 `0.25.0-rc-603e6108-20241029`，是上游写死的，换不掉。G5-B 把渲染库装进 server 时它会一并进生产镜像，到时在 02 第 5.5 节的锁定清单里记一笔 |
| 占位文本不是法务定稿 | 条款到位后由 G5-B 用真文本复测页数与看样 |
| 签名后的表现没有验 | 归 G5-B，最晚 M8 进入前（计划 第 8.6 节） |

3. 该勘误而本包不能改的三处（不在任务书允许的目录里，按 `CLAUDE.md` 第 11 节停在报告，请业主安排）：
   - D6 第 1.2 节硬约束表里渲染库那一行写的“用 `Font.registerHyphenationCallback` 逐字切分”：应改为“并段回调，见 ADR-042”。
   - D6 第 3.5.3 节末条的回调写法 `word => Array.from(word)`：应改为“并段回调，段间插空串，见 ADR-042”。

4. 重新评估的时机：升级 `@react-pdf/renderer`；缺字在真实数据里出现得多（那时评估渲染库对 OTF 全量字体的支持）；业主决定字体改为构建时下载（只动 W1-22）。

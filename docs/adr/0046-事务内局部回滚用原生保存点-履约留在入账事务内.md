| 回写 | 计划 第 8.6 节表一 V4 行；`docs/plan/external-verification/v04-savepoint.md`；02 第 3.3 节“事务保存点”行；`docs/plan/status/W0-07.md` |

## 背景

- 两处设计依赖“同一个事务里局部回滚”：付款履约（03 第 1.3 节第 4 条、01 第 8.1 节：履约失败只回滚保存点，收款照常入账）；埋点直记（14 分组 第 2.9 节：埋点写入失败不把业务事务带成中止状态）。
- V4 要答的是：Prisma 7 交互式事务里保存点能不能用。不通过的退路是“履约改为入账提交后的第二个事务”，W1-11a 的事务结构跟着变（05 第 5 节；计划 第 8.6 节）。
- 实测的版本：Prisma 7.9.1（`prisma`、`@prisma/client`、`@prisma/adapter-pg` 三包同版）、`pg` 8.23.0、PostgreSQL 17（`postgres:17-trixie`）、Node 24。

## 决定

V4 通过，不走退路。事务内的局部回滚一律用 kernel 的 `savepoint(tx, fn)`（`packages/services/src/kernel/tx.ts`）；履约留在入账事务内，W1-11a 按 03 第 1.3 节的原方案做。

### 1. 做法

| 项 | 做法 |
| --- | --- |
| 发什么 | 原生 SQL 三句：`SAVEPOINT`、`ROLLBACK TO SAVEPOINT`、`RELEASE SAVEPOINT`，用事务句柄的 `$executeRawUnsafe` 发，走交互式事务的同一条连接 |
| 名字 | 封装自己取：`lyx_sp_<序号>`，一个事务内递增。调用方不写保存点的名字 |
| `fn` 正常返回 | `RELEASE SAVEPOINT`，返回值原样给出；写入随外层事务提交或回滚 |
| `fn` 抛错 | `ROLLBACK TO SAVEPOINT` 再 `RELEASE SAVEPOINT`，错误原样抛给调用方；接不接由调用方定 |
| 嵌套 | 可以套。内层失败不带走外层 |
| 锁序记录 | 保存点里加的行锁随回滚释放，锁序断言的记录跟着退回到保存点之前 |

### 2. 调用方的规矩

1. 接错误只接业务错误。死锁、锁等待超时、序列化失败要让它继续往外抛，由 `tx.run` 把整个事务重试；接住它们会把“请重试”变成“履约失败”。
2. 要接住数据库错误并接着用这个事务，必须用保存点包住那一段。不包的话事务已被数据库中止，后面的语句报 `25P02`。
3. 保存点期间不并发地用同一个事务句柄：同一条连接上的语句一句一句发。
4. 不用 Prisma 事务客户端在运行时带的 `$transaction`（见“放弃的备选”）。

### 3. 顺带查实并处理的一件事

事务里接住了数据库错误、之后不再发语句就返回：PostgreSQL 会把 `COMMIT` 当成 `ROLLBACK` 执行且不报错，Prisma 的 `$transaction` 照样报成功，写入全丢而调用方以为成功。`tx.run` 因此在提交前探一句 `SELECT 1`：事务已被中止时在这里报错。

## 理由

实测结果（`packages/services/src/kernel/tx.savepoint.test.ts`，连真库；随 CI 的“测试”一步每次都跑，首次运行见 W0-07 的 PR）：

| 场景 | 结果 |
| --- | --- |
| 保存点内抛业务错 | 保存点外的写入随提交落库，保存点内的不落库；回滚后事务还能接着写 |
| 保存点内触发数据库错（唯一约束冲突 `23505`），原生 SQL 与模型接口各一例 | 同上：回滚到保存点之后事务恢复可用，后面的写入落库 |
| 保存点之前拿到的行锁 | 保存点回滚后还在：另一条连接 `FOR UPDATE NOWAIT` 拿不到，事务提交后才拿得到 |
| 保存点里拿到的行锁 | 随保存点回滚释放：事务还没结束，另一条连接已经拿得到 |
| 保存点套保存点，内层失败 | 外层的写入落库，内层的不落库 |
| 保存点成功、事务随后失败 | 保存点里的写入一并回滚 |
| 对照：不用保存点接住数据库错误 | 接着写报 `25P02`；不再写则提交前的探查报错。两种都是整个事务不落库 |

两处变异核对过用例管用：去掉 `ROLLBACK TO SAVEPOINT`，前五例变红；去掉提交前的探查，对照一例变红。

## 放弃的备选

| 备选 | 为什么不选 |
| --- | --- |
| 履约改为入账提交后的第二个事务（V4 的退路） | 保存点可用，不需要。两个事务之间进程中断会留下“已入账、没履约”的中间态，要另写补偿 |
| Prisma 事务客户端在运行时带的 `$transaction` | 7.9.1 实测它在同一条连接、同一个事务里执行回调，但类型上不公开（事务客户端的类型去掉了它），行为没有文档承诺；用了它也绕过“开事务只有一个入口”的 lint 规则 |
| 每句 SQL 自动套一个保存点 | 每句多两个来回；数据库错误被自动吞掉，掩盖真问题 |

## 代价

- 保存点是手写 SQL，不是 Prisma 公开的功能：升级 Prisma、换数据库驱动或在应用与库之间加连接池中间件时，以 `tx.savepoint.test.ts` 的结果为准，红了就回到本条重新评估。
- 每个保存点多两个来回（失败时三个）；`tx.run` 的提交前探查让每个事务多一个来回。
- 履约留在入账事务内，这个事务比“只入账”长，仍受事务超时（缺省 10 秒）约束：履约里不能有慢查询，更不能调外部服务。

## 总体形态

### ADR-001 模块化单体 + monorepo（提议）

- **背景**：早期数百商家、千级订单；3–6 人团队；订购提交要同步冻结积分。
- **决定**：一个 pnpm monorepo，五个应用（weapp、admin、portal、api、worker）与五个包（contract、db、services、shared、config）；服务端是一个模块化单体，api 与 worker 是同一份代码的两种进程。
- **理由**：单事务跨模块是刚需；一份契约、一份 schema、一份业务逻辑。
- **放弃**：微服务（丢失单事务，运维成本高）。
- **代价**：模块边界靠工具强制而非进程隔离（见 ADR-004）。

### ADR-002 新仓库、整体换名，不与参考工程共用运行资源（提议）

- **背景**：参考工程也叫“狸有戏”，占用了 `@liyo/*`、队列名、Redis 键、进程名、令牌受众；其队列名没有产品前缀。
- **决定**：新仓库，包作用域 `@liyoxi/*`，技术前缀 `lyx`；不共用机器、数据库实例、Redis；可共用云账号与已备案主域的子域。
- **理由**：共用 Redis 会互相消费任务；共用小程序 AppID 会互相顶掉 access_token（改用稳定版接口可缓解，但类目、订阅模板、体验版槽位、手机号额度仍然耦合）。
- **代价**：小程序 AppID 是否新注册需业务定（[05](05-risks-and-open-issues.md) 第 3 节）。

### ADR-003 契约先行（提议）

- **决定**：`packages/contract` 的 Zod schema 是接口唯一手写源，生成三份 OpenAPI（商家端、后台、下载页）与类型；持续集成检查生成物与兼容性；小程序每次上传生产版本时打标签，标签即契约快照。
- **理由**：沿用参考工程已跑通的链路；小程序发版有审核周期，线上会长期存在旧版本客户端。
- **代价**：新增状态值与事件类型须“先声明、下一版再写入”。

### ADR-004 分层与依赖方向由工具强制（提议）

- **决定**：services 分五层（横切、基础、资金、履约、读侧），同步调用只能向下；用 dependency-cruiser 在持续集成中强制；同层调用按白名单。
- **理由**：参考工程只靠约定，已出现越层访问；本项目模块数量是它的数倍。
- **放弃**：每个模块只经事件通信（订购无法单事务冻结积分）。

### ADR-005 业务逻辑只落在 services，事务句柄显式传递（提议）

- **决定**：路由与任务处理器是薄壳；改库的函数第一个参数是带类型标记的事务句柄；只有用例函数可开事务；事务内禁止调用外部服务（测试环境直接抛错）。
- **理由**：沿用参考工程；防止“事务里调微信接口”造成长事务与不一致。

## 数据与一致性

### ADR-006 PostgreSQL 是唯一业务真相，Redis 可丢（提议）

- **决定**：钱、积分、状态、到期时间、任务状态、会话都在 PostgreSQL；Redis 只做队列执行通道、限流、缓存。
- **理由**：腾讯云把托管 Redis 定位为缓存，其命令使用准则明文写“禁止将 Redis 当作消息队列使用”（属厂商定位，不是技术封禁，但出问题时不在其推荐用法内）；账务系统不能把真相放在可丢的存储里。
- **代价**：需要出站事件表、定时器表与扫描（ADR-008、ADR-009）。

### ADR-007 金额存整数分，积分存整数，统一取整（提议）

- **决定**：金额 `int`（分），积分 `int`，比例用万分比整数；全仓一个取整函数（四舍五入）；计价是 `packages/shared` 的纯函数，三端共用。
- **放弃**：Decimal 类型（在 JavaScript 里易出错，且本业务没有小数积分）。
- **补充（2026-10-03，数据模型阶段）**：单据金额一律 `integer`；对账日汇总的合计列与媒体成本估算用 `bigint`，出接口转字符串（[06](06-data-model.md) 第 3.2 节）。

### ADR-008 出站事件表（提议）

- **背景**：参考工程是“事务提交后入队 + 补偿扫描”。
- **决定**：事务内写出站事件；任务进程中继到队列；另有“事件 × 订阅者”的投递表，重试由数据库驱动、有上限，死信可在后台重投。需要即时结果的动作在提交后由 API 进程内联尝试一次。
- **理由**：扣减积分、付款入账之后的动作（生成工单、通知、授权书）不能丢。
- **代价**：多两张表与一个中继循环。

### ADR-009 三种时间机制（提议）

- **决定**：账务时钟用领域表的到期列加幂等推进函数；会改状态的时限用定时器表；纯提醒由通知模块从业务表当前到期日派生；周期任务登记为数据库定时器行。
- **理由**：到期日会被延长、升级、退款、改期移动，为它再维护一份定时器就是两份真相。
- **放弃**：BullMQ 延迟任务与调度器（Redis 清空即丢）；节点内的 cron。

### ADR-010 统一状态迁移函数与状态历史（提议）

- **决定**：所有状态变更经一个迁移函数：按全局顺序加锁、查状态迁移表、校验守卫、写状态历史、发事件。状态迁移表是数据，放在 `packages/shared`。
- **放弃**：状态机库、工作流引擎。
- **理由**：状态迁移表可直接评审、可穷举测试；状态历史支撑交付时长等指标。

### ADR-011 主键用 UUID v7（提议）

- **决定**：业务表主键为应用生成的 UUID v7；只增的流水与日志另带自增序号；对人展示用业务单号。
- **理由**：标识出现在接口与小程序路径中；避免 BigInt 在 JSON 与 TypeScript 中的转换；按时间有序、索引友好。
- **放弃**：`bigint` 自增（多数草案的写法）。
- **代价**：主键与索引比 `bigint` 多占一倍空间，在本项目的数据量下可忽略；须在第一条数据库迁移脚本之前回写草案。

### ADR-012 全局加锁顺序与事务重试（提议）

- **决定**：全系统一份加锁顺序表；一个事务只锁一个主体的计费账户；事务包装对死锁与锁超时有限次重试。
- **理由**：订购、取消、开工、付款入账会并发触碰相同的行。
- **代价**：新增需要加锁的表时须先登记顺序。

### ADR-013 幂等键（提议）

- **决定**：涉及钱、积分、状态的写接口要求客户端幂等键，幂等记录与业务写同事务；账本操作另有全表唯一的操作键。

## 账务与支付

### ADR-014 积分账本按批次建模（提议）

- **背景**：两类积分、套餐积分期末清零、先扣快到期的、冻结跨周期、退回要回到原来源、报表要按来源折算预收款。
- **决定**：账户 + 批次 + 冻结单（含批次分摊）+ 只增流水；每主体一行账户作为行锁；余额是批次汇总的缓存。
- **放弃**：只存两个余额数字加流水（无法正确退回与清零，无法出积分负债报表）。

### ADR-015 折算价值不在写路径上（提议）

- **决定**：流水只记数量，批次只记入账成本；预收款余额与收入确认金额由流水按“估值口径版本”回放生成，可重算。
- **理由**：财务口径（开票时点、套餐款是否全额计入积分价值）尚未确定，且可能变化。

### ADR-016 微信支付自研薄封装（提议）

- **决定**：用 Node 内置 crypto 与 fetch 实现预下单、验签、查单、关单、退款、账单；按公钥模式；用官方示例与验签工具做对照测试。
- **理由**：没有官方 Node SDK，官方不对社区 SDK 的质量负责；参考工程的微信能力同样是自研 Provider，写法可沿用。
- **放弃**：`wechatpay-node-v3`（自 2024-08 未更新）；`wechatpay-axios-plugin`（仍在维护，但会引入 axios 等依赖，而参考工程的协作规范禁用 axios）。
- **代价**：验签、解密与安全更新的维护责任自担，须用官方示例与验签工具做对照测试。

### ADR-017 购买入口策略与线下签约退路（提议）

- **背景**：“会员套餐 + 积分充值”可能被判为虚拟支付；被判定后小程序内不能展示普通支付与对公入口。
- **决定**：服务端唯一的 `getPurchasePolicy` 输出三种模式；通知、订购、首页都调用它；V1.0 实现“后台代建付款单 + 对公确认”的线下签约退路，开关默认关闭；不实现也不预留虚拟支付渠道。
- **理由**：定性只能靠提审确认；线下签约是唯一不依赖发版与平台审核的收款路径。
- **代价**：所有带购买引导的文案都要走策略。

### ADR-018 付款单超时以关单结果为准（提议）

- **决定**：到点先查单，仍未支付才关单，以关单接口返回为准；收到款的付款单一律离开未完成状态；履约在保存点内，失败记“已支付 · 履约受阻”。
- **理由**：官方建议的顺序；避免“回调晚于取消”成为日常差异。

### ADR-019 统一审批单（提议）

- **决定**：一张单级的 `approval_request` 记录审批结论；领域单据保存内容与执行状态，一对一；每类一个执行入口；统一守卫保证审批人不是发起人；超级管理员兜底。
- **放弃**：可配置的多级审批链；每类单据各自实现审批（四份草案出现了三种做法）。PRD 的各类敏感操作都是一道审批；PRD 12.3 第 4 项原型里的“主管审批延长、积分入账另经财务审批”用两张单级审批单串联表达。

## 身份与安全

### ADR-020 不透明会话令牌，会话存 PostgreSQL（提议）

- **背景**：参考工程用 JWT 双令牌，禁用账号后令牌仍有效两小时。
- **决定**：商家、员工、下载页三类会话都是不透明令牌，会话行存数据库，每请求查库。
- **理由**：更换老板、移除店员、禁用员工须即时生效，且吊销要与状态变更同事务。
- **代价**：每请求多一到两次主键查询。

### ADR-021 后台登录用密码 + TOTP（已定，业务确认 2026-10-02）

- **决定**：第二因子为 TOTP；短信只发一次性激活码；企业微信扫码延后。
- **理由**：短信作第二因子强度弱，且使登录依赖短信通道与签名报备。
- **与原型不同**：原型为短信验证码；业务已确认改用 TOTP。

### ADR-022 两层租户与服务端字段裁剪（提议）

- **决定**：主体 → 门店 → 成员；门店上下文逐请求校验；店员不可见字段用按角色的响应 schema 在服务端剥离，并有回放测试。
- **放弃**：只在前端隐藏（会经接口泄漏）。

### ADR-023 后台权限 = 模块等级 + 权限点 + 数据范围（提议）

- **决定**：13 模块 × 4 级，按钮级权限点，数据范围折算为负责人集合并强制传入数据访问层；权限点注册表在契约包里只有一份；8 个预置角色，V1.0 不支持自定义角色。
- **放弃**：通用的资源级 RBAC 框架（对固定的 8 个角色过重）。

### ADR-024 审计日志只追加、与业务写同事务（提议）

- **决定**：单表不分区；数据库角色只有插入与查询权限，触发器拦截改删；在线保留不少于 36 个月。
- **延后**：摘要链等防篡改措施（是否需要取决于等保定级结论）。

### ADR-025 敏感字段加密与盲索引（提议）

- **决定**：手机号、统一社会信用代码、银行账号在应用层用 AES-256-GCM 加密，HMAC 盲索引用于查找，另存脱敏列；查看明文留痕并限频。
- **代价**：盲索引只支持精确查找，不能按前缀或模糊搜索；密钥轮换须重算全部密文与索引。

## 媒体与制作

### ADR-026 四个私有桶，直传，业务授权 + 现签短链（提议）

- **背景**：参考工程是公有读桶加随机路径，不满足签名播放、防盗链、签名下载的要求。
- **决定**：证照、素材、媒体、公开分发四个桶，只有公开分发桶挂 CDN；小文件预签名表单、大文件临时密钥分块直传；先进写入区，由任务进程校验后复制入库；下载有效期记在业务表，每次点击现签短时地址。
- **理由**：CDN 回源鉴权是桶级授权；S3 兼容的预签名最长 7 天，用临时密钥签名时还受临时密钥有效期限制（视签发方式为 2、12 或 36 小时），且长期签名不可撤销。

### ADR-027 电脑端下载页进入 V1.0（提议）

- **背景**：小程序单次下载上限 200MB，切后台 5 秒中断；成片包 2–5GB。
- **决定**：`apps/portal` 列入 V1.0：扫码登录、逐集与打包下载、发布清单、样片与广告预览、授权书验真页。
- **代价**：多一个前端应用与一个身份空间。

### ADR-028 小程序内视频由服务端开关控制，V1.0 不播放短剧预告片（已定，业务确认 2026-10-02）

- **背景**：涉及微短剧播放的小程序可能被要求申请“文娱 > 微短剧”类目；一旦通过该类目，只能播放平台过审链接，自托管视频都会播不出来。唯一的整改兜底是移除视频内容。
- **决定**：预告片、样片、广告三个播放开关，另有自动播放与全屏滑动流开关。V1.0 预告片开关默认关闭，商城与短剧详情用“海报 + 文字”；样片默认不在小程序内播放（存相册或电脑端预览）；商家自己的广告视频可在小程序内预览。
- **业务确认**：海报加文字在前期已能满足需求；日后启用预告片时默认点击播放，不自动播放。
- **与 PRD 不同**：PRD 6.5 的预告片模式、6.6 的详情页顶部预告片播放器不进 V1.0；两处的“自动播放”改为点击播放。

### ADR-029 预告片出两档 MP4（已定，业务确认 2026-10-02；V1.0 不启用）

- **决定**：480P、720P 两档 MP4 经 CDN 鉴权分发，端上按网络选档；HLS 多码率自适应待验证后作为增强。按 ADR-028，V1.0 小程序内不播放预告片，本决定在启用预告片时生效。
- **与 PRD 不同**：PRD 10.1 写“多码率自适应”；业务已确认接受两档 MP4。

### ADR-030 V1.0 不建合成管线，只引入隔离的媒体工具容器（提议）

- **决定**：成片在系统外制作后上传；“制作模型”是计价与标签；引入无网络、无密钥的 `mediatool` 容器做体检、抽封面、文档抽文本、AI 标识元数据的写入与回读。V1.1 的自动贴片用独立主机的合成进程。
- **理由**：PRD 与原型在 V1.0 没有任何系统内合成的功能点；AI 全片重制的成本约为一单收入的 2–15 倍（调研估算，未经一手核实）；每集提示标识是制作机构的法定义务，隐式标识的法定主体是生成合成服务提供者，本项目按从严口径一并写入（待法务确认）。
- **放弃**：V1.0 自建渲染队列；AI 全片重制。

### ADR-031 素材理解只用境内端点，人工复核为准（提议）

- **决定**：转写、识别、提炼经 Provider 接入境内服务，主备两家；任何一步失败不影响入库；用途、时效、可用性以交付经理的复核为准。
- **理由**：素材含门店与人像；参考工程生产走境外线路，合规待定。

## 平台与工程

### ADR-032 腾讯云单云，双节点容器化，托管数据库（提议）

- **背景**：参考工程是阿里云单机、PM2、现场构建、容器内数据库、本机备份 14 天，达不到 99.9% 与 30 天备份。
- **决定**：腾讯云单地域；两台应用节点 + 一台预发；Docker Compose；持续集成构建镜像；托管 PostgreSQL 17 一主一备；托管 Redis（验证通过为前提，退路是每节点自建）。
- **放弃**：单机；Kubernetes；Serverless 容器；跨云。
- **代价**：每月比单机多约 800–1,000 元。

### ADR-033 任务进程用数据库租约做热备单活（提议）

- **决定**：两台节点各一个任务进程，数据库租约决定主备；所有循环按可多实例并行设计。
- **理由**：任务进程宕机时定时器、中继、对账都会停。

### ADR-034 预发环境完全独立（提议）

- **决定**：独立 AppID、独立商户号、独立 VPC 与数据库、独立桶；预发不持有任何生产资金凭据与生产发版凭据。
- **理由**：支付、退款、积分账务必须有真实环境可测；共用 AppID 会互相干扰。
- **代价**：多一套小程序认证、备案与商户号进件的费用和周期；申请不到独立商户号时须业务书面接受替代措施的风险。

### ADR-035 版本精确锁定且须发布满 7 天（提议）

- **决定**：全部依赖精确版本；锁定值为已发布满 7 天的最新补丁；关闭安装脚本；月度巡检。
- **理由**：今天 `typescript`、`prisma`、NutUI 的 `latest` 都指向不该安装的版本，pnpm、vitest 的新大版本也暂不跟进；2026-05 发生过波及图表生态的供应链投毒，而本项目持有支付密钥。
- **例外**：含安全修复而必须提前使用的版本，逐个登记豁免并在合并请求里说明，须两人确认。
- **代价**：常规补丁至少晚 7 天用上；每月要花半天做依赖巡检。

### ADR-036 运营后台用 React 19 + Ant Design 6 + 自建构件（提议）

- **决定**：独立单页应用，与接口同源部署；不引 ProComponents 与 Refine。
- **理由**：两者都没有支持 antd 6 的稳定版；antd 5 的维护期即将结束；56 个画板可归成 7 种骨架。
- **代价**：约 20 个业务构件（筛选表格页、队列工作台、确认与驳回弹层等）要自己写和维护，前期工作量高于直接用现成的中后台套件。

### ADR-037 可观测不建指标栈（提议）

- **决定**：结构化日志进云日志；错误监控走 Sentry 协议并经自有域名转发；任务进程每分钟跑 SQL 探针并告警到企业微信；外部拨测兜底；健康端点由 API 自查，不依赖任务进程与 Redis。
- **放弃**：Prometheus 与 Grafana。
- **代价**：没有历史指标曲线与趋势图，排查性能问题靠日志与数据库统计；规模上来后需要补指标栈。

### ADR-038 导出只走服务端异步任务（提议）

- **决定**：导出一律异步，服务端生成 xlsx 或 csv；按发起人在执行时刻的权限与数据范围重查；文件保留 24 小时；前端不引 Excel 库。
- **理由**：npm 上的 Excel 库一个有高危漏洞、一个已停更；导出涉及脱敏与留痕。

### ADR-039 外部能力一律走 Provider，未配置不崩溃（提议）

- **决定**：wechat、wechatPay、sms、storage、media、ocr、asr、llm、wecom、esign、invoice、mail 十二个接口，各有“未配置”实现与测试替身。
- **理由**：沿用参考工程；平台账号开通周期长，开发不能被它阻塞。
- **例外**：电子签 Provider 在生产不允许静默降级为图片章，须显式开关与法务书面同意。

## 2026-10-02 业务答复后新增

### ADR-040 商家端登录：手机号为账号，用微信的手机号验证组件（提议；目标已获业务确认）

- **背景**：业务要求登录文案去掉“微信”字样，并且同一个账号可以在不同的微信上登录，只要能收到该手机号的短信验证码。
- **决定**：账号以手机号唯一，一个账号可挂多个微信身份。常规登录用手机号快速验证组件；新微信首次登录已有账号、换绑手机号时用实时验证组件。自建“手机号 + 短信验证码”登录列为备选，V1.0 默认不做。
- **理由**：快速验证组件允许用户自主添加微信绑定号码以外的号码并由微信验证，业务目标不需要平台自己发短信就能实现；运营规范 12.6.1 要求有账号体系时必须提供微信授权登录，自建短信登录只能并存、不能替代；自建短信每条约 0.045–0.05 元，高于组件的 0.03 元，且依赖签名报备，审核时还要另备测试账号通道。
- **放弃**：只提供自建短信验证码登录（违反 12.6.1）；所有登录都用实时验证组件（每次多 0.01 元，且老用户本可静默登录）。
- **代价**：组件里“添加其他号码”的具体交互与可添加数量没有核到一手原文，须真机验证；每次验证有费用，体验额度用完即不可用，须预购资源包并做余量告警。
- **待定**：真机验证不通过时，增加自建短信验证码登录作为第二种方式。

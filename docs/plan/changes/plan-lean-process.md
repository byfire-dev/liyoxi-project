# 协作流程精简：不再有六类要业主先说“同意”，复审一轮一份，文书缩短

| 项 | 内容 |
| --- | --- |
| 改了什么 | 原来（[上一条](plan-merge-by-dispatch-session.md)）：调度会话合并，六类 PR 要业主先说“同意”；复审的提交就是合并的提交，其后改了内容要补一轮复审；复审全文连同派工的任务原文都贴，逐类写属不属于六类；PR 模板十节，验收逐条给证据链接。现在：① 三项齐了调度会话就合并：`required` 在已与 main 同步的提交上为绿、有一轮独立复审且没有未处理的阻断项、PR 不是草稿。② 不再有六类。甲类、看样、门禁放松、计划小改、体量超限、任务书偏差、边界情况都由调度会话定并合并，合并评论里用几句话列出留给业主事后看的事项。③ 仍然先问业主的只有：动服务器的每一步、部署与发布、用到真实密钥或账号、花钱、删数据或别的不可逆操作、改 main 的保护规则与必过检查的名单。④ 复审每个 PR 一轮、一份（甲类也是），限时，只找真问题（bug、违反硬性规则、验收核心没做到、放松门禁而理由站不住）；阻断项修完由 CI 把关，不再补复审。⑤ 要看样的包先合并，业主看了再提意见、另开 PR 改；通用构件在业主提过意见并改完后冻结。⑥ 放松类门禁改动照旧单独成 PR、打 `gate-change`，平台上的分类检查照旧，但不用等业主。⑦ PR 描述各节几句话，证据就是 CI 运行，复审模板缩成半页。作者会话照旧不推送、不开 PR、不合并；拿不准的、须小幅超出任务书范围的，照最贴近 01–07 的做法做并记一句，不停下来等人。改的文件：[README.md](../README.md) 第 3.5 节整节重写，第 3.1、3.2、3.4 节与第 2 节各几处；`CLAUDE.md` 第 1、2、3、7、8、11 节行内改；[开发计划](../../08-development-plan.md) 文首“计划变更”行、前提 ①、E15 行、Q12 行、第 5.3 节六行、第 9.3 节一行、第 10.1 节一行、第 11 节第 9、10 项，修订记录加一行；[复审模板](../templates/review.md)与 `.github/pull_request_template.md` 换成精简版；[owner-checklist.md](../owner-checklist.md) 登记原话并改相关各行；[tasks/README.md](../tasks/README.md)、`apps/admin/README.md` 各一句。没有动的：`CLAUDE.md` 第 6 节硬性规则（规则 27 的字面也没有动，“看样确认”怎么算写在 README 第 3.5 节第 6 项）；密钥与 `.env` 的规则；main 的保护规则；计划 第 13 节（大改仍须业主确认）与 Q9；里程碑范围、退出条件、包数、规模、级别、依赖 |
| 原因 | 业主 2026-10-05 在对话里的三句原话（照调度会话的转述记，前两句与 #24、#35 的合并评论对过）：“都按建议，#24同意”“#35复审过了就同意”“这个进度太慢了，你做了大量的没必要的确认和验证。接下来的大部分情况，你都无须让我确认。我是希望你能尽快把系统开发出来，这样我能尽快给你反馈。”**业主的话只有这三句。**上面 ①–⑦ 是调度会话照第三句归纳的，不是业主的原话；业主可以随时纠正，说一句就改。执笔的会话另补了两处、没有照归纳走的一处，都列在做这次改动的 PR 的描述里：第 3.5 节第 5 项末尾“要把这张清单改少，或放宽硬性规则、密钥规则、保护规则，也先问”半句（归纳里没有；不补的话任何会话改一下文档就能把清单改没）；`CLAUDE.md` 第 2 节“任务书与 01–07 或 08”一行跟着第 3 节第 6 步对齐（任务点名的是第 1、3、7、8、11 节）；计划的大改（里程碑范围、退出条件、前提）仍须业主确认，没有改（归纳里只说到计划小改） |
| 影响的包 | 各包的依赖、顺序、规模、级别都不变。在途与之后的每个包：合并不再等业主；复审一轮一份；PR 描述与状态文件“偏差”简短写。已交付的任务书里写成合并前要业主过目、确认或亲手做的事不挡合并（能客观核对的由调度会话代核，其余挪到合并后），任务书是当时的记录，没有回改。W0-29 看样：不挡别的包合并，业主看了提意见，意见另开 PR 改 |
| 类别 | —（协作流程，不属拆并、顺序、估算、归属、留桩。改了计划 第 5.3 节的合并条件，PR 标 `plan-change`；照[上一条](plan-merge-by-dispatch-session.md)的先例在本目录记一条备查） |
| PR | 调度会话开 PR 后填编号 |

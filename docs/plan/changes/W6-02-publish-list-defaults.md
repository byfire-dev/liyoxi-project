## 查实的问题

剧名请求按 Unicode code point 限制 1–20 字，发布清单保存的话题按 UTF-16 长度限制 1–20，最多 10 项。因此 11 个 emoji 的合法剧名可进入首次预填，却生成不能原样保存的话题。题材编码没有 10 项上限，题材名直接映射也可能超话题数量，或去 `#`、去空白后重复。

合集名超过 60 的情况属于历史数据或超长快照的防御边界：正常 20 code point 剧名加合法集数后缀不会超过 60。本修复不把它表述为已确认的正常业务入口缺陷。

## 修复边界

仅在清单尚不存在时生成安全默认值。题材名按快照编码顺序处理，用现有去前导 `#` 与 trim 规则得到稳定值，按原保存 schema 的 UTF-16 长度最多保留 20，不拆代理对；截取后去空、去重，最多 10 项。无有效题材才回退同规则处理的剧名，连剧名也无有效话题时保持空数组，由原完整性规则提示待完善，不编造标签。

合集名仅限制生成的剧名部分，在 60 单位内保留完整集数后缀；简介沿原 200 单位上限同样保留完整字符。已有清单的提前返回不变，包括已经保存的用户内容及历史未保存的生成值。GET 不修补数据，手动 PUT/导入不截断，字段校验、乐观锁和原错误路径不变。历史问题仍由有权用户显式纠正并保存。

## 验收与移交

新增纯测试覆盖正常值、20/21 单位及代理对边界、规范化与截取后重复、多题材限量、无有效题材回退、合集后缀与简介边界。新增真库测试通过实际 prefill/get/replace 验证合法 emoji 输入和多题材默认值可原样提交保存、GET 前后零内容/审计/事件变化、重进不写已保存及历史未保存内容。真库准备沿既有内容编辑测试的历史 delivering 输入，不宣称覆盖完整媒体生产或外部发布链。

首轮真库验证发现新测试在下单后更新不可变 `drama_snapshot`，被真实数据库触发器拒绝。修正只涉及测试准备：既有 delivery harness 的 `order` 末尾增加可选已存在剧目 ID，先读取该剧目的真实资料，在订单项 INSERT 时冻结快照；原四参数调用保持原行为。新测试先经已有公开工厂创建合法剧目资料，再创建订单，不禁用触发器，不修改冻结契约或生产 writer。

本地验证由调度以单 worker、文件串行执行：新增两文件、原清单“预填 N 行且重进保留”目标及既有导入解析目标，再执行 services 类型与定点格式/lint；不增加原时限或并发。本地6项纯测试、修正准备后的3项真库测试、原预填目标1项及导入解析21项均通过；services类型、格式/lint、5020模块分层及台账检查通过。唯一独立静态复审无新增阻断，已知快照准备失败修复后由原3项真库测试验证；不追加第二轮复审。完整CI与实际合并由调度后续记录。本记录不改变 W6-02 状态，也不代表 W6-08 页面验收、外部验收或 M6 退出。

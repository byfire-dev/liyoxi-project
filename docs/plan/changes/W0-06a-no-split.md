# W0-06a 体量超过甲类一个 PR 的上限，业主同意不拆

| 项 | 内容 |
| --- | --- |
| 改了什么 | 计划正文没有改。[开发计划](../../08-development-plan.md) 第 5.3 节“粒度”行原样：甲类一个 PR 只含一个机制、非生成非测试代码约 600 行，超过即拆 a、b，并在本目录记一条。W0-06a（角色与授权迁移）超过了这个上限而不拆：仍是一个工作包、一个 PR、一份状态文件，不新建别的包（已排定的 W0-06b 是结构快照，与这里无关）。实际行数（第二轮修订之后；总行数 / 去掉空行与整行注释；测试、反例、文档不计）：授权迁移 `packages/db/prisma/migrations/20261005060000_grants/migration.sql` 165 / 107，核对脚本 `infra/ci/db-verify-grants.mjs` 153 / 110，它的判定规则 `infra/ci/db-grants-rules.mjs` 559 / 476，根 `package.json` 的两个脚本 2 / 2，四处共 879 / 695。两份手写的数据另列：期望的授权 `packages/db/src/grants.expected.json` 217 / 217，下限清单 `infra/ci/grants-floor.txt` 48 / 31。两种算法：不算这两份数据是 879 / 695 行；连它们一起算是 1,144 / 943 行（只连期望数据是 1,096 / 912 行）。两种算法都超过约 600 行。包数、依赖、顺序、规模、级别都不变 |
| 原因 | 业主 2026-10-05 定。这句话是调度会话转述的，原话：“都按建议，#24同意”；它答的是调度会话列给业主的一张表，表里“体量”一行的建议是“算超，但不拆，记一条计划变更”。起因：第二轮复审（b 份）把体量记为阻断项。那时核对脚本 391 行，四处手写代码 558 / 443 行，在上限之内；连期望数据 215 行是 773 / 658 行，超过上限。期望数据是第一轮修订时从测试文件里搬出来的清单，作者没有算它；复审判它该算：它是手写的，不是测试的核对脚本靠它才能跑。拆不拆不是改代码能定的。第二轮修订又长了一截：核对脚本由 391 行长到两个文件共 712 行，新增下限清单 48 行，所以现在不算两份数据也超过上限。长出来的是两轮复审点到、合并之后再改就算“放松”的几处：成员、库的连接权、视图等别的关系、属主、缺省授权的核对，开头核对服务器版本，对写明库名的已部署的库单独跑，“请人过目”的条目写明角色、对象与权限，下限清单的解析与核对。复审给过的拆法：a 包是迁移、期望数据、权限测试、ADR、分组文档；b 包是核对脚本、它的用例与反例、两个根脚本，任务书的验收第 10 条跟 b 走。照这个拆法，b 现在是 762 行（核对脚本两个文件、下限清单、两个根脚本），自己仍超过上限 |
| 影响的包 | W0-06a：体量一事不再挡着；任务书 第 9 节“超过可评审体量即拆 a、b”一条按业主的决定不执行，验收十条不变；评审级别仍是甲，合并前业主看权限测试的输出与 ADR-045（任务书 第 8 节），并指着 PR 说“同意”。阻断项是否解除由下一轮复审引业主的话写明。下游（W0-06b、W0-21）：不受影响，交付的内容没有变，不用等第二个 PR。其余甲类包：计划 第 5.3 节的上限没有改，照旧按它执行。业主那句话里另提到的 #24 是另一个 PR（W0-28），不在本条范围；同一张表里与本包有关的另三行（同意 PR #32、认“另起核对脚本用后置钩子接上”的做法、加受门禁口径管的下限清单）记在 W0-06a 的状态文件里，不属于计划变更 |

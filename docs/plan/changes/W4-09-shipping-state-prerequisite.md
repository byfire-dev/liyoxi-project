## 1. 授权与边界

调度会话按业主授权，将发货未知结果的持久化单独交付为结构前置；基线为 `b04a5f8b`。本片只声明专用字段、枚举、行内约束及读兼容，不安装 writer、订阅或 job，不启用 `billing.payment.shippingReport`，不调用真实微信发货或支付。系统退款结构前置及旧人工退款语义不在本片改动范围。

现有 `payment_txn.applied_at/recon_state/query_count`、付款单履约快照、纸票寄出时间与通用投递/幂等记录均各有用途，不能承载发货是否被微信受理的永久业务事实；尤其通用幂等记录会在24小时后清理。

## 2. 最小结构

在 `payment_txn` 原行追加六个可空、无默认值列：`shipping_report_state/appid/mchid/item_desc/upload_time/confirmed_at`。原有主键、外键、索引与锁顺序不变；旧行及旧写者自然保留六列全空。已有表级授权覆盖新增列，不新增角色权限。

- `state=NULL`：从未认领，六列必须全空。
- `unknown`：已固化拟发送意图，但不能证明微信是否受理；包括写入意图后、调用前崩溃。必须先提交该状态，才允许事务外首次 POST。
- `not_accepted`：只有 Provider 明确返回 `acceptance=not_accepted` 才可记录；后继写者按原有界退避重新认领。
- `confirmed`：已收到可信成功响应，或查询完整匹配原收款与固化发货意图；必须记录真实观察时刻。

三个新增 CHECK 分别限定枚举、完整意图及成功微信入账资格、确认时刻。认领必须有主体、付款单、入账时间、渠道流水号、实收额与实际渠道付款身份；AppID沿现有微信配置格式，商户号沿现有支付配置格式，描述为非空且最多120个Unicode字符。约束不承诺跨表付款单反向关联或 AppID 配置一致，后继写者仍须校验。

## 3. 时间、身份与恢复交接

`upload_time` 保留注入 Clock 给出的毫秒精度，是固化报文意图时间，不冒称网络已发送。微信 query 返回的上传时间为秒，后继写者以 `floor(upload_time毫秒/1000)` 匹配；`confirmed_at` 则取注入 Clock 的真实观察值，不能用服务器秒级上传时间替代。观察时钟倒退至意图之前时保持 `unknown`，不得通过 `max` 或虚构偏移填补时间。

成功 query 不含 AppID；必须先校验此次调用所用 AppID 配置与固化 AppID 一致，再逐项匹配 `mchid/transactionId/outTradeNo/实际付款openid/实收金额`，以及虚拟物流类型、统一发货模式、完成标记、描述和秒级上传时间。字段缺失、查无发货、身份或金额不符、查询失败都不证明未受理，不允许据此再次 POST。

后继写者复用整段 SessionMutex 和短事务 `billing_order(290)→payment_txn(300)`，校验同主体、`paidPaymentTxnId` 反向关联及真实成功入账事实；不新增锁排名、不锁账户、不在事务内调用 Provider。状态结算须带原状态与固化身份/意图条件，防失锁后的迟到响应覆盖；`confirmed` 永不自动重报，通用幂等清理、投递换代、人工 redrive 均不得清除永久 `unknown`。这些跨调用迁移守卫属于后继 writer，本片 CHECK 仅验证单行形状，不伪称已经实现运行流程。

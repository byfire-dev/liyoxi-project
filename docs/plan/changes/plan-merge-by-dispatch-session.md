| 原因 | 业主 2026-10-05 在对话里的原话（原话分三行，这里接成一行，字没有改）：“我觉得合并PR的工作，也应该由你进行，避免：1、你在工作时，我需要持续守在旁边 2、我合并PR不及时，到时要反复变基同步”。“你”指调度会话。此前 Q12 按默认，批准 = 业主本人点合并；业主的结论与它不同，按计划 第 4.3、13 节先改文档里的写法。**业主的原话只有上面这一段**，定的是“合并 PR 由调度会话做”和两条理由。九条口径是调度会话据此拟的，不是业主的话。做这次改动的 PR 自己带 `plan-change`，又改了 `CLAUDE.md` 里命令以外的内容，口径也不是业主的原话，所以不适用口径第 3 条里的例外，须业主本人表态后才合并；业主表态并合并，即业主确认，业主要改就在那个 PR 上说。那个 PR 的独立复审第 1 轮指出：照九条的条文，有几类原本由业主先看的 PR 不再等业主。按复审的建议收紧了几处，写在第 3.5 节那张表的右栏，同样不是业主的话：合并条件里 `gate-classify` 任务自己也要为绿，复审的提交就是要合并的提交，阻断项由复审会话写明已解除，调度会话自己写的或加过提交的 PR 同样要独立复审；业主的“同意”要指到具体的 PR 或具体的事；属不属于“仍要业主本人表态”按改动的内容判，不按有没有贴标签判；第 3 条的例外只管带 `plan-change` 的 PR，每一处都要对到业主的原话，由独立复审核对；代核只限不需要密钥、真机、外部账号就能核的客观事项；另加三类仍要业主本人表态的（改 CI 工作流或 `infra/ci/` 下已有脚本的、甲类包的、别的依据文档写明须业主过目或确认的），取的是偏严的一头，要不要放宽待业主定。另有三处与原写法不同，照查实的事实写：① 次序。业主说这段话之后、这条变更合并之前，调度会话已经按这段话合并了 [#23](https://github.com/byfire-dev/liyoxi-project/pull/23)（X-02）：CI 的 `required` 在已同步的提交上为绿，独立复审无阻断项，不带 `gate-change`、`plan-change`，合并前在 PR 上留了一条评论、引了业主的原话。“先改文档里的写法、再照着做”这一次没有守住，依据是业主在对话里的直接交代。#23 里“请业主定、请业主过目”的事没有等业主确认，调度会话另记了清单，下一次台账更新时记进业主清单第 4.1 节。② 合并方式。计划 第 5.3 节原写“压缩合并”，而 main 上 #1–#23 都是合并提交，没有一个是压缩合并；口径第 7 条写合并提交，文档按事实改。③ `agent-reviewed` 标签。原来的合并条件括注了这个标签；口径第 2 条的三项条件里没有它，第 6 条只说“照旧，开 PR 的会话不给自己的 PR 打”。已合并的 23 个 PR 里带这个标签的只有 #6、#7。“合并条件”行照口径写，不再括注标签；标签谁打、何时打（README 第 3.4 节、计划 第 5.3 节“复审”行、第 10.1 节）都没有动 |
| 影响的包 | 各包的依赖、顺序、规模、级别都不变。在途与之后的每个包：作者会话收尾照旧，不合并；合并不再等业主本人去点，仍要业主本人表态的几类除外（口径第 3 条）。任务书第 8 节“需要业主做的事”里“合并前”一行分两种：客观核对由调度会话代核，结果写在 PR 评论里（口径第 4 条）；要业主凭主观判断的（看样、归属确认等）仍等业主表态（口径第 3 条）。归哪一种照第 4 条的右栏：代核只限不需要密钥、真机、外部账号就能核的客观事项，拿不准的归主观；甲类包的“逐项看证据”（W0-07、13、14、15、16、17、20、23 与 X-04 的任务书这样写）在业主另有说法前按要业主表态处理；合并前要业主亲手做的事（X-01 带密钥、用真机的实测）照旧等业主做完。已交付的 27 份任务书与 [tasks/README.md](../tasks/README.md) 里同新口径不一致的句子没有回改（任务书是当时的记录，也不在那个 PR 的范围里），清单列在那个 PR 的描述里。W0-31、W1-23 的验收“L 与甲类包的任务书业主已过目”：合并不再等于业主已过目（口径第 5 条），这一条怎么取证没有定，已在那个 PR 的描述里提请业主定。合流包：`mN-done` 仍由业主或调度会话打在 main 的合并提交上。关键路径不变 |

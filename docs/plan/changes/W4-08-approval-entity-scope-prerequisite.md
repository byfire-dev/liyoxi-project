| 项 | 内容 |
| --- | --- |
| 改了什么 | `points_adjust`、`subscription_extend` 的审批决定与读队列统一按主体数据范围；其余类型的处理人、门店、主体优先级保持 |
| 原因 | a07 第 2.0 节规定调整单、延长单按主体授权；积分调整的可选 `storeId` 必须保存为发起上下文，旧范围逻辑却优先使用该门店，导致主体内另一门店可见时仍读不到、决定不了 |
| 影响的包 | W4-08 在此前置实际合入后消费；不改领域登记、接口契约、审批状态机、DDL、内核、锁序或门禁 |
| 类别 | 顺序、范围；调度批准独立窄前置 |
| PR | — |

范围目标仅在 approval 仓储内部选择，单条与批量共用。两类主体审批缺主体时拒绝；保留门店上下文，不伪造全部范围，也不借角色队列放行。领域接口仍须按自身主体范围取对象，发起人自读、自审禁止、同组主管及代撤规则保持。

测试使用既有样例审批登记与真实数据库，覆盖同主体其他门店的可见性、列表/计数/详情/待办一致、通过/驳回/代撤与跨主体拒绝，并保留门店与处理人优先的反例。实际 W4-08 领域入账、真实员工与生产验证仍由原包承担。

本地定点验证：Node 24.20.0，单 worker；`scope.db.test.ts` 新增 3 例通过，`approval-read.test.ts -t '主体范围贯通'` 新增 2 例通过；services、api 类型检查与三个 TS 文件的 ESLint 通过。首轮 HTTP 因命令漏传 `APP_ENV=test` 未进入业务链，补上后仅重跑该两例通过；失败会话库按精确 session 清理。数据模型仅补一行授权语义，不改变表、列、枚举或约束；未重跑整套框架与迁移校验。

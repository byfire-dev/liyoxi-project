## 1. 已核事实与授权边界

基线为 actual main `2fa686c087ebbe4e572ffb9ddb5c1139805cbc98`。原 W4-17 分支保留，本片使用独立 `codex/w4-09-system-refund-schema`。调度已根据 W4-09“支付后10分钟自动发起退款”的原目标明确授权本片可逆实现；本页记录具体边界，不把服务器、真实资金、真实账号或部署授权混入其中。

`refund_request.approval_request_id` 为非空唯一外键，继续保留。原 `customer_service`、`exception` 来源及 `plan_refund` 人工审批不改：旧来源、规则/原因映射、原审批与执行人约束、三人分离、余额/权益/发票事实仍生效。现有 approval 已能记录真实 system 提交和决定，新增的只是一个准确区分用途的类型，不新增通用审批机制。

首版之后只写新迁移、现行 `packages/db/prisma/schema.prisma`、官方快照和正式字段文档；冻结的 `docs/data-model/schema.prisma`、`docs/data-model/constraints/`、旧迁移与首版拼接输入不修改。

## 2. 新来源与类型的精确语义

- `source = staging_probe` 只代表预发系统意图，必须成对引用 `kind = staging_pay_refund`；两个人工来源继续只引用 `plan_refund`。领域不变量按这两支精确核对，不将所有审批类型泛化为退款。
- 新审批类型仍是 `category = approval`，有执行步、单号前缀 `TK`、`dedupe_key = NULL`。对象仅为真实 `billing_order`，主体必填，门店不冒充主体范围；原退款申请在途唯一索引继续去重。旧类型的对象、大类、单号与去重条件逐项保留。
- 新类型只允许真实 `submit_actor_type = system`、提交人/客户端/发起员工及发起组为空；通过或驳回必须真实 `is_decided_by_system = true` 且审批员工为空。其它类型的现有系统/员工规则不变，不造“系统财务员工”。
- `is_executed_by_system boolean NOT NULL DEFAULT false` 是明确执行事实。原两种来源始终为 false，执行中/完成仍须真实执行员工、执行路由与时间。新来源执行员工为空，只有确实建立执行意图后才置系统执行位，并保留实际执行时刻；不能从 NULL 人员反推系统执行。
- 新来源在数据库可表达的部分限定为 `window` 规则、非 override、金额整数1..100分及仅 `wechat_original`（尚未执行时路由可空）。真实已付款、可退余额、未消费权益、红票/发票和审批主体一致性沿原服务复核，不通过结构片制造付款或退款事实。

跨表的来源/类型/主体关联由保留的审批外键、领域公口与既有 `payment.I11` 精确核对；不为跨表 CHECK 引入新触发器或新审批框架。

## 3. 实施分界与只读兼容

本片只声明结构/契约并让已有读侧能够准确呈现新来源与系统执行标记。退款详情继续保留原 `executedBy` 员工字段，新系统标记显式返回；新来源不获得原人工通过、执行、线下退回、重试等按钮能力。原人工来源的 permissions、scope、step-up、confirm 和 actions 不放宽。

通用审批仅在已有执行种类表和 `TK` 编号地图追加新键，不登记生产 kind handler、job、HTTP 或伪业务入口。`approval.I1` 仍按实际登记的领域类型工作；后继 W4-09 在 stg 真正登记新类型后，才消费对应领域关系。

现 `billing/refund/binding.ts` 与 `billing/invoices/refund.ts` 有 `plan_refund` 专属写侧守卫。它们不在本片凭空扩展；后继真实系统写者必须在登记时按新 kind+source 精确配对消费，并继续复用原审批/Saga/发票与权益回收，不绕过原路退款。金额、预发单前缀/白名单、满10分钟、APP_ENV=stg 三保护及 prod registry/handler 双侧不存在，均由后继运行实现和反例验收，不能把本结构片当作已经自动退款。

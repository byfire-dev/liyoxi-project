# 本机开发验证与性能观察

2026-10-08 业主说明开发设备为配置较低的 MacBook Air，要求控制性能测试的并发、数据量和评估标准。本机核对为 16 GiB 内存，Docker 可用约 8 GiB；这些是开发环境条件，不能作为预发容量结论。

2026-10-13 业主进一步要求降低日常验证和测试量、加快开发。以下按改动风险选择验证范围；不把每个小片都当作整包重新验收。

## 日常功能验证

- 编辑、阅读和独立审查可并行。连库测试、构建及压测安排在互不重叠的运行窗口，避免多工作树同时争用 PostgreSQL、Docker 内存与 CPU。
- Vitest 目标集使用 `--maxWorkers=1 --no-file-parallelism`。已有用例的并发、种子、轮数、时限及断言不为提速而删改；用精确文件或测试名选择本片需要的用例。
- 默认只跑新增与受影响的测试，加最小关键旧回归；类型检查按受影响包执行。页面只验新增行为及相邻关键路径，不重复全部历史截图场景。无关全量检查不作为每片本机合流的默认步骤；CI 必过项仍按原配置运行。
- 新增竞争用例通常用两个业务客户端（各连接池 `max: 1`）、3–5 轮，验证锁序、事务结果或幂等；只有具体风险需要时才增加并发或轮数。已有专门的正式验收要求不以此替代。
- 代码收口后统一运行相关组合检查。通过后，只有新的代码修改、失败或未解决的问题需要再次验证时才重跑；修复先重跑失败项及受修复影响的相邻用例，不重复已通过且未受影响的整套检查。纯文档改动只核对内容、格式与涉及的登记，不跑业务测试。
- 各工作树沿用独立测试会话、库和 Redis 前缀，只清自己的资源。通过小批合法数据验证真实业务路径、边界、锁序和幂等，不以大量造数代替正确性测试。

例如，从仓库根目录运行一个 services 目标集：

```sh
pnpm exec vitest run --project services --maxWorkers=1 --no-file-parallelism packages/services/src/identity/phone.test.ts
```

## 本机性能观察

只有改动涉及性能风险或需要调查瓶颈时才进行本机性能观察。先按脚本已有的轻量档或自有隔离夹具观察单接口：并发从 1 开始，必要时加一组并发 2 对照；数据用能代表目标路径的最小样本，必要时增至约 100–200 个业务对象。具体数据结构和样本量须在运行结果中写明，不把此建议直接替换为任务书要求的数据规模。

记录代码版本、运行参数、数据量、预热与采样次数、总耗时、P50/P95、错误数及运行时的其他负载。小样本的 P95 只用于定位慢查询和比较同条件下的改动；需要稳定分位数时增加采样，优先增加时间而非瞬间并发。

一次只运行一个性能进程，不与构建或其他连库目标集重叠。本机观察结束后释放自有资源。全量放大数据、持续高并发及已有 FULL 档安排在任务要求的预发或专用环境；不能在开发机后台反复尝试直到偶然通过。

## 结论口径

| 验证 | 可以说明什么 |
| --- | --- |
| 原判据下通过的功能、并发和不变量测试 | 对应业务正确性通过 |
| 本机轻量性能观察 | 指定数据与负载下的测量结果、相同条件的改动对照 |
| 达到规定规模、环境和采样要求的正式性能验收 | 对应任务的容量与性能门槛结论 |

本机性能失败保留实际结果，先检查资源竞争、查询与执行计划，再决定是否需要修复或移至正式环境复测。不得仅凭设备配置判定业务正确性失败，也不得把降低数据量后的通过写为正式性能通过。既有 P95 门槛、退出条件、门禁、基线和测试断言继续按原任务执行；未完成的正式性能验收明确记为未验。

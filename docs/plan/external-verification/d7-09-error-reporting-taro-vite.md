| 验证什么 | 小程序错误上报库在 Taro Vite 构建下可用、转发可用、体积在预算内 |

| 结论 | `sentry-miniapp@1.20.4` 在 Taro 4.2.1 的 Vite 构建下能构建通过，但主包多出 157.4KB，超过 80KB 的预算（D7 第 4.2 节）。按退路换成自研上报器（`apps/weapp/src/lib/errors.ts`）：同样的钩子收集错误，拼成 Sentry 信封发给 `m.clientError.create`；`sentry-miniapp` 没有装进依赖。转发是否可用没有验：转发接口还没落地。细节见下面“做法与数字” |
| 证据 | 体积数字是 W0-27a 会话在本机量的，见下表；自研上报器的用例在 `apps/weapp/src/lib/errors.test.ts`，W0-27a 的 PR 上 CI 运行的 `verify` 任务“小程序单测”一步跑它，“构建”一步出带上报器的包并过体积门禁。PR 与运行的链接见 [状态文件](../status/W0-27a.md) 的 PR 栏 |
| 关闭日期 | 2026-10-05 |

## 做法与数字

| 项 | 内容 |
| --- | --- |
| 怎么量的 | 同一份工程骨架（四个占位页、NutUI 的 7 个组件样式，还没有请求层）出两次生产构建：一次不引上报库；一次在启动时 `import * as Sentry from "sentry-miniapp"` 并调 `Sentry.init`（带 `dsn`、`tunnel`、`release`、`environment`、`beforeSend`）。体积取 `dist/` 下全部文件的字节数 |
| 能不能构建 | 能。Taro 4.2.1（Vite 4.5.14）出小程序包没有报错，库被打进 `vendors.js` |
| 体积 | 不引：349,624 字节。引了：510,817 字节，其中 `vendors.js` 161.0KB。多出 161,193 字节，即 157.4KB，是预算 80KB 的近两倍 |
| 结论 | 超预算，按 D7 第 10.6 节第 9 项与任务书 第 11 节第 3 项换自研上报器，不装 `sentry-miniapp` |
| 自研上报器 | `apps/weapp/src/lib/errors.ts`。收集：全局错误、未处理的拒绝、页面不存在（启动时挂钩子），以及页面里主动报的（接口、支付、上传、下载、处理函数）。清洗：令牌、形如手机号与统一社会信用代码的字符串打码，用户只带 id，不带请求体。同一条错误一次会话只报一次，每分钟至多 10 条；上报失败不重试、不抛错。带上报器、请求层与另外三个封装之后，主包从 322.2KB 涨到 338.2KB，一共多 16.0KB。这一组与上面“体积”一行不是在同一次依赖安装上量的（上面那组在整理依赖之前，基线不同），两组各自的差值成立，基线之间不能互相比 |
| 什么时候发 | 构建时给了 `WEAPP_SENTRY_DSN`，且转发调用已接上（`apps/weapp/src/lib/server.ts` 的 `sendClientError`）才发；两样缺一样就不发请求。现在两样都没有 |
| 没验的 | 转发是否可用：`POST /m/client-errors` 还没落地，信封的写法照 Sentry 的信封格式写，接口落地的那个包联调时核对。真机上钩子触发的实际情况：随 X-01 与 M2 的真机验证。`sentry-miniapp` 在真机上能不能跑：没有验，已不采用 |

业主事项的状态见 [业主清单](../owner-checklist.md)。填写规则见 [README](README.md)。

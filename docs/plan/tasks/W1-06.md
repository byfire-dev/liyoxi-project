## 1. 目标

- 各域的“申请—审批”有一套共用的做法：领域用例在自己的事务里调 `approval.submit`、`approve`、`reject`、`withdraw`，审批单的状态、状态历史、审计、事件由本模块写，领域的效果由该类型登记的回调在同一事务里做。
- 后台三个工作台（资质审核、账号核验、链接核验）与“我的待审批”的队列、计数、详情有接口可取；驳回弹层的原因单选有字典项可取（`admin.dictItem.list`，由 M2 提前到 M1，见第 11 节第 7 项）。
- 使用方：W1-08（`qualification`）、W1-14（`channel_account`、`launch_link`）；M2 起的账号变更，M4、M5 的退款、取消、积分调整、延长。

| 5 | 决定的守卫顺序：不是 `pending` → 409 `APPROVAL_NOT_PENDING`；审批人是发起人 → 403 `APPROVAL_SELF_FORBIDDEN`（超级管理员也不例外，库里另有 CHECK）；决定权限点、“仅主管”与发起人所在组、对象在数据范围内 → 403 `PERMISSION_DENIED`；通过时 `lockVersion` 不符 → 409 `VERSION_CONFLICT`；`revalidate` 认为前提已变 → 回滚并 409 `PRECONDITION_CHANGED`，审批单保持 `pending` | a03 第 1.1 节；D4 第 7.6 节 |

| 8 | 系统决定（免审批、同信用代码自动驳回）：`decided_by_staff_id` 为空、`is_decided_by_system = true`，不查权限与发起人 | 03 分组 第 2.12 节 |
| 9 | 在途去重：没有执行步的 8 类必填 `dedupe_key`（取法由登记给出），撞上部分唯一索引 → 409 `APPROVAL_ALREADY_PENDING`；有执行步的 4 类必为空 | 03 分组 第 3.2 节 |
| 10 | 执行与决定分开：有执行步的类型，审批单停在 `approved`，执行是领域用例的另一个事务；执行成功由领域调 `approval.recordExecuted` 发 `approval.executed`，执行失败本模块什么都不写 | 03 分组 第 2.12 节；x01 第 3.3 节 |
| 11 | 读接口不写库；可读的 `kind` = 调用方满足“查看所需模块等级”的类型，再套数据范围（发起人总能看到自己发起的；`channel_account` 对持 `publish.account.verify` 的人不套范围）。列表显式传不可读的 `kind` 回 403，计数静默略去，详情一律 404 | a01 第 2.10、3.36–3.38 节 |
| 12 | `countTodo` 是一个函数：列表 `tab=todo`、计数的 `todo`、`total.todo` 都用它，M7 的工作台与菜单角标也引它 | a01 第 3.36、3.37 节说明 |

- “只升锁版本”的入口（03 分组 第 2.12 节 `lock_version` 一行，A143）随 M2 的修正识别字段做。
- 不调 staff、tenant、identity 的函数（同层白名单里没有 approval → 它们）；不读 L3 的表。不改 `infra/ci/layers.json`、锁序常量、表结构。

## 10. 实现要点与顺序

1. 读已合并的 flow、audit、events、assembly 的 README 与 W1-01a 交的权限断言、数据范围函数，名字以代码为准。
2. `kinds.ts`：按键端口 `approval.kind` 与登记类型（见第 11 节第 1 项）；`register.ts` 声明端口、登记状态机的守卫与活动流描述。
3. `submit`：查登记 → `validate` → 生成摘要并按 `ApprovalSummary` 校验 → 取号（有单号的类型）→ 插行并迁移到 `pending` → 审计 → `approval.submitted`。

## 1. 目标

微信成功事实经唯一 applyPayment → fulfill 入账；查单、关单、回调与兜底扫描任意重放仍只履约一次。

要落地的接口（只有下表属于本包）：

| operationId | 方法与实际路径 |
| --- | --- |
| `m.paymentOrder.cancel` | POST `/m/payment-orders/{paymentOrderId}/cancel` |
| `m.paymentOrder.list` | GET `/m/payment-orders` |
| `m.paymentOrder.summary` | GET `/m/payment-orders/summary` |
| `m.paymentOrder.sync` | POST `/m/payment-orders/{paymentOrderId}/sync` |
| `admin.paymentOrder.list` | GET `/admin/payment-orders` |
| `admin.paymentOrder.summary` | GET `/admin/payment-orders/summary` |
| `admin.paymentTransaction.list` | GET `/admin/payment-transactions` |
| `admin.paymentTransaction.summary` | GET `/admin/payment-transactions/summary` |
| `hooks.wechatpay.transaction.notify` | POST `/hooks/wechatpay/transactions` |

- 当前actual M1公共applyPayment只完成对公，微信/无付款单仍INTERNAL；开工必须等W4-01实际最小微信适配。本包复用其公口，不重写或反向要求01等待02。
- 表：billing_order、payment_txn、payment_exception、webhook_event、timer、outbox_event；订阅周期/账本由既有 fulfill 公口写。
- recordChannelSuccess 的 T1 先提交可信渠道事实与收件行；提交后另一个短事务调用 applyPayment，订单 paid 与 fulfill 仍同 TX。渠道成功时间不充当账户时钟。
- 回调 T1 锁等待2s；T1失败按框架 T1′ 只存 failed 收件行并兜底重处理。内联入账 lock_timeout=1500ms/statement_timeout=3s，失败不丢已收渠道事实也不影响应答。
- 付款状态仅 pending_payment/pending_confirmation/paid/cancelled/refunded；payment_txn 仅 created/prepaid/succeeded/closed 的条件写，不写伪状态历史。
- 回调必须消费真实driver的verifyNotification/reopenResource判别结果（含来源/密钥版本/密文）；简单verifyAndDecryptNotification不够，公共Provider只扩该typed窄边界。
- 成功先落收件行再处理，验签/解密消费 W2-01 与 W4-01；错 appid/mchid 不入账且告警，不以 HTTP 200、前端支付成功或 NO_STATEMENT_EXIST 推断收款。
- 取消/到期先事务外查询和关单，再锁后复核结果；查得成功就入账，全部尝试真实 closed 才取消，处理中返回 cancelling。
- po.expire 属微信关单；保留已有 po.transfer_ttl 对公处理，不取消待财务确认凭证，不把到点当作已关单。
- 孤儿成功交易保持渠道唯一性，按真实回传关联/恢复事实开单或开差异；不得给未知主体虚造套餐与资格。差异解决由 W4-11 承接。
- 入账先 order290 → txn300 → account420；每 TX 一个主体。fulfill(tx,{billingOrderId,ctx}) 留在原事务内，复用公共 savepoint。
- 业务履约拒绝保存 paid/blocked 与差异；连接失败、重试异常、ACCOUNT_BUSY、KernelViolation 回滚整 TX，不吞成受阻成功。
- 同键重放不追加序号、ledger_operation、历史、事件、审计或差异；唯一入账位与 fulfill 操作键均保持。

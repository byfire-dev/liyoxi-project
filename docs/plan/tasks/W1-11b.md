## 1. 目标

- 老板在小程序里看钱包、选套餐、拿报价、建对公付款单、传回单；财务在后台看队列、确认到账或驳回。确认到账后套餐生效、积分到账（演示点 B 的“对公开通”一段）。
- 购买入口只有一个出处：`billing.getPurchasePolicy`，报价、建单、钱包、付款单详情都调它，端上不自己判断。
- 使用方：W1-12（页面）、W1-21（端到端脚本与演示种子汇总）。

M1 只做主路径的这一段，其余返回什么写死在这里：

| 事项 | M1 的做法 |
| --- | --- |
| 购买动作 | 只做 `subscribe`（从未开通或已过期）。已有生效或预约周期时，报价与建单返回 409 `STATE_NOT_ALLOWED`（续费、升级、降级在 M4）；`pointPackId` 建单同样拒绝 |
| 渠道 | 只有对公。微信渠道在策略里 `isEnabled = false`（没有配置驱动），选它返回 403 `CHANNEL_NOT_ALLOWED` |
| 报价 | 只读：不拿账户锁、不 `advance`。建单时在账户锁内（W1-10 的 `lockAccount`）重算并与 `expectAmountFen` 比对 |
| 建单 | m07 第 3.7 节的守卫与副作用做全：资质、策略、同内容复用、未完成单唯一、协议同意、取 `FK` 单号、记收款账户版本、登记 `po.transfer_ttl`、发事件、结果脱敏 |
| 凭证 | 状态迁移、替换、文件引用、`due_at` 与时限快照做全；不登记 `sla.breach`、不发起回单识别（都归 M4），`check_result` 留空 |
| 确认到账 | 建成功的对公收款交易后调 W1-11a 的 `applyPayment`。二人复核分支不做：受控配置里阈值非空且金额达到时返回 409 `STATE_NOT_ALLOWED` |
| 驳回 | 凭证置已驳回，付款单回到待支付（`proof_rejected`），`expires_at` 顺延一个有效期，按新键重新登记 `po.transfer_ttl` |
| 钱包 | `subscription`、`points` 取 W1-10 的 `getWalletView`；`topUp.canTopUp` 恒为 false（`blockReason` 照算，能加购的情形给 `not_offered`）；`usage` 调 `tenant.getQuotaUsage`（W1-03 交，m02 第 2.1 节的口径），本包不另算 |
| 开票相关字段 | `invoiceItemName` 为 null，`invoiceState` 一律 `not_eligible`，`activeInvoiceRequest` 为 null；后台详情的 `invoice` 给 `not_eligible`、`refundRequests` 给空数组（M4 做实） |
| 受控财务配置 | 只做种子要用的写侧：提议函数与 `finance_config_change` 的审批处理器（通过时写一次 `effective_at`）。接口与页面在 M4 |

要照做的规定：硬性规则 6、7、9、19、20、26；m07 第 2.0 节（主体范围、店员一律 403、金额整数分）；a07 第 2.0 节（数据范围、二次确认、再验证、加锁顺序：付款单 → 凭证 → 计费账户）。

## 9. 交付与收尾

- 一个工作包一个 PR（13 条，在乙类 20 条之内）。提交按“契约 → 纯函数 → 服务 → 接口与定时器 → 种子 → 测试”组织，PR 描述给阅读顺序。原估计非测试代码约 1,400 行；本次非测试非生成生产源码新增 3,382、删除 41、净增 3,341 行。调度按同一付款生命周期与乙类 13 条接口的范围确认保留一份 PR，估算修正记录在 `docs/plan/changes/W1-11b-purchase-estimate.md`。

- 先交付可读的中间成果；遇到阻塞即停，把原因写进状态文件并报告。不推送、不开 PR、不合并。

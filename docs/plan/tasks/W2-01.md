## 1. 目标

- 交付一个回调机制：验签后的收件、去重、处理与恢复统一使用现有 `WebhookEvent`；没有新增归 M2 的 operationId 或页面。
- 注册并实现两项 x01：订阅者 `security.onWebhookReceived`、循环 `webhook_reprocess`（展示名 webhook.reprocess）。所属域向框架提供验证、事件标识、载荷策略、协议应答和幂等处理函数；security 不导入上层域。
- 内联来源去重与业务处理同事务；收件箱来源先提交可信最小载荷，worker 独立处理，扫描恢复漏掉的唤醒。框架供 W2-21/22、M3 媒体和 M4 支付使用。

实现默认（本任务书定）：

- rawBody 为只读字节；验证成功后才解析/取事件标识。Provider 指定 inline/inbox、最小载荷、保留期和成功/失败应答，缺注册拒绝；有时间戳才执行偏差检查。
- 按实际 `uq_webhook_event_provider_event_id` 去重；持有收件行锁后调用注入的领域 handle，之后不反向锁其他收件行。不得用“行存在即成功”吞掉 failed/received。
- inbox 首次插入同事务发 `webhook.received`；唯一冲突不重复出站。订阅者与分钟扫描用同一幂等处理函数，按到期顺序每批50、SKIP LOCKED，逐条独立事务；技术状态不用 flow。
- 失败处理必须使领域写回滚，再独立保存受控错误摘要/attempts/nextAttemptAt；保留原 received/failed 可恢复。1/5/15分钟、1/6小时退避，达到8次 dead 并经告警端口上报。
- 支付内联失败后的 inbox 兜底是按来源显式选择的策略，允许后继 W4-02 登记；其他 inline 来源失败不静默落成功。支付保留180天的密文与 summary，不能照旧草案存解密明文/三年。
- 载荷到期只清准许清理的 payload 部分，保留行、summary、digest 与举证列，记录实际 purgedAt；security 经既有 `cleanups` 注册每日清理，由已落地的 `ops.retention` 调用，不新增独立扫描器或 x01。不能 DELETE、清表或改固定表结构。

## 5. 不做什么

- 不实现任何微信/短信/支付/媒体业务 hook 的 operationId；分别归 W2-21/22、W3-03、W4-02/10 和 M7。
- 不导入 billing/media/identity/notify 等上层模块；不在事务中调用 Provider。来源经组合根向公共框架注入，不改层级白名单。
- 不做告警独立事务隔离（W2-24 PR1）、运维列表/人工死信重置（W2-23）、真实平台地址配置或新的 DDL。
- 不提前将其他包的接口/x01 标已落地，不删旧规则或提高基线；unknown source、坏签名及失败事务不能应答成功。

## 6. 允许新增的依赖

无。使用 Node 标准库、现有 Provider 向量、Prisma/事务、fast-check 与 fake clock；需要新的协议库由所属 Provider 包提出独立允许项。

## 9. 交付与收尾

- 仅一个回调机制、一包一 PR，非测试非生成代码约600行上限；超限报告调度按机制内可独立阶段拆，不混入真实业务处理或告警 kernel 变更。
- 先交可读的框架与性质模型，再接 app/worker 薄壳和登记；安全模块 register/public出口由本包持有，后继来源只通过注册接口增量接入。
- 本包状态写实际完成；普通 hooks、独立复审、CI 全绿、同步 main 后调度合并。证据链接到运行，不提交另一份验收输出文档。

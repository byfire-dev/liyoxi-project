## 1. 目标

- 老板在小程序里看套餐与积分、选套餐、按服务端给的渠道走对公转账、传回单、看付款结果。
- 财务在后台“对公收款确认”里逐条核对并确认到账或驳回。
- 两端接上 W1-11b 的 13 条接口，演示点 B 的“对公开通套餐、积分到账”能在界面上走通（手验并入 W1-21）。

M1 的口径：

| 事项 | 做法 |
| --- | --- |
| 购买入口 | 价格、按钮、渠道、协议名、称呼全部取 `PurchasePolicy`（`isPriceShown`、`isPurchasePromptAllowed`、`channels`、`copy`）与报价里的 `policy`；页面不看平台、金额、版本号。策略不是 `in_app` 时不出现价格货架与任何购买按钮 |
| 钱包的入口 | 只做“开通套餐”（从未开通）与过期态的“续费”（服务端判为开通）。生效中的续费、升级、加购、积分明细、发票入口 M1 不渲染（留桩） |
| 套餐选择 | 只走开通：版本卡、周期（取 `cyclePrices`）、“本次变更”区与主按钮金额取报价。渠道按钮按 `channels` 里 `isEnabled` 的渲染；微信支付的调起不做（策略里它不可用，按钮自然不出现） |
| 对公弹层 | 建单后展示收款账户与转账备注（付款单号），可复制；选图经隐私封装，直传后提交凭证；提交按钮挂订阅点位 `transfer_submit`。幂等键在打开确认时生成一次；重放得到的账号为 null 时改调详情取 |
| 结果页 | 只显示服务端状态：待上传凭证、待财务确认、凭证被驳回（原因与重新上传）、已开通（周期与积分）、已收到付款正在处理、已取消。下拉刷新；不轮询、不调查单接口（M4） |
| 后台工作台 | 两个页签与计数（30 秒静默刷新）；详情含付款单信息、业务提示、凭证图、核对表（M1 为空表加“未配置识别”的说明）；确认：勾选、银行流水号、到账金额，收到 `BANK_SERIAL_DUPLICATE` 后才出付款行；驳回弹窗：原因单选加说明。处理完自动进入下一条 |
| 错误 | 只按错误符号名处理：`QUOTE_CHANGED` 用返回的新报价刷新并请用户再确认；`OPEN_ORDER_EXISTS` 引导去那张单的结果页；`VERSION_CONFLICT` 重新取详情；`STEP_UP_REQUIRED` 拉起再验证后用同一幂等键重试；其余走各端的统一处置 |

## 5. 不做什么

- 充值、积分明细、发票、合同四页；钱包里通向它们的入口；微信支付的调起与查单轮询：M4（G4-C）。

- 不写任何算钱的逻辑：金额、积分、能不能买、用哪个渠道都取接口的值（硬性规则 20）；不写色值与状态色，状态色取状态色调字典（硬性规则 24）。
- 不改契约、不改服务与接口；接口不够用即停下报告，不在页面里凑。
- 不改通用构件、页面骨架、请求层、菜单与页面清单里别人的行；不新增依赖。

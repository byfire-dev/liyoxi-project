## 5. 不做什么

- CI 不放 `prisma validate`、迁移、结构快照、`contract:check`、体积检查、不变量、Playwright。它们由交付的包“只增”一步（W0-05、W0-06b、W0-08、W0-10、W0-27a、W0-24、W0-28）。
- 不做模板库、按会话建库、Redis 分库、可拨时钟、故障注入，也不写共享 Compose 的用法说明（W0-05b）。
- 不建桶，不写 MinIO 驱动、Provider 的配置变量与启动时的生效状态打印（W0-19）。不做 `check-env` 命令与应用启动（W0-22、W0-23）。
- Compose 不起 server、gateway、mediatool（W1-22）；不做镜像构建、部署与预发（G2-D）。不做四个计数的报表（W0-30）；不做留桩、变更、外部验证三张汇总表（随 W0-30，`docs/plan/tasks/README.md` 第 5 节移交表第 9 行）。
- CI 里不放任何密钥；不建、不读 `.env`（计划 第 3 节 ⑦）。不改仓库设置与分支保护（业主做 E15 ③）。
- 不放松 W0-01、W0-02 立下的规则。

## 9. 交付与收尾

- 一个工作包一个 PR；超过可评审体量（计划 第 5.3 节“粒度”行）即拆成 a、b 两个可独立合并的 PR，并记一条计划变更。拆法见第 11 节第 11 项。
- PR 描述按 `.github/pull_request_template.md` 填全；借用清单写“源路径@f1361e3 → 目标路径”。
- 同 PR 更新 `docs/plan/status/W0-03.md`。
- 先交付可读的中间成果；遇到阻塞即停，把原因写进状态文件并报告。
- 不自行合并。

## 10. 实现要点与顺序

1. Compose：文件里写死 `name: liyoxi`，任何 worktree 里执行都指向同一套容器。服务名 `postgres`、`redis`、`minio`：PostgreSQL 17（库 `liyoxi`，端口 5442，不设 `TZ`，库内用 UTC）、`redis:7.4-alpine`（6389）、MinIO。三个服务都带健康检查与命名卷。`pnpm infra:up` 等到健康才返回。
2. `loadEnv(source = process.env)`：Zod 校验；报错逐条是“键名: 原因”，不带值；带一个“成组变量成对校验”的助手与用例。键与 `*_FILE` 的规则见第 11 节第 2、3 项。
3. `ci.yml`：`pull_request` 与推到 main 时触发；按分支分组并发，新提交取消在途。步骤顺序照计划 第 5.5 节“M0 起”一栏里本包有的那些。挂服务容器。权限最小：只有分类任务能写 PR 描述与标签。Node 版本读 `.nvmrc`。
4. 门禁改动分类：分类脚本与门禁文件清单从 main 检出后运行，用 main 上的版本判 PR 的差异；main 上还没有时（即本 PR）用 PR 里的。规则见第 11 节第 7 项。
5. `gates:selftest`：一个固定入口；一个反例一个文件，自动收集；断言“检查失败且原因对得上”。后续包只加文件，不改已有文件。
6. 时长统计、状态汇总、`.env.example` 核对。`nightly.yml`：定时与手动触发，另在改到它自己的 PR 上跑一次；Node 26；安装时关掉 `engine-strict`（根 `engines` 限在 24）；失败只告警。
7. `infra/ci/README.md`：怎么加一步检查、怎么加一个反例、怎么把新门禁文件登记进清单。回写文档，开 PR。

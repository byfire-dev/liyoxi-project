## 1. 目标

- 一次发布是一条可重跑的命令：编排脚本在 CI 里按固定顺序调节点步骤，哪一步失败就停在哪一步，并说清线上动没动。回滚是同一个脚本的另一个入口，顺序相反、有拒绝条件。
- 发布全程有持续探测的记录（中断时长与失败数）。预发是单机、不摘流，有短暂中断，不要求为 0，要求有数。
- 合并到 main 后自动上传预发体验版；部署后对预发库跑结构核对。
- 脚本有测试（真 bash 加桩命令），进 PR 必过检查：这是 M2 退出条件 ⑤ 里“发布编排与回滚脚本的测试通过”那一半。

## 5. 不做什么

- 不登录服务器，不接触发布密钥与任何密钥文件的内容；`deploy-stg.yml` 里用到的密文只按名字引用。
- 不做摘流、负载均衡健康状态查询、发布角色与临时凭证、远程命令通道：随引入负载均衡与建生产。脚本里给这几处留出明确的接缝（一个“节点列表”与一个“摘流前后”的钩子，预发时节点只有一个、钩子为空）。
- 不做生产发布任务与人工审批、`v*` 标签、送审上传与 `weapp-v*` 标签（后者在 W2-29）。
- 不改 `apps/`、`packages/` 的代码。api 没有“排空”状态时不在本包补：单机不摘流，用不上。
- 不做 `contract:compat` 与混跑冒烟（W2-28）；编排脚本的预检里给混跑冒烟的结论留一个输入位。

## 7. 验收

都在本机与 CI 上验。预发上的实跑写在第 8 节。

| # | 验收项 | 命令 | 判据 |
| --- | --- | --- | --- |
| 1 | 发布的顺序与失败即止 | `pnpm test`（`infra` 项目里 `infra/deploy/test/orchestrate.test.ts`） | 桩命令记下的调用顺序是：预检 → `pull` → `check-env` → `stage-assets` → `migrate` → `seed`（W2-25 交的播种一步，紧跟迁移） → `worker-swap` → `api-stop`、`api-start` → `status`、`verify-db` → 冒烟；任一步非 0 退出，后面的步骤一步都不调，摘要写明停在哪一步、线上动没动；同一个版本重跑一遍不出错 |
| 2 | 回滚 | 同上（`rollback.test.ts`） | 顺序是先 api 与 gateway、后 worker；不调 `migrate`、`seed`、`stage-assets`；发布记录标了“回滚不安全”时拒绝，带 `--force --reason` 才执行并把理由写进记录；目标镜像不在节点本地时先报错不动线上 |
| 3 | 预检 | 同上 | 有未恢复的 P1 时停下；`--override-p1 <告警编号> --reason` 越过并留记录；查不到告警表（探针与告警包还没合并）时跳过这一项并在摘要注明；冻结变量为真时停在预检 |
| 4 | 节点步骤 | `pnpm test`（`infra/deploy/test/node-step.test.ts`，真 bash 加桩命令） | 每个步骤重复执行结果相同；`stage-assets` 不覆盖已有文件；`worker-swap` 先发 SIGTERM、等退出（上限 60 秒）再起新的；`api-start` 等 `/readyz` 连续 3 次 200，超时即失败；`prune` 留最近 3 个版本的镜像；不认识的步骤名非 0 退出 |
| 5 | 演练：发布加回滚 | `pnpm stg:rehearse -- --release` | 在 W2-25 的演练环境上，用构建号不同的两份本地镜像做一次发布、一次回滚，全程开持续探测：发布后 `/health` 报的版本是新的，回滚后是旧的；新旧两版后台的静态资源在发布前后都取得到；探测报告给出中断时长与失败数 |
| 6 | 持续探测脚本 | `pnpm test`（`infra/ci/test/probe-during-deploy.test.ts`） | 对一个会中断几秒的假服务，报告的中断时长误差不超过 1 秒；入口页引用的资源有一个 404 即计为失败；报告是一份 JSON |
| 7 | 部署后的库核对 | 演练里的 `verify-db` | 授权核对通过；约束清单比对 0 差异；分区断言成立。在演练库上手工删一个索引后这一步变红 |
| 8 | 上传体验版 | `pnpm test`（`weapp-upload` 的用例，桩掉上传工具） | 产物的 sha256 与流水线记下的不一致即拒绝；机器人编号固定是 1；不打任何标签；桶没配置时以“跳过”结束、退出码 0、摘要注明 |
| 9 | 已有门禁 | `pnpm lint && pnpm format:check && pnpm typecheck && pnpm test && node infra/ci/classify-gate-changes.mjs --base origin/main` | 退出码 0；门禁改动只有只增类 |

每一步都是“业主执行，或业主在场逐步确认后由调度会话执行”；合并即部署的启用由业主同意一次（W2-25 第 8 节）。

| 时点 | 业主操作 | 判据 |
| --- | --- | --- |
| 开工前 | 无 | — |
| 合并前 | 无 | — |
| 合并后 | 让流水线在预发上做一次完整发布，全程开持续探测 | 发布成功；探测报告里有中断时长与失败数。报告链接记进 `d7-02-release-channel.md`，发布通道这一半关闭 |
| 合并后 | 在预发上做一次回滚演练（手动触发回滚工作流），再发布回来 | 回滚后 `/health` 的版本是上一个；演练记进运行手册第 6.4 节 |
| 合并后 | 预发的 `secure` 桶与上传密钥到位后，看一次合并后的自动上传 | 微信后台出现 1 号机器人的新开发版；“再次上传是否自动更新体验版”有结论，记进平台配置核对表 |

## 9. 交付与收尾

- 一个工作包一个 PR。提交顺序：节点步骤补全与测试 → 编排脚本与测试 → 回滚 → 持续探测 → 演练 → 工作流与文档。
- 体量：脚本约 700 行，测试另算。超过 800 行即拆：a = 节点步骤、编排、回滚与测试；b = 持续探测、上传体验版、库核对、工作流。并记一条计划变更。
- 调度于 2026-10-07 将原 b 续拆 b1（持续探测、全资源/DB核对、双版本机演练）与 b2（上传/工作流消费者，须等 W2-25b 实际合入）。a 已由 #100 实际合入；编号、任务范围与退出条件不变，只有 b2 收口才完成，见 [续拆](../changes/W2-26-b-split-b1-b2.md)。
- 同 PR 把 `docs/plan/status/W2-26.md` 写成“完成”，“没有验的”写明预发上还没有实跑。不推送、不开 PR、不合并。

## 10. 实现要点与默认（本任务书定）

| # | 要定的事 | 默认 |
| --- | --- | --- |
| 1 | 编排脚本怎么到节点上执行步骤 | 一个“通道”函数：预发实现是 `ssh <发布用户>@<节点> <步骤> <参数>`（节点上限定命令会把它交给 `node-step.sh`）；测试与演练实现是本机直接调。换通道只换这个函数 |
| 2 | 发布记录放哪 | CI 的运行摘要一份；节点上 `/opt/liyoxi/releases.log` 追加一行 JSON（版本、镜像摘要、各步耗时、结果、回滚是否安全）。回滚的目标缺省取这份记录里上一条成功的 |
| 3 | 单机上换 worker | 先停旧的再起新的，中间有几秒没有 worker；出站与定时器的真相在库里，起来后自己接上。mediatool 随 worker 一起换 |
| 4 | api 与 gateway 怎么重启 | 先 `api-stop`（SIGTERM，等在途请求至多 30 秒）再起新的 api，然后换 gateway；这段时间宿主机 nginx 回 502，持续探测记下的就是它 |
| 5 | 冒烟打哪里 | 三个预发域名的 `/healthz`、`/readyz`，从 `/health` 读版本号（它的整体状态要等探针与告警包合并后才断言），后台与下载页入口页及其资源；地址来自 `stg.env`，不写死 |
| 6 | 冻结 | 仓库变量 `STG_FREEZE` 为 `true` 时发布任务停在预检并说明。送审期间由业主打开（W2-29 的核对表里有这一步） |
| 7 | “回滚是否安全”谁来标 | 发布任务的一个输入，缺省“是”；打开过“写入新值”的开关后由发布人改成“否”。脚本只认这个标记，不自己判断 |

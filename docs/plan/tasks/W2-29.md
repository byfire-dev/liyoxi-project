## 1. 目标

- 业主手里有一份照着能做的真机清单第一版，M2 起每个里程碑在预发体验版上按它回归。
- 试提审（V2）前要核对的事有一张补全的表；送审那一次上传是一条手动触发的流水线：核对出包条件 → 打 `weapp-v*` 标签 → 用 2 号机器人上传。提交审核本身是业主在微信后台的人工步骤。
- 最小可提审版本不开分支：从 main 的某个提交出，功能靠服务端开关裁剪，指向预发。本包给出送审期间开关该是什么样的清单与一条只读的核对命令。

## 5. 不做什么

- 不提交审核、不设体验版、不改小程序后台的任何设置、不碰上传密钥：都是业主在微信后台的操作。
- 不改 `apps/weapp` 的页面与代码；不为送审另开分支、另做构建变体。缺的入口靠开关隐藏，开关不够用时列出来交给对应的代码包。
- 不把任何版本写进 `retired.json`：那是审核结束后的一个单独 PR（放松类，W2-28 第 4 节）。
- 不写测试账号的口令；审核用的账号由业主在提审时直接填进审核后台。
- 不做生产的上传通道（G2-E）。

## 8. 需要业主做的事

出包与提审的每一步都由业主执行；涉及服务器的由业主执行，或业主在场逐步确认后由调度会话执行。

| 时点 | 业主操作 | 判据 |
| --- | --- | --- |
| 开工前 | 无 | — |
| 合并前 | 无 | — |
| 合并后 | 过目真机清单第一版与提审核对表 | 有异议直接说，另开 PR 改 |
| 出包前 | 办完 E3、E5；在小程序后台核对类目、隐私保护指引、合法域名（预发三个域名与桶域名攒成一批加），现值记进平台配置核对表；定审核期间价目与自动退款怎么处理（默认见第 10 节第 4 项） | 提审核对表第 1–13 项无“待核” |
| 出包 | 打开冻结（仓库变量 `STG_FREEZE`）→ 手动触发 `weapp-review-upload.yml`，填提交与版本号 → 在微信后台把 2 号机器人的版本设为体验版 → 三台设备按真机清单回归（Wi-Fi 与 4G）→ 填审核说明、提交审核 | 标签在；清单 P0 全过并记进回归记录；提审往返记录加一行 |
| 审核期间 | 不做恢复导入、清空 Redis、放大数据；跑一次 `log-stats` 按 `X-Env-Version` 分组，看审核人员用的版本取到的是哪一种 | O4 有结论，记进 `adr041-review-env-version.md` |
| 审核结束 | 记结论与平台反馈；过审后不发布；让调度会话开 PR 把该标签登记进 `retired.json`；关掉冻结 | `v02-trial-submission.md` 有结论；购买入口的形态按结论定 |

## 9. 交付与收尾

- 一个工作包一个 PR。提交顺序：真机清单 → 提审核对表与审核说明 → 出包条件核对 → 送审上传工作流 → 开关与隐私核对 → 台账。
- 体量：文档约 250 行，脚本约 300 行，不拆。
- 同 PR 把 `docs/plan/status/W2-29.md` 写成“完成”；“没有验的”写明还没有出过包。不推送、不开 PR、不合并。

## 1. 目标

- 一笔成功的收款经唯一的入账函数 `applyPayment` 变成“已支付的付款单 + 生效的套餐周期 + 到账的积分”，重复调用只履约一次；履约失败只回滚保存点，钱的事实不丢，开一张差异单。
- 套餐付清后建周期与月度发放计划、发首月积分，发出 `billing.subscription.activated`（W1-17 靠它给门店分配交付经理）。
- 建主体时同事务建出计费账户，去掉 W1-03 的桩。使用方：W1-11b（对公确认到账）；M4 的微信回调、查单、对账、补单接同一个函数。

要照做的规定：

| # | 规定 | 出处 |
| --- | --- | --- |
| 1 | 入账一个事务，加锁顺序：付款单（290）→ 收款交易（300）→ 计费账户（420，在 `fulfill` 里，最后）。加锁后重读 | 08 分组 第 2.1、2.2 节；硬性规则 10 |
| 2 | 三层防重并存：`applied_at` 非空即返回（另有 `uq_payment_txn_applied`）；付款单按原状态条件迁移；账本操作键 `fulfill:billing_order:{id}` 与 `uq_subscription_term_source_billing_order_id` | D2 第 6.4 节 |
| 3 | 校验在函数内，任何入口绕不过：交易已成功；渠道实收 = 应付，否则付款单置已取消（`amount_mismatch`）并开差异单，交易保持未入账 | 03 第 1.3 节规则 3；D2 第 4.5 节 C1 |
| 4 | 付款单已是已支付或已退款又来一笔：开 `duplicate_receipt`；已取消后到账：开 `paid_after_cancel`，置 `has_open_exception` | D2 第 4.5 节 |
| 5 | 先置已支付（实收、收款时间、入账交易、入账时间与状态同一条语句，走 `flow.transition` 的随迁列），再调 `fulfill`，再写回履约状态、结果与说明 | 08 分组 第 2.1 节“履约子状态” |
| 6 | `fulfill`：拿账户锁（不 `advance`）→ 操作键已有即返回上次结果 → 保存点内 `advance`、按快照履约、自检、写 `ledger_operation` → 释放保存点。保存点里抛的错（业务错误、约束冲突、自检失败）回滚到保存点并返回 `blocked`；只有可重试的数据库错误（死锁、锁等待超时、序列化失败，用 kernel 的 `isRetryableDbError` 判）原样抛出，整个入账事务回滚，不算受阻 | D1 第 6.4 节；ADR-0046 |
| 7 | `blocked`：付款单仍是已支付，同事务开 `fulfillment_blocked` 差异单、置 `has_open_exception`，发 `billing_order.fulfillment_blocked` | 08 分组 第 2.1、2.6 节 |
| 8 | 套餐形态：没有生效周期就建 `active` 周期（起点 = 账本时钟，锚定日 = 当天几号，`origin` 取 `new` 或 `resume`）并立即发第 0 个月；已有生效周期就建 `scheduled` 周期接在链尾、沿用链尾锚定日，标 `queuedBehindActive`，不发首月。发放计划 N 行，`value_fen` 向下取整、尾差放最后一行 | D1 第 6.4 节；07 分组 第 2.11 节 |
| 9 | 履约只读付款单的内容快照与快照指向的修订行，不回查现价；起算时刻在履约时定，不取建单时刻与渠道时间 | 07 分组 第 4.8 节；D1 第 6.4 节末表 |
| 10 | 周期不重叠：建周期前在服务层查同主体 `scheduled`、`active`、`ended` 的周期区间，相交即按受阻处理；另登记 `billing.I10`。排他约束在不在都成立 | 计划 第 7.3 节 W1-11a 行、第 8.6 节 V5 |
| 11 | 差异单开单：先按去重键查，已有即跳过；没有才取 `CY` 单号、插入、经 `flow.transition`（新建）写历史与事件 | h01 第 2.6 节 |

| 4 | 入账后取消付款单的定时器 | 按主体取消该付款单名下未触发的 `po.transfer_ttl`（M4 起另有 `po.expire`）；没有也不报错 |

| 6 | 两个端口的名字与签名 | 以 W1-03 合并后的定义为准（建账户端口在 tenant，入参是事务句柄、身份上下文、主体 id；事实端口在 `kernel/ports/`，按来源分键）；本包只实现与登记，不改签名 |

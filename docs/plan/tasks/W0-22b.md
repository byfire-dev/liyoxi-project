## 1. 目标

每条路由按约定 C68 的档位限流，Redis 不可用时不放开。路由级中间件的先后只在 `apps/api/src/routing/pipeline.ts` 一处定义：M1 的鉴权链、授权、验签等包各写自己的中间件文件、在登记表里加一行，先后不由加在哪一行决定（硬性规则 28）。

别的包交给本包的事（移交表里没有归本包的行）：

| 出处 | 事项 | 本包怎么办 |
| --- | --- | --- |
| `docs/plan/status/W0-22.md`“往后移交” | 接手 `pipeline.ts`，定成装配顺序的唯一定义；限流中间件的名字用 `rateLimit`；429 的 `Retry-After` | 照做 |
| 同上，交给“M1 第一个写接口的包”的一行 | `required` 的写路由，请求头带 `Content-Type: application/json` 而请求体为空时回 400 | 本包顺手改：空请求体按 `null` 算，加用例 |
| W0-10 的复审提醒 | 约定 C51 登记的 `x-three-phase`、C68 的档位不在路由元数据里，“声明了什么就挂什么”无从核对 | 在契约里补两张按 operationId 的登记（第 10 节第 1 项） |

## 7. 验收

都在 `pnpm test` 里。连库与连 Redis 的用例走测试支架；“停掉 Redis”用故障注入的转发口造，不动共享的容器。

| # | 验收项 | 命令 | 判据 |
| --- | --- | --- | --- |
| 1 | 超限 429 | `pnpm exec vitest run --project api test/rate-limit.test.ts` | 额度内 200；超出即 429 `RATE_LIMITED`（42901，`retryable` 为真），带 `Retry-After`（正整数秒，不超过窗口）；不同来源 IP、不同用户各算各的；专用档位与组的缺省档位同时生效；回调按来源 IP |
| 2 | 停掉 Redis 后仍生效 | 同上 | 转发口断开后请求照常应答，限额减半后照样 429；恢复并过了熔断时长后回到 Redis 上计数 |
| 3 | 声明了档位而没挂中间件 | `pnpm exec vitest run --project api test/mount.test.ts` | 装配里摘掉限流：建应用即抛 `MountError`，点名路由与 `rateLimit`；档位没有额度、路由写了没登记的档位同样失败 |
| 4 | 装配顺序一处定义 | `pnpm exec vitest run --project api test/pipeline.test.ts` | 每条路由的中间件链都是 `PIPELINE_ORDER` 的子序列，与登记的先后无关；同一槽位同一组登记两次、槽位名不在顺序表里即失败；`apps/api/src` 下只有 `app.ts` 与 `routing/mount.ts` 挂中间件 |
| 5 | 客户端 IP | `pnpm exec vitest run --project api src/http/client-ip.test.ts` | 对端不在可信网段：取对端，忽略转发头；在可信网段：从右数第 N 个；伪造在左侧的值不起作用；链不够长取对端 |
| 6 | 档位与三段式登记 | `pnpm --filter @liyoxi/contract exec vitest run src/routes/declarations.test.ts` | 登记的 operationId 都在路由清单里；一个 operationId 至多一个专用档位；每组的缺省档位齐全 |
| 7 | 限流器 | `pnpm --filter @liyoxi/services exec vitest run src/rate-limit` | 固定窗口：计数键带过期时间；多条规则一次往返；Redis 报错或超时即改用进程内计数、限额减半；熔断期内不再碰 Redis |
| 8 | 空请求体 | `pnpm exec vitest run --project api test/idempotency.test.ts` | `required` 的写路由，带 `Content-Type: application/json`、请求体为空：照常执行，与不带请求头的同键请求互为重放 |
| 9 | 不带坏已有门禁 | 全套（lint、格式、类型、依赖方向、测试、`gates:selftest`）；`node infra/ci/classify-gate-changes.mjs --base origin/main` | 退出码 0；没有放松类门禁改动 |

## 10. 开工前要定的点（默认，本任务书定）

| # | 要定的事 | 默认 |
| --- | --- | --- |
| 1 | 档位数据从哪来 | 契约里按 operationId 登记（约定 C68“按 operationId 登记”）：`packages/contract/src/routes/rate-limits.ts` 写档位、各组的缺省档位、专用档位名下的 operationId；一条路由的生效档位 = 专用档位 + 自己写的 `x-rate-limit` + 所在组的缺省档位。669 条元数据不逐条补键。三段式同法：`three-phase.ts` 登记约定 C51 的表 |
| 2 | 额度放哪 | 约定写的是部署配置。初始值照约定 C68 写成 `apps/api` 里的一张表，建应用时可以整张换；不加环境变量（同 W0-22 第 10 节第 4 项）。回调的“高上限”约定没给数，先取每来源 IP 1200 次 / 分 |
| 3 | 按什么计数 | 四种：来源 IP、用户（操作人）、会话（鉴权链给了会话标识用它，没给退到操作人）、路径参数（票据、支付单）。“每 IP …；登录后每用户 …”读成二选一：登录的请求按用户，匿名的按 IP。一个档位里没有一条规则套得上这次请求时按来源 IP 算，不放开 |
| 4 | 算法与回包 | Redis 固定窗口（一段 Lua：计数与首次设过期原子完成）；一次请求的各条规则一次往返；超限抛 `RATE_LIMITED`，`Retry-After` 取超限那个窗口的剩余秒数（向上取整，至少 1） |
| 5 | 降级 | Redis 命令报错或 200 毫秒没回：这次请求改用进程内固定窗口、限额减半（至少 1），随后 5 秒不再试 Redis；到点再试，通了就回去。进程内的计数表有条数上限 |
| 6 | 客户端 IP | 照 D4 第 9.5 节：对端在可信网段内才看 `X-Forwarded-For`，从右数第 N 个。跳数与可信网段走命令行参数（`--trusted-proxy-hops` 缺省 1；`--trusted-proxy-cidrs` 缺省回环与私有网段），结果放进 `c.var.clientIp`，以后审计、会话、白名单用同一个 |
| 7 | 装配顺序 | `PIPELINE_ORDER`：版本门槛 → 后台访问面 → 鉴权 → 回调验签 → 成员关系 → 协议同意 → 后台请求头检查 → 授权（能力点、权限点）→ 再验证 → 开关 → 限流 → 幂等上下文。约定 C7 没单列“授权”与后台的两件，照 D4 第 7.4 节插进去。各包在 `ROUTE_MIDDLEWARES` 里一件占一行（槽位、适用的组、工厂），链按槽位排序 |
| 8 | 限流器放哪 | `packages/services/src/rate-limit.ts`（包级文件），经 `runtime.rateLimiter` 给 api：它要进程的 Redis 连接，而运行时不把连接交给应用层。没有放进 `security/`：main 上那个模块的入口已由 W0-14 改写，本分支建在较早的提交上，改它必冲突 |
| 9 | 根路径探活 | 不限流（约定 C1、C68） |

## 1. 目标

- 任务进程能跑：谁持有数据库租约谁干活；出站事件被展开、派发、消费；到期定时器被认领、执行；周期任务每期补登记。
- Redis 丢数据或不可用时不丢业务：真相在 PostgreSQL，关键类在进程内执行。
- 交一个兼容脚本，业主拿到托管 Redis 后当天验 V1。使用方：W0-24、W0-30、G2-D 与全部带订阅者、定时器的域。

## 5. 不做什么

- 探针循环、告警规则、告警端口的实现：G2-D。本包遇死信与定时器失败只调 `alerts.raise`。
- 不变量与清理的调度，`invariant.*`、`ops.retention` 的处理器：W0-24。
- 其余循环（账务推进、`notify.scan`、`webhook.reprocess`、媒体任务、`flow.*_sweep`）与其余队列：各域。
- 不登记任何真实订阅者、定时器处理器、周期任务；样例只在测试装配。
- 流程运维的重投接口与命令行：G2-D。镜像与整套 Compose：W1-22。`/health` 读租约：W0-22。
- 不用 BullMQ 的调度器、重复任务与内置重试。不建 `event_redelivery`，不做 `events.redeliver`。
- 不改锁序常量、`infra/ci/layers.json`、表结构、W0-07 的事务单元。会话不连托管 Redis，不读任何连接串。

## 10. 实现要点与顺序

- 顺序：队列封装 → 租约与看门狗 → 出站中继与派发 → 定时器扫描与 `runTimer` → 长任务模式 → 周期补登记循环 → 故障注入测试 → 兼容脚本。
- 认领、执行、失败处理写在 `packages/services` 的 events、timers，租约的 SQL 写在 ops；`apps/worker` 只放循环、看门狗、队列装配、信号处理（`CLAUDE.md` 第 6 节规则 5、6）。
- 中继：每秒调 W0-15 的展开入口。派发：每秒；jobId `evt-{事件 id}-{订阅者}-{序号}`；`consume()` 在行锁下比对 `dispatch_no`，与订阅者的业务写同事务。
- 扫描：每 20 秒；jobId `tmr-{id}-{序号}`；`runTimer` 最后才更新 timer 行，影响 0 行时照常提交。
- 租约与重试时间用数据库时间；业务时间仍用注入时钟。续约用专用连接（`statement_timeout` 3 秒），不进业务连接池；看门狗只读本地变量。
- BullMQ 消费连接 `maxRetriesPerRequest: null`；这类参数在装配代码里写死。队列名、循环名取 W0-09a 的登记，带 `lyx` 前缀。
- 兼容脚本覆盖 D7 第 7.3 节的 7 项：第 1、2、4、7 项自动；第 3 项（主从切换）、第 5 项（写满）提示人工操作后继续；第 6 项（清空自愈）在本地与 CI 自动，在其他实例上先要人工确认。第 2 项的空闲时长可用参数缩短，缺省 60 分钟。

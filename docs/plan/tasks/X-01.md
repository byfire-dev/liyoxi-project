## 1. 目标

给 V19、V8、V3、V7 四项各出一份书面结论。做法：会话交一个探针小程序、一个验证服务和一份执行清单；业主带真实密钥在本机运行验证服务，在三台真机上按清单执行；会话据回传结果写结论。结论决定登录（G2-B）、素材上传页（M3）、下载页扫码登录与逐集下载（M6）的真实形态。

**密钥纪律（计划 第 3 节 ⑦）**：验证服务由业主在自己的终端运行。会话不读密钥文件，不带真实密钥启动服务，不在回复、提交、日志里出现密钥、`session_key`、openid 原值、完整手机号。会话自测只用替身模式。

## 5. 不做什么

- 不做 `wechat`、`storage` 的真实驱动（G2-D、G3-A）。验证服务里的真实调用只为验证，不进 `packages/services`，不被任何应用依赖。
- 不改 `apps/*`、`packages/*`。不动 M1 的登录页与逐集下载页（替身形态）。
- 不实现退路（短信登录、手输为主路径、后台代传）：只改写计划与任务书。
- 不做登记合法域名后的复测；不做 D5 第 16 节其余项（P2、P3、P5–P10、P12、P13）。顺带看到的现象只记备注。
- 不发布、不提审、不上传体验版。
- 会话不读 `~/.lyx/` 下任何文件，不运行会打印环境变量或密钥文件内容的命令，不读 `server/.logs/` 的原始日志（只读脱敏后的 `results/summary.md`）。

## 9. 交付与收尾

- 一个工作包一个 PR，分两段提交：第一段交验证包与清单，PR 保持草稿，状态文件写“阻塞：等业主实测”；业主回传后第二段写结论，转为非草稿。超过可评审体量或业主要先合并验证包时，拆成 a、b 两个可独立合并的 PR，并记一条计划变更（计划 第 5.3 节“粒度”行）。
- PR 描述按 `.github/pull_request_template.md` 填全；借用清单写“源路径@f1361e3 → 目标路径”。
- 同 PR 更新 `docs/plan/status/X-01.md`。先交付可读的中间成果；遇到阻塞即停，把原因写进状态文件并报告。不自行合并。

## 10. 实现要点与顺序

1. 建独立工程 `spikes/weapp-probe`：`app/`（Taro，构建配置照 `apps/weapp` 的写法）与 `server/`（Hono，监听 `0.0.0.0`）。工程自己的脚本：`build`、`test`、`server`、`fixtures`、`report`。服务地址经构建变量注入探针，不入库。
2. 密钥读取只有一个入口：从 `PROBE_SECRETS_FILE`（默认 `~/.lyx/x01-probe.env`）读，或逐项读 `*_FILE`（预发）。`PROBE_MODE=fake` 时不读文件。启动只打印各能力“已配置 / 未配置”。
3. 验证服务四组端点，字段形状照所引接口文档，不接契约包：登录（登录凭证换身份、手机号换取、内存里的“账号 ↔ 手机号 ↔ 多个微信身份”表）；扫码（电脑页面、建票据、查票据、确认、轮询）；上传（登记并按 `clientToken` 复用对象键、签临时密钥、确认时核对大小）；下载（现签读地址、回报）。
4. 每次尝试自动上报一行：项、机型、基础库、网络、文件大小、耗时、结果、错误码。写入前脱敏，落 `server/.logs/`（已被 `.gitignore` 忽略）。`report` 命令汇总成 `results/summary.md`：成功率、耗时中位数与最大值。
5. 探针四个页面各对应一项，参数照第 2 节。上传页要能演示：切后台再回来、杀进程后重选、以压缩方式重选。下载页要能切换 `temp` 与 `user_dir`。
6. `fixtures` 命令：生成 30、50、60、100、150、200、300、500MB 的竖屏 H.264 + AAC MP4（`moov` 前置）并传到测试前缀；由业主运行。
7. 写 `CHECKLIST.md` 与 `README.md`（业主步骤、常见报错、费用提示：手机号组件每次成功都计费）。提交第一段。
8. 业主回传后：写 ADR；更新台账与计划；采用退路的记变更并改写。

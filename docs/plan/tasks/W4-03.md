## 1. 目标

只验证并定点补强统一入账并发机制，覆盖乱序、重复和中断，不夹带新的支付/退款/对账功能。

要落地的接口（只有下表属于本包）：

| operationId | 方法与实际路径 |
| --- | --- |
| 无 | 沿已落地入口验证，不新增 HTTP 资源 |

- 现状：apply.test/property/concurrency/interleave/fault.test.ts 与公开 createPaymentHarness/pendingPlanOrder/transferReceipt 已在 actual；先复用，不复制测试框架。
- 没有新 operationId、页面、x01 或留桩；本包的产物是同一机制的实证性质与必要服务修正。
- 观察表：billing_order、payment_txn、ledger_operation、point_ledger_entry、subscription_term、grant_schedule、payment_exception、outbox_event、status_transition。
- 性质 P1：任意可信收款入口排列/重复，只一条 paidPaymentTxnId/applied_at；既有订单 paid/refunded 事实不可逆退回未支付。
- 性质 P2：fulfill 操作键、周期、发放批次和入账事件唯一，重复返回冻结结果，不增加审计、序号或差异。
- 性质 P3：同一交易与多个成功交易并发，只一个正常入账；另一笔按真实重复收款/金额差异分类，而非错误合并。
- 性质 P4：业务拒绝隔离回滚履约写、保存渠道成功和 blocked；基础设施异常整 TX 回滚，恢复后能再次推进。
- 性质 P5：账户420最后锁、同 TX 一个计费主体；不同主体可并行，无跨主体复用、嵌套事务或账户锁后业务行锁。
- 用实际 PostgreSQL 双连接/明确屏障制造竞态；注入业务 Clock 推进，不用 sleep 排列随机赌时序。
- 中断点涵盖渠道事实写、入账位、savepoint 内多项账本写、事件写和提交前；事务外请求仅沿现 Provider 防线。
- 模型期望独立按整数分/积分与状态事实算，不抄待测 apply/fulfill 代码；失败给随机种子、最小反例和表级差异。

| --- | --- |
| 无 | 不登记新处理器或变更旧归属 |

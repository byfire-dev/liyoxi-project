## 1. 目标

严格按14种差异处理矩阵解决异常收款/履约与渠道退款；从未决到处理结果都可追溯且幂等。

要落地的接口（只有下表属于本包）：

| operationId | 方法与实际路径 |
| --- | --- |
| `admin.paymentException.create` | POST `/admin/payment-exceptions` |
| `admin.paymentException.get` | GET `/admin/payment-exceptions/{paymentExceptionId}` |
| `admin.paymentException.list` | GET `/admin/payment-exceptions` |
| `admin.paymentException.resolve` | POST `/admin/payment-exceptions/{paymentExceptionId}/resolve` |

- 现状：payment/exception.ts 已能按键开差异并刷新has_open_exception，处理/恢复/退款等未落地；不能靠普通入账重放自动关旧差异。
- 表：payment_exception、billing_order、payment_txn、refund_request/txn、transfer_proof；退款与基础回收通过W4-10公口；external refund包装本包新增，不能假称10已交付该包装。
- 状态flow为open/resolving/resolved/auto_healed，ignored保留但V1.0矩阵不产生；expectedVersion、处理说明、权限/stepup/回显单号金额服务端检查。
- paid_after_cancel仅restore/refund，金额/付款人/重复收款仅unapplied_receipt退款；fulfillment_blocked可retried/refund，仍blocked保持open。
- bill_only依关联重分类或rebuild/refund；bank_unmatched可link_order/offline_return；补单需事务外真实查单成功且锁后复核，不仅凭账单旧快照。
- 转退款同TX建立申请/审批并resolving，done才resolved；未执行驳回/撤回/作废回open并清处理字段/引用，原事实留审计。
- refund_bill_only补记可信渠道成功，套餐权益调revokeTermForExternalRefund；已有退款闸门或已用/冻结收不回另开entitlement_unrecovered，不强行释放。
- status_mismatch/platform_only/refund_platform_only/refund_amount_mismatch仅corrected；refund_over/entitlement_unrecovered追回后corrected或超管written_off，普通财务不能核销。
- restore/record_channel_refund是C51事务外查询再锁后提交，幂等结果随最终TX；其余单TX，重复写不增第二差异/退款/履约。
- 先approval/refund申请需要的低阶锁，再order290/txn300/proof310/refund320/exception340/account420；按实际处理方式预定锁集，不以先锁差异再锁订单逆序。
- 基建异常整体回滚；业务履约blocked可持久差异，不把连接/lock_timeout/ACCOUNT_BUSY吞成已处理。未决超过1工作日/两高危类型沿现告警规则升级。

## 5. 不做什么

- 不删渠道原始资金事实/账本历史，不通过普通apply重放代替显式restore，不把所有差异当一种退款。
- 不新增付款/退款机制、对账导入或页面，复用actual公口与保存点，不放宽核销/二次验证。
- 不跨层直接写订单/媒体/审批内部表，不重复登记兄弟x01，不改kernel/锁序/DDL。
- 不调用真实云、真实支付或真实员工账号，不用 SQL 直接推进状态，不绕过公口制造已付款/已退款事实。
- 不删旧测试、提高等待/重试、放松门禁或把 fake/mock 成功写成线上联调完成。

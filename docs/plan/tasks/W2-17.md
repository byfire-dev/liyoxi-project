## 1. 目标

消费已落地的业务事件，按真实当前事实和场景配置生成通知、站内消息及通道投递；失败重试、静默时段和删除清理可验证。
回补五份 M2 桩，给“我的”聚合提供真实未读数，给 W2-03 提供员工激活码通知能力；外部驱动未配置时保留规定降级。
提醒框架只实现 M2 已有业务 producer 的规则，未来 R1/R2/R3/R5/R6/R7 的业务扫描分别交所属包，不能注册恒真守卫/空查询当作完成。

PR1要落地的接口（5 条；其他发送事实属于PR3）：

| operationId | schema/约束 |
| --- | --- |
| `m.message.batchRead` | 账号/当前门店可见范围全部已读，不影响范围外消息 |
| `m.message.list` | MessageListQuery；MessagePage，tab/cursor/limit 与 X-Store-Id 可选 |
| `m.message.read` | messageId；只标本人此刻可见的消息已读，防越权 |
| `m.message.summary` | 未读总数/分类，与 list 使用同一可见谓词 |
| `m.notifySetting.list` | 实际槽位/额度/开关派生设置，不虚构授权 |

表：notify_scene、wx_template_slot、sms_template（仅读取/既有种子）、notification、notification_delivery、merchant_message、staff_message、wx_subscribe_quota、manual_reminder_log。
公告分页另消费已独立实际合入本地 main 的 notification_fanout 结构能力；本 PR 不内嵌 DDL。正式 notify.fanout.batch 默认 1000，必要补登范围 1–10000，由调度会话核准；隔离测试设 2 仅验证页边界，不代表默认容量性能验收。
状态机：notification_delivery.status 沿 x01 正式迁移/守卫；消息 read_at 是条件写，不能创建新状态机。场景枚举与 NOTIFY_SCENES 一一对账。
x01：notify.onEvent、notify.onMerchantUserDeleted、notify.remind_scan、notify.scan（notify_scan）、notify 队列（并发4、按通道限速）；不抢 W2-22 两条短信周期任务。
发送前重新校验当前对象、接收人身份、动作仍需要；notification 去重/合并、delivery 通道重试与状态更新用真实唯一键和租约，不重复写业务事件。
账号消息与门店消息按 m08 当前成员/主体/ownerOnly/inbox.scope 过滤；老板变店员后不能读历史 ownerOnly，店员不接积分/金额文案；summary/read/batchRead 同口径。
外呼在 TX 外，经 providers/types 注入；额度预扣/返还与无额度清零按正式规则，已配置与实际到达分别记录。Redis 不可用保留框架规定关键通道处理，不能假称已发送。

notify.N1/N2/N3/N15 按正式 subject/mode/heal 登记；删除订阅者清除/撤销对应待发送事实，不在账户删除后继续外发。

## 5. 不做什么

- 不改内核 outbox/timer/lease/队列机制、同层白名单、草稿/约束/表结构或 route metadata。
- 不做 W2-18 订阅/埋点/错误、W2-19 页面、W2-22 短信初始化/驱动，不扩未来业务 producer。
- 不在 notify/docs 反向 import 上层域或查询其表；域事实从公开端口提供，域模块不能直接调用 notify。
- 不重发原业务事件补通知，不把当前 null 端口的假成功当回补，不读取真密钥或发真实短信。

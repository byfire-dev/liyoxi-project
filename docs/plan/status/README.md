# 进度台账（status）

依据：[开发计划](../../08-development-plan.md) 第 13 节“进度记在哪”行、第 9.3 节“台账”行、第 5.3 节“怎么运转”行。

## 1. 用途

| 项 | 规则 | 出处 |
| --- | --- | --- |
| 粒度 | 一包一个文件：`docs/plan/status/<编号>.md`，如 `W0-05b.md`、`X-01.md` | 计划 第 13 节 |
| 谁更新 | 该包的 PR 自己更新自己的文件；不改别的包的文件。并行的 PR 互不冲突 | 计划 第 13 节 |
| 汇总表 | 由脚本从各包的状态文件现生成，不入库，不手改；CI 只核对状态文件合不合规（第 5 节） | 计划 第 9.3、13 节 |
| 谁读 | 新会话先读 `CLAUDE.md`、状态汇总与任务书 | 计划 第 13 节 |
| 选下一个包 | 从汇总里取“依赖已全部合并”的；同泳道按编号先后 | 计划 第 5.3 节 |
| 待评审上限 | 待评审数 = 仓库里打开的非草稿 PR 数；上限 5 个，到上限不开新包 | 计划 第 5.3、11 节 |
| 上游未合并 | 下游包不得基于上游分支开工 | 计划 第 9.3 节 |
| 结构变更包 | 首版迁移之后改结构只走结构变更包，同一时刻只允许一个在途，在本目录登记 | 计划 第 9.3 节 |

## 2. 文件格式

按[状态文件模板](../templates/status.md)写。字段表的“项”一列是脚本读的键，不改名。

| 键 | 写法 |
| --- | --- |
| 编号、里程碑 | 里程碑写 M0、M1 或技术验证泳道 |
| 状态 | 取值见第 3 节 |
| PR | 未开 PR 写“—”；开了写编号或链接。按体量上限拆成 a、b 两个 PR 的，两个都写 |
| 依赖 | 抄计划该行的“依赖”列，展开成完整编号（计划 第 7.1 节：只写两位数字的指同一里程碑内的包）。Q、E 项与文字条件照抄。计划写“M0”的，这里写“M0 退出”。没有写“—” |
| 评审级别 | 甲、乙、丙（计划 第 7.1 节的表） |
| 规模 | S、M、L（计划 第 7.2–7.4 节的“规模”列） |
| 阻塞原因 | 没有写“无”。有则写等什么：上游包编号、Q、E、V 项，或发现了什么问题 |
| 结构变更包 | 首版之后改表结构的包写“是”；同一时刻只允许一个在途（计划 第 9.3 节） |
| 任务书 | `docs/plan/tasks/<编号>.md`。没有任务书的包写“无”并注明出处（只有 W0-04） |
| “偏差”一节 | 没有写“无”。有则按模板的表逐条列，每条一两句：文档原来怎么写、查实的事实、回写到哪 |
| “留桩”一节 | 没有写“无”。有则指向 [stubs/](../stubs/README.md) 下的文件 |

默认：计划 第 13 节只列了状态、PR、阻塞原因、偏差，其余的键是加的（W0-04 定）。依赖、评审级别、规模供脚本找“依赖已全部合并”的包，供业主按级别排评审顺序；这三行的值以开发计划为准，计划改了，同 PR 改这里。任务书另写了前置而计划依赖列没有的：“依赖”不动，先记在“阻塞原因”，等计划补上（[tasks/README.md](../tasks/README.md) 第 6 节）。

空值的写法：PR、依赖写“—”；阻塞原因与“偏差”“留桩”两节写“无”。

## 3. 状态取值

取值与判定以本节为准（默认，W0-04 定）；[docs/plan/README.md](../README.md) 第 4.1 节与[模板](../templates/status.md)跟随本节。汇总脚本遇到本节之外的取值即报错（W0-03 任务书 第 7 节）。

| 取值 | 何时 |
| --- | --- |
| `未开工` | 初始值 |
| `进行中` | 已开工，PR 还没就绪 |
| `阻塞` | 会话停下，同时写明阻塞原因 |
| `完成` | 本包的 PR 在分支里写成 `完成`，开 PR 后填上 PR 编号；随 PR 合入 main 即“已合并”。main 上是 `完成` = 已合并 |

“待评审”不是文件里的取值，从打开的非草稿 PR 读。

## 4. 改编号与新增包

| 情况 | 做法 | 出处 |
| --- | --- | --- |
| 评审后拆出或新增的包 | 用 a、b 后缀，原编号不动；新建对应的状态文件 | 计划 第 7.1 节 |
| 超体量按 a、b 拆 | 新建状态文件，并在 [changes/](../changes/README.md) 记一条 | 计划 第 5.3 节 |
| 任务书里预拆成几个 PR、编号不变（M1 的十三个包与 W1-23、W2-25、W2-27） | 状态文件仍是一份：不是最后一个的 PR 写“进行中”，“偏差”首行写“第 N 个 PR 已合并”，最后一个才写“完成”。只等第一个 PR 的下游写“；开工另等某包的第一个 PR”，本包后一个 PR 另等的包写“；第二个 PR 另等谁”：都是文字条件，脚本判不了，列进“另需核对”，“开工另等”的要在开工前自己核对。细则见 [tasks/README.md](../tasks/README.md) 第 7.1、7.2 节 | W0-31 定 |
| M1 的依赖与级别被修正 | 由 W0-31 同步改本目录对应文件（已改：依赖写成具体编号，不再写“M0 退出”；W1-23 的规模改 L） | 计划 第 7.2 节 W0-31 一行 |
| M2 以后的包 | 由各拆包 PR 建状态文件：G2-D 环境包随 W0-31（已建 W2-25–W2-29，“里程碑”写“环境泳道”，不计入“M2 退出”）；G2-E 随生产，默认由 M7 交 M8 的拆包 PR 建（ADR-041）；M2、M3、M4全部状态随W1-23a；M2任务书随a，M3/M4任务书随b，没有已合任务书不得开工；之后见计划第7.5节 | 计划 第 7.5、13 节 |

## 5. 汇总脚本

| 项 | 内容 |
| --- | --- |
| 做什么 | 读本目录各文件的字段表，输出汇总表；列出“依赖已全部合并”的可开工包 |
| 谁提供 | 计划没有写明由哪个包交付。默认：随 W0-03 交付，放 `infra/ci`，与门禁改动分类脚本同处（W0-04 定）。已交付：`infra/ci/status-summary.mjs` |
| 怎么跑 | `pnpm status:summary`，要看汇总时现跑。改了自己的状态文件（包括开 PR 后填 PR 编号），不用生成、提交汇总；换了分支、拉了 main 之后要看就重新跑 |
| 输出到哪 | 本目录的 `SUMMARY.md`（文件名是默认，W0-04 定）。不入库：它在 `.gitignore` 里。原因：它入库时，改了状态文件的 PR 之间要么在它上面冲突、要么合出过期的汇总，每合并一个，其余的都要重新生成。业主已同意改为不入库（[owner-checklist.md](../owner-checklist.md) 第 5 节） |
| 核对 | CI 的“状态文件核对”一步跑 `node infra/ci/status-summary.mjs --check`：只核对状态文件能不能生成出汇总（下一行列的几种问题），不写文件，也不读、不比对任何已有的汇总。汇总不入库，没有“重新生成后无差异”这道核对 |
| 报错 | 第一行不是 `# <编号> <名称>`；字段表缺键；状态取值不在第 3 节之内；标题、“编号”一行与文件名不一致；依赖里的工作包没有状态文件；依赖里的 `M<n> 退出` 对不上任何里程碑。生成与 `--check` 一样会报，并指出是哪个文件的哪一项 |
| 可开工的判定 | 状态是“未开工”，且“依赖”里的工作包都写着“完成”；“M0 退出”这类里程碑条件，指该里程碑的包全部完成。Q、E 项与文字条件脚本判不了，列在“另需核对”一栏，开工前自己核对 |
| 与四个计数的关系 | 四个计数（已落地接口数、待落地数、留桩数、未实现页面数）由 CI 产出，本地用 `pnpm counts:report` 出（`infra/ci/four-counts.mjs`，W0-30）；不在本脚本内 |

## 6. 汇总表

汇总表不入库。要看时跑 `pnpm status:summary`，生成到本目录的 `SUMMARY.md`（被 git 忽略）：计数、可开工的包、各包状态。它是生成那一刻的快照，不手改；与单个状态文件不一致时以单个文件为准，重新跑一遍即可。

随 W0-04 给出的手工表已在 W0-03 删除，由脚本生成的汇总接替；那份汇总起初入库，经业主同意后改为不入库（第 5 节“输出到哪”行）。

## PR2 本地实现与待验收

本地已补齐本包十一条 typed route、请求与响应 schema、公开导出及薄 HTTP handler。`createDeliveryM5` / `DeliveryM5Deps` 提供活动流、剪辑师与发布专员指派、纠偏、求值、返工、改期、催办及补发三个动作。写入口沿原权限、required 幂等与真实范围；纠偏消费 PR1 的中央权限、再验证、确认、白名单与回滚机制。活动流汇合本工单及相关方案、样片、剧集、质检、包和补发的审计；改期同步方案草稿及 `draft_lock_version`，不生成方案版本。

样片、剧集登记不再隐式写入 `editor_id`；首次指派和改派经显式入口，首次不写空来源改派行，改派保留原负责人。工单环节使用注入时钟及既有工作日历计算 `due_at` / `sla_snapshot`，同步 `step_due_at` 与方案 `staff_due_at`；本地实现 `delivery.onCalendarImported` 及原 `sla.breach` 的 `delivery_ticket_stage` 分支，旧时钟投递须复核当前环节和快照。M1 的唯一 `flow.reevaluate_sweep` / `flow_reevaluate_sweep` 沿原 worker 叶运行，没有另建同名循环；M5 的 order `flow.reconcile_sweep` / `flow_reconcile_sweep` 留给 PR3。

暂停原因集合、汇总与剩余工作分钟沿同一事务收尾；补发发布复核真实制作事实、通过的质检记录、替换集完整性及原包和授权。`delivery.I2` 检查暂停来源、集合与汇总并记录真实自愈，`delivery.I14` 检查补发集号及发布包归属与变更集；均已接入正式不变量登记，不以恒零结果替代检查。人工催办经正式通知派发重新读取当前对象和商家收件人，HTTP 用例已补 owner 消息归属、重放去重、跨店错误对象及失效场景不投递断言。

本片还补齐 a09 第 2.9 节三个既有事件的通知接线：`package.reissue_opened` → 当前剪辑师的 `s.delivery_progress`；`package.reissued`、`order.item.launch_rescheduled` → 老板的 `m.order_progress` 站内消息。对象事实及旧事件有效性由 delivery 自有 keyed reader 提供，`specFor` 按场景与对象类型精确选重验 reader，不新增场景或商家外部通道。补发包/日期被新事实取代时旧事件不派发，人工催办和再次改期按真实事件 id 保留每次合法发生，原事件重投仍去重。

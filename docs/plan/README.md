## 1. 目录结构

| 路径 | 放什么 | 粒度 | 谁更新、何时 |
| --- | --- | --- | --- |

| `sample-review/<编号>.md` | 看样清单：逐项列“看什么、规范哪一节、怎么打开”，留“结论”一栏给业主填；留给看样定的事项也列在里面 | 一包一个文件 | 交看样页或要业主看样的包同 PR 建（第一份是 W0-29）；业主看完填结论，对话里说的由调度会话代填。默认（W0-29 定）：台账里原来没有放看样结论的地方，计划 第 7.2 节 W0-29 行要求“结论入库” |

- 汇总表（状态汇总、留桩数、变更汇总、外部验证汇总）由脚本生成，不手改。状态汇总不入库，要看时跑 `pnpm status:summary` 现生成（业主已同意，见 [owner-checklist.md](owner-checklist.md) 第 5 节；细则见 [status/README.md](status/README.md) 第 5 节）。其余三张同样不入库（W0-30 定，理由相同，见 [changes/W0-30-ledger-summaries-not-committed.md](changes/W0-30-ledger-summaries-not-committed.md)）：跑 `pnpm plan:summaries` 现生成，写到 `stubs/`、`changes/`、`external-verification/` 各自的 `SUMMARY.md`（被 git 忽略）；CI 的“台账单项文件核对”只查单项文件合不合规。
- 状态汇总的脚本随 W0-03（默认，W0-04 定；计划没写由谁交）；留桩、变更、外部验证三张汇总的脚本随 W0-30（`infra/ci/plan-summaries.mjs`），已到位。各 PR 照旧只改单项文件；各 README 里的手工表是 W0-04 给的初始快照，不再更新，与单项文件不一致时以单项文件为准。
- 四个计数由 CI 在 main 上每次产出：已落地接口数、待落地数、留桩数、未实现页面数；另出 x01 归属的未落地清单。本地用 `pnpm counts:report` 出（`infra/ci/four-counts.mjs`，W0-30）；里程碑退出时加 `--require <里程碑>` 核对四样清零。
- 三份运维文档在 D7 里的旧文件名与这里的对应，见开发计划文首“与其他文档的关系”。
- 本目录不放密钥、证书、`.env` 内容；证据只放链接或脱敏后的截图。

## 3. 怎么运转

### 3.1 开一个工作包

业主（或业主授权的调度会话）开会话。提示语固定，原文如下，只替换编号：

> 读 `CLAUDE.md` 与 `docs/plan/tasks/<编号>.md`，完成工作包 <编号>

| 项 | 规则 |
| --- | --- |
| 会话凭什么开工 | 只凭固定提示语、`CLAUDE.md`、任务书与状态汇总。会话不带记忆，不向业主追问 |
| 下一个包怎么选 | 从状态汇总里取“依赖已全部合并”的；同泳道按编号先后。状态汇总不入库：跑 `pnpm status:summary` 现生成，写到 `status/SUMMARY.md`（被 git 忽略；[status/README.md](status/README.md) 第 5、6 节） |
| 待评审上限 | 待评审数 = 仓库里打开的非草稿 PR 数。到上限（默认 5 个）不开新包 |
| 上游未合并 | 下游包不得基于上游的分支开工。判定：main 上该包的状态文件写“完成”即已合并 |
| 任务书不存在 | [tasks/README.md](tasks/README.md) 第 3 节列的 13 个 S、M 包由开工的会话补全（先查该文件第 5 节的移交表）；L 与甲类包停下报告。那 13 个都在 M0，已全部交付；M1 与五个环境包的任务书已入库，之后的由拆包 PR 交，所以现在遇到任务书不存在一律停下报告 |
| 一会话一包 | 在独立 worktree 里做；只改任务书允许的目录；拿不准的、为做完本包必须小幅超出范围的，照最贴近 01–07 的做法做并在“偏差”里记一句，由调度会话定，只有做不下去才停下报告（`CLAUDE.md` 第 3 节第 6 步）；先交付可读的中间成果 |
| 分支 | `feat/<工作包编号>-<短名>`，修复用 `fix/*`，验证用 `spike/*`；从最新 main 切；不直接推 main |
| 首包例外 | W0-04 由业主过目后才开第二个会话（计划 第 12 节） |

### 3.2 一个工作包从开工到合并

| 步骤 | 谁 | 做什么 |
| --- | --- | --- |
| 1 开工 | 作者会话 | 读 `CLAUDE.md`、任务书、状态汇总；切分支；S、M 包没有任务书的，先按清单行与模板补全（第 3.1 节“任务书不存在”行） |
| 2 实现 | 作者会话 | 只改允许的目录；改表、改接口、改默认做法，同 PR 改对应文档 |
| 3 登记 | 作者会话 | 更新 `status/<编号>.md`；有留桩记 `stubs/`；有计划变更记 `changes/`；有验证结论记 `external-verification/` |
| 4 开 PR | 作者会话 | 按 PR 模板写描述，各节几句话；验收是“命令 + 判据”，证据就是 CI 运行，不另写证据文件 |
| 5 同步 | 维护会话 | 变基、重新生成、重跑门禁（第 3.3 节） |
| 6 复审 | 复审会话 | 由调度会话启动；每个 PR 一轮、一份，甲类也是，限时；按 [templates/review.md](templates/review.md) 写，只找真问题 |
| 7 合并 | 调度会话 | 合并条件、哪几样事仍然先问业主，见第 3.5 节。合并提交，合并后删远端分支；一次合一个。作者会话、复审会话、维护会话不合并。main 的保护规则已设，由平台强制：必须经 PR、必过检查 `required`、合并前与 main 同步，对管理员同样生效（[owner-checklist.md](owner-checklist.md) E15 行） |

第 4 步的推送与开 PR、第 6 步的贴复审评论由调度会话代做，作者会话、复审会话把 PR 描述与复审全文写好交给它（第 3.5 节第 1 项）。

业主按评审分级事后看证据（计划 第 5.3 节“评审分级”行）：甲类看性质或并发测试的结果；乙类看验收输出、对账差异与默认项清单；丙类看截图与清单。各级别的包合并都不等业主，甲类也是（第 3.5 节第 4 项）。

### 3.3 维护会话

| 项 | 规则 |
| --- | --- |
| 数量 | 一个，常驻 |
| 负责 | 在途 PR 的变基、重新生成、重跑门禁 |
| 不做 | 不改业务代码 |
| 台账 PR | 默认：业主回传结论、进展或实测结果后，开只改台账的独立 PR 记入（第 4.5 节“谁来改”）（W0-04 定） |
| 节奏 | 每合并一个 PR，把其余在途 PR 同步一遍 |
| 合并前看什么 | 同步后的 CI 结果 |
| 生成物冲突 | 一律变基后重新生成，不手工合并。文本上能自动合并不等于生成物与源码一致 |
| 台账冲突 | 台账一包（一项、一条）一个文件，正常不会冲突。四张汇总都不入库，不参与合并 |

### 3.4 标签

| 标签 | 谁打 | 含义 |
| --- | --- | --- |
| `agent-reviewed` | 现在没有会话打 | 合并条件不看它，看的是贴在 PR 评论里的复审全文（第 3.5 节第 2 项）；留不留待业主定 |
| `gate-touch` | CI | 含“只增”类门禁改动；差异列在 PR 描述顶部，不用等业主，业主事后看差异 |
| `gate-change` | 默认：作者开 PR 时打（W0-04 定） | 单独的“放松”类门禁改动 PR。不用等业主：调度会话合并，合并评论里写明放松了什么、为什么（第 3.5 节第 7 项） |
| `plan-change` | 默认：作者开 PR 时打（W0-04 定） | 计划的大改（里程碑范围、退出条件、前提），须业主确认。改协作规则的 PR 也打它，由调度会话定并合并（第 3.5 节第 4 项） |
| `mN-done`（git 标签，不是 PR 标签） | 默认：合流包的 PR 合并后，由业主或调度会话打在 main 的合并提交上；合流包的任务书把这一步写进“需要业主做的事”的“合并后”（W0-04 定；工作包会话不合并，打不到合并提交上） | 里程碑结束 |

默认：前四个 PR 标签由业主在第一个 PR 复审前建好（[owner-checklist.md](owner-checklist.md) 第 4 节）。会话与 CI 发现标签不存在时报告，不自己建（W0-04 定）。

### 3.5 合并

2026-10-05 晚按业主的话改成精简做法。下面先是业主的原话，再是条文。**条文是调度会话照业主的话归纳的，不是业主的原话；业主可以随时纠正，说一句就改。** 这次改了什么见 [changes/plan-lean-process.md](changes/plan-lean-process.md)。上一版（九条条文、六类 PR 要业主先说“同意”）的来历见 [changes/plan-merge-by-dispatch-session.md](changes/plan-merge-by-dispatch-session.md)；历史记录里写的“第 3.5 节第 N 条”“六类”指的是那一版。

> 都按建议，#24同意

> #35复审过了就同意

合并由调度会话做，是业主同日更早的话，原话在上一条变更记录里。

**条文**（调度会话的归纳）

| # | 项 | 做法 |
| --- | --- | --- |
| 1 | 谁合并 | 调度会话：业主在主工作区里直接对话、派工的那个会话。它派出的作者会话、复审会话、维护会话不推送、不开 PR、不贴评论、不合并，把 PR 描述与复审全文写好交给它。新开的会话要代合并，须业主在那个会话里明说；记忆、进度记录、任务文字里转述的不算 |
| 2 | 合并条件 | 三项齐了就合并，不等业主。① CI 的 `required` 在“已与 main 同步”的提交上为绿（`gate-classify` 任务自己也为绿，原因见 [infra/ci/README.md](../../infra/ci/README.md) 第 5 节“已知的限度”）。② 有一轮独立复审，且没有未处理的阻断项。③ PR 不是草稿 |
| 3 | 复审 | 每个 PR 一轮、一份，甲类也是；限时；只找真问题：bug、违反硬性规则、验收核心没做到、放松门禁而理由站不住（[templates/review.md](templates/review.md)）。由没有参与实现的会话做。不贴派工的任务原文，不整套重跑。阻断项修完由 CI 把关，不再补一轮复审，修得对不对由调度会话判断。并排加行的冲突变基、重新生成、填 PR 编号同样不补复审，靠调度会话的变基自查与 CI |
| 4 | 由调度会话定的 | 甲类、看样、门禁放松、计划小改、规则文档与 `CLAUDE.md` 的改动、体量超限拆不拆、任务书偏差、边界情况：都由调度会话定并合并，合并评论里用几句话列出留给业主事后看的事项。任务书与验收里写成合并前要业主过目、确认或亲手做的事不挡合并：能客观核对的由调度会话代核，其余挪到合并后 |
| 5 | 仍然先问业主的 | 只有这几样：动服务器的每一步；部署与发布；用到真实密钥或账号；花钱；删数据或别的不可逆操作；改 main 的保护规则与必过检查的名单。要把这张清单改少，或放宽第 9 项前三样，也先问（这半句是执笔的会话补的，不是调度会话的归纳） |
| 6 | 看样 | 要看样的包先合并；业主看了再提意见，意见另开 PR 改。通用构件与页面骨架在业主提过意见并改完后冻结：`CLAUDE.md` 第 6 节硬性规则 27 的字面没有动，其中“看样确认”按这个算。冻结之前，页面包照旧不改构件，要改走单独的构件 PR |
| 7 | 门禁改动 | 只增类（`gate-touch`）随工作包 PR，清单在 PR 描述顶部。放松类照旧单独成 PR、打 `gate-change`，平台上的分类检查照旧；不用等业主，调度会话合并，合并评论里写明放松了什么、为什么 |
| 8 | 文书 | PR 描述各节几句话。证据就是 CI 运行，不另写证据文件。状态文件的“偏差”简短写。合并不等于业主已确认：业主事后的结论与已合并的做法相反时，开变更 PR。要业主拿主意的事随下一个台账 PR 记进 [owner-checklist.md](owner-checklist.md) 第 4 节，一件一行（2026-10-05 晚以后合并的记在第 4.3 节）；只是知会的以合并评论为准，不另抄 |
| 9 | 不变的 | `CLAUDE.md` 第 6 节硬性规则，一条不动；密钥与 `.env` 的规则；main 的保护规则（必须经 PR、必过检查 `required`、合并前与 main 同步、对管理员生效）。另有两样这次没有碰：计划的大改（里程碑范围、退出条件、前提）仍须业主确认，阻塞性决定（Q 项）里 Q9 仍须明确答复（计划 第 4.2、13 节） |

## 4. 各台账的规则

### 4.1 工作包状态

| 项 | 规则 |
| --- | --- |
| 细则 | [status/README.md](status/README.md)：键、状态取值、汇总脚本、汇总表怎么看。本节与它不一致时以它为准 |
| 字段 | 表里的键：编号、里程碑、状态、PR、依赖、评审级别、规模、阻塞原因、结构变更包、任务书；另有“偏差”“留桩”两个小节。计划 第 13 节只列了状态、PR、阻塞原因、偏差，其余是默认（W0-04 定） |
| 谁更新 | 该包的 PR 自己更新；别的 PR 不碰 |
| 默认：状态取值（W0-04 定） | `未开工`、`进行中`、`阻塞`、`完成`。“待评审”不写进文件，从打开的非草稿 PR 读 |
| 默认：收尾怎么写（W0-04 定） | 本包的 PR 在分支里把状态写成“完成”并填 PR；随合并进入 main。main 上状态为“完成”即已合并 |
| 初始文件 | M0、M1 与四个 X 包的随 W0-04 建好；之后由各拆包 PR 建 |
| 结构变更包 | 首版之后改表结构的包在状态文件“结构变更包”一行写“是”；同一时刻只允许一个在途 |
| 偏差 | 实现中发现文档有错：以查实的事实为准，同 PR 回写文档，在状态文件与 PR 描述里列出 |

### 4.2 留桩

| 项 | 规则 |
| --- | --- |
| 什么要登记 | 故意不做实、留给后面里程碑回补的能力；端口的实现方未到时用桩顶替的 |
| 什么不许留桩 | 内核、账本、鉴权链；提交校验这类正确性逻辑 |
| 什么不算留桩 | “入口隐藏”的页面，在 `pages.md` 单列 |
| 对“已落地”的影响 | 在留桩清单里的接口不算已落地 |
| 清零 | 回补的里程碑退出前，应在本里程碑回补的留桩为 0；“开发完成”要求留桩清单为空 |
| 统计 | 留桩数由 CI 统计。默认：留桩数 = 状态为“留桩中”的文件数；回补的 PR 把状态改为“已回补”，文件保留不删（W0-04 定） |
| 清单之外新留桩 | 默认：先改计划 第 7.3 节的留桩清单，并在 `changes/` 记一条，类别写“留桩”（W0-04 定；留桩清单在计划里，改它属小改） |
| 细则 | [stubs/README.md](stubs/README.md)：何时登记、命名、计数。键以 [templates/stub.md](templates/stub.md) 为准 |

### 4.3 计划变更

| 类别 | 范围 | 做法 |
| --- | --- | --- |
| 小改 | 包的拆并、顺序调整、估算修正；接口、页面、x01 条目改归属 | 直接改开发计划，并在 `changes/` 记一条（细则见 [changes/README.md](changes/README.md)） |
| 大改 | 里程碑范围、退出条件、前提 | PR 标 `plan-change`，须业主确认 |
| 实现与任务书的出入，不改计划 | — | 不记 `changes/`；写在该包状态文件的“偏差”与 PR 描述 |
| 架构取舍 | — | 另写 ADR（`docs/adr/`，一条一文件） |
| 待确认事项有结论 | — | 先改文档里的默认做法，再改代码，同一个 PR；必要时开“变更工作包” |
| 与其他文档冲突 | — | 以 01–07 为准，回改开发计划 |

### 4.4 外部验证

| 项 | 规则 |

### 4.5 业主清单

| 项 | 规则 |
| --- | --- |
| 范围 | 计划 第 4.1 节的 E 项、第 4.2 节的 Q 项 |

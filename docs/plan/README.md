- 汇总表（状态汇总、留桩数、变更汇总、外部验证汇总）由脚本生成，不手改。状态汇总不入库，要看时跑 `pnpm status:summary` 现生成（业主已同意，见 [owner-checklist.md](owner-checklist.md) 第 5 节；细则见 [status/README.md](status/README.md) 第 5 节）。其余三张按生成物处理：冲突时变基后重新生成。
- 状态汇总的脚本随 W0-03（默认，W0-04 定；计划没写由谁交）；留桩、变更、外部验证三张汇总的脚本随 W0-30 的四个计数报表（计划 第 7.2 节 W0-30 一行）。脚本到位前，各 PR 只改单项文件，不改各 README 里的手工表；两边不一致时以单项文件为准。
- 四个计数由 CI 在 main 上每次产出：已落地接口数、待落地数、留桩数、未实现页面数；另出 x01 归属的未落地清单。
- 三份运维文档在 D7 里的旧文件名与这里的对应，见开发计划文首“与其他文档的关系”。
- 本目录不放密钥、证书、`.env` 内容；证据只放链接或脱敏后的截图。

## 3. 怎么运转

### 3.1 开一个工作包

业主（或业主授权的调度会话）开会话。提示语固定，原文如下，只替换编号：

> 读 `CLAUDE.md` 与 `docs/plan/tasks/<编号>.md`，完成工作包 <编号>

| 项 | 规则 |
| --- | --- |
| 会话凭什么开工 | 只凭固定提示语、`CLAUDE.md`、任务书与状态汇总。会话不带记忆，不向业主追问 |
| 下一个包怎么选 | 从状态汇总里取“依赖已全部合并”的；同泳道按编号先后。状态汇总不入库：跑 `pnpm status:summary` 现生成，写到 `status/SUMMARY.md`（被 git 忽略；[status/README.md](status/README.md) 第 5、6 节） |
| 待评审上限 | 待评审数 = 仓库里打开的非草稿 PR 数。到上限（默认 5 个）不开新包 |
| 上游未合并 | 下游包不得基于上游的分支开工。判定：main 上该包的状态文件写“完成”即已合并 |
| 任务书不存在 | [tasks/README.md](tasks/README.md) 第 3 节列的 13 个 S、M 包由开工的会话补全（先查该文件第 5 节的移交表）；L 与甲类包停下报告 |
| 一会话一包 | 在独立 worktree 里做；只改任务书允许的目录；超出范围即停并报告；先交付可读的中间成果 |
| 分支 | `feat/<工作包编号>-<短名>`，修复用 `fix/*`，验证用 `spike/*`；从最新 main 切；不直接推 main |
| 首包例外 | W0-04 由业主过目后才开第二个会话（计划 第 12 节） |

### 3.2 一个工作包从开工到合并

| 步骤 | 谁 | 做什么 |
| --- | --- | --- |
| 1 开工 | 作者会话 | 读 `CLAUDE.md`、任务书、状态汇总；切分支；S、M 包没有任务书的，先按清单行与模板补全（第 3.1 节“任务书不存在”行） |
| 2 实现 | 作者会话 | 只改允许的目录；改表、改接口、改默认做法，同 PR 改对应文档 |
| 3 登记 | 作者会话 | 更新 `status/<编号>.md`；有留桩记 `stubs/`；有计划变更记 `changes/`；有验证结论记 `external-verification/` |
| 4 开 PR | 作者会话 | 按 PR 模板填全；验收是“命令 + 判据”，证据链接到 CI 运行或产物（CI 就绪前的办法见 [templates/review.md](templates/review.md) 第 2 节 B 类） |
| 5 同步 | 维护会话 | 变基、重新生成、重跑门禁（第 3.3 节） |
| 6 复审 | 复审会话 | 由业主或调度会话启动；按 [templates/review.md](templates/review.md) 发评论，打 `agent-reviewed` |
| 7 合并 | 调度会话 | 合并条件、哪六类 PR 要业主先说“同意”，见第 3.5 节。合并提交，合并后删远端分支；一次合一个。作者会话、复审会话、维护会话不合并。main 的保护规则已设，由平台强制：必须经 PR、必过检查 `required`、合并前与 main 同步，对管理员同样生效（[owner-checklist.md](owner-checklist.md) E15 行） |

第 4 步的推送与开 PR、第 6 步的贴复审评论由调度会话代做，作者会话、复审会话把 PR 描述与复审全文写好交给它（第 3.5 节第 1 条）。

业主按评审分级看证据（计划 第 5.3 节“评审分级”行）：甲类逐项看证据；乙类看验收输出、对账差异与默认项清单；丙类看截图与清单。评审顺序：甲类 → 门禁与契约 → 其余。甲类包合并前要业主先说“同意”；乙类、丙类包不因级别要等业主，业主事后看，另属六类的照六类办（第 3.5 节第 3、4 条）。

### 3.3 维护会话

| 项 | 规则 |
| --- | --- |
| 数量 | 一个，常驻 |
| 负责 | 在途 PR 的变基、重新生成、重跑门禁 |
| 不做 | 不改业务代码 |
| 台账 PR | 默认：业主回传结论、进展或实测结果后，开只改台账的独立 PR 记入（第 4.5 节“谁来改”）（W0-04 定） |
| 节奏 | 每合并一个 PR，把其余在途 PR 同步一遍 |
| 合并前看什么 | 同步后的 CI 结果 |
| 生成物冲突 | 一律变基后重新生成，不手工合并。文本上能自动合并不等于生成物与源码一致 |
| 台账冲突 | 台账一包（一项、一条）一个文件，正常不会冲突。状态汇总不入库，不参与合并；其余汇总表按生成物处理 |

### 3.4 标签

| 标签 | 谁打 | 含义 |
| --- | --- | --- |
| `agent-reviewed` | 复审会话 | 已按模板复审，无阻断项 |
| `gate-touch` | CI | 含“只增”类门禁改动；差异列在 PR 描述顶部，不因此要等业主，业主事后看差异，另属六类的照六类办（第 3.5 节第 3、4 条） |
| `gate-change` | 默认：作者开 PR 时打（W0-04 定） | 单独的“放松”类门禁改动 PR，业主必看 |
| `plan-change` | 默认：作者开 PR 时打（W0-04 定） | 计划的大改（里程碑范围、退出条件、前提），须业主确认 |
| `mN-done`（git 标签，不是 PR 标签） | 默认：合流包的 PR 合并后，由业主或调度会话打在 main 的合并提交上；合流包的任务书把这一步写进“需要业主做的事”的“合并后”（W0-04 定；工作包会话不合并，打不到合并提交上） | 里程碑结束 |

默认：前四个 PR 标签由业主在第一个 PR 复审前建好（[owner-checklist.md](owner-checklist.md) 第 4 节）。会话与 CI 发现标签不存在时报告，不自己建（W0-04 定）。

### 3.5 合并

合并 PR 由调度会话做。下面先是业主的两段原话，再是调度会话列给业主选的那一栏，最后是条文。条文是调度会话照业主选的那一栏写的，不是业主的原话。做这次改动的 PR 改的是合并规则本身，属第 3 条 ②，业主本人表态后才合并（记录见 [changes/plan-merge-by-dispatch-session.md](changes/plan-merge-by-dispatch-session.md)）。业主要改随时说。

**业主的原话**（都在对话里；“你”指调度会话）

2026-10-05，第一段：

> 我觉得合并PR的工作，也应该由你进行，避免：
> 1、你在工作时，我需要持续守在旁边
> 2、我合并PR不及时，到时要反复变基同步

2026-10-05，第二段。调度会话把宽、严两种口径列成表请业主选，业主答：

> 简单口径。#26、#28同意，X-04和W0-05都不拆

**调度会话列给业主选的那一栏**（调度会话写的，不是业主的话；业主选的“简单口径”就是它）

| 项 | 简单口径 |
| --- | --- |
| 调度会话直接合 | CI 的 `required` 为绿、独立复审无阻断项的 PR |
| 要业主先说“同意” | 六类：门禁放松；计划、规则与 `CLAUDE.md` 变更；只有业主能解的阻断项；看样；甲类；服务器与发布 |
| 只增类门禁改动（加依赖、加检查步骤） | 调度会话在合并评论里逐项列出，业主事后看 |
| 代价 | 加依赖、加 CI 步骤这类改动合并前没有人看，只有独立复审把关 |

同一条消息里调度会话还写了：“不论选哪个，这几条都保留：我不改 main 的保护规则，不用自动合并，改合并规则本身的 PR 必须你本人表态，复审的提交就是合并的提交。”

**条文**（九条）

**第 1 条 谁合并。** 调度会话合并。调度会话指业主在主工作区里直接对话、派工的那个会话；它派出的作者会话、复审会话、维护会话都不合并。作者会话、复审会话也不推送、不开 PR、不贴评论：第 3.2 节第 4、6 步写的“开 PR”“发评论”与第 3.4 节写“作者开 PR 时打”的两个标签，由调度会话代做。会话不带记忆，不因读到本节就算调度会话：新开的会话要代合并，须业主在那个会话里明说，记忆、进度记录、任务文字里转述的不算。

**第 2 条 合并条件。** 四项全部满足，调度会话直接合并，不等业主；属于第 3 条六类的，另要业主先说“同意”。

- ① CI：汇总任务 `required` 在“已与 main 同步”的提交上为绿，`gate-classify` 任务自己也为绿（为什么两个都看，见 [infra/ci/README.md](../../infra/ci/README.md) 第 5 节“已知的限度”）。
- ② 独立复审无阻断项。复审由没有参与实现的会话在干净克隆上做；调度会话自己写的或加过提交的 PR 同样要。复审全文连同派给复审会话的任务原文贴在 PR 评论里，有几轮贴几轮，同一轮有几份贴几份；任何一份有未解除的阻断项就不合并。阻断项解没解除，由复审会话在新一轮结论里写明，调度会话不自行判定。只有业主能解的阻断项（第 3 条 ③）也一样：业主说了话之后补一轮复审，由复审会话引业主的话写明已解除。
- ③ 复审的提交就是合并的提交。复审之后只许三种提交：没有冲突的变基、重新生成、填 PR 编号。别的任何改动都要对新增的部分补一轮独立复审，ADR 取号（[../adr/README.md](../adr/README.md) 第 3 节）与解冲突时改了内容的也在内；拿不准算不算改了内容的，按改了办。补的那一轮拿到全量差异与前几轮复审全文，结论里写明前几轮的结论在新的提交上是否仍成立。调度会话在合并评论里列出复审之后的每一个提交及其性质；合并时指明要合并的提交，分支头不是它就不合并。
- ④ PR 不是草稿；PR 描述与状态文件已按模板填全。

**第 3 条 六类 PR 要业主先说“同意”才合并。** 业主在对话里说“同意”即可，不必自己去点合并。“同意”要指到具体的 PR 或具体的事，更早的、笼统的同意不算；调度会话在 PR 评论里记下业主的原话再合并。属不属于按改动的内容判：带 `gate-change`、`plan-change` 标签的一律属于，没带标签而内容属于的也属于；边界拿不准的按属于办。独立复审在结论里写明属不属于、属于哪一类，没写的视为复审没做完；各轮各份复审里只要有一份认为属于，就按属于办。

| # | 哪一类 | 指什么 |
| --- | --- | --- |
| ① | 门禁放松 | 带或应带 `gate-change` 的 PR：删改已有的规则、检查脚本、反例、黄金条目与工作流里已有的步骤，调高基线，改 `layers.json` 白名单与锁序常量等（计划 第 5.3 节“门禁改动”行；[infra/ci/README.md](../../infra/ci/README.md) 第 5 节的分类脚本判成“放松”的，判不出而按放松算的在内） |
| ② | 计划、规则与 `CLAUDE.md` 变更 | 带或应带 `plan-change` 的 PR（计划的大改：里程碑范围、退出条件、前提）；改 `CLAUDE.md` 里命令与共享环境用法以外内容的 PR；改合并规则本身的 PR：本节、[复审模板](templates/review.md)、PR 模板（`.github/pull_request_template.md`），以及凡是会让某类 PR 由“要业主先说同意”变成“不用”的改动，不论改的是哪个文件 |
| ③ | 只有业主能解的阻断项 | 复审记了阻断项，而作者改代码解除不了的。例如体量超限，要业主定拆还是同意不拆；验收或依据文档把业主的过目、确认或答复写成合并的前提（如计划 第 4.2 节 Q9；W0-31、W1-23 的验收），而还没有业主的话可引 |
| ④ | 看样 | 要业主看了才算数的：通用构件与页面骨架（`CLAUDE.md` 第 6 节硬性规则 27）、设计样张；任务书“需要业主做的事”里合并前要业主凭主观判断或亲手做的事（真机、带密钥的运行）也算 |
| ⑤ | 甲类 | 计划 第 7.1 节定为甲类的包的 PR |
| ⑥ | 服务器与发布 | 会改动服务器、触发部署或发布的 PR 与操作；服务器上的改动每一步先问业主。合并即部署现在没有启用。启用后合并就会触发部署，哪些合并可以不问，启用时由业主定；定之前都按属于办，送审期间（计划 第 4.2 节 Q11）的合并也在内 |

**第 4 条 只增类门禁改动不等业主。** PR 带 `gate-touch`（加依赖、加检查步骤、加用例、重新生成的生成物这类，口径见 [infra/ci/README.md](../../infra/ci/README.md) 第 5 节），不因此要等业主：调度会话在合并评论里把 PR 顶部的门禁改动清单逐项列出，业主事后看。它若另属六类，照第 3 条办。代价，列给业主选时写明了：这类改动合并前没有人看，只有独立复审把关。其余不属于六类的 PR 同样不等业主，乙类、丙类包也在内，业主按评审分级事后看证据（第 3.2 节）。

**第 5 条 合并不等于业主已确认。** PR 里“请业主定”“请业主过目”的非阻断事项不挡合并。调度会话在合并评论里逐项列出，随下一个台账 PR 记进 [owner-checklist.md](owner-checklist.md) 第 4.1 节，业主随时看；带 `gate-touch` 的 PR 的清单同样记。业主的结论与已合并的做法相反时，开变更 PR。任务书“需要业主做的事”里合并前的客观核对（不需要密钥、真机、外部账号就能核的，例如打开 CI 产物核对数字）由调度会话代核，结果写在 PR 评论里；拿不准的归主观，按第 3 条 ④ 办。

**第 6 条 合并方式。** 合并提交，合并后删远端分支。一次合一个；合完同步下一个，等它的 CI 绿了再合。不用平台的自动合并：它在 `required` 变绿时合并当时的分支头，绕开第 2 条 ③。

**第 7 条 调度会话不做的。** 不改 main 的保护规则（必须经 PR、必过检查 `required`、合并前与 main 同步、对管理员生效）、必过检查的名单与仓库的合并设置，要改先经业主同意。不直接推 main。不摘 `gate-change`、`plan-change` 两个标签。`.env` 与密钥的规则照旧。

**第 8 条 还没定的两件。** 业主没有答复，条文照现状写，不替业主定。① 业主有没有表态，现在只有调度会话的转述为凭：PR 的作者、评论人、合并人是同一个账号，调度会话记在 PR 评论里的“业主原话”与业主本人写的评论，在平台上分不出。② `agent-reviewed` 标签留不留、谁来打：合并条件不看它，看的是贴在 PR 评论里的复审全文；开 PR 的会话不给自己的 PR 打，复审会话不碰 PR，所以现在没有会话打它，而第 3.2、3.4 节、计划 第 5.3 节“复审”行与第 10.1 节、两份模板仍写着它。

**第 9 条 收回。** 业主随时可以收回或改范围，说“停”即停。

## 4. 各台账的规则

### 4.1 工作包状态

| 项 | 规则 |
| --- | --- |
| 细则 | [status/README.md](status/README.md)：键、状态取值、汇总脚本、汇总表怎么看。本节与它不一致时以它为准 |
| 字段 | 表里的键：编号、里程碑、状态、PR、依赖、评审级别、规模、阻塞原因、结构变更包、任务书；另有“偏差”“留桩”两个小节。计划 第 13 节只列了状态、PR、阻塞原因、偏差，其余是默认（W0-04 定） |
| 谁更新 | 该包的 PR 自己更新；别的 PR 不碰 |
| 默认：状态取值（W0-04 定） | `未开工`、`进行中`、`阻塞`、`完成`。“待评审”不写进文件，从打开的非草稿 PR 读 |
| 默认：收尾怎么写（W0-04 定） | 本包的 PR 在分支里把状态写成“完成”并填 PR；随合并进入 main。main 上状态为“完成”即已合并 |
| 初始文件 | M0、M1 与四个 X 包的随 W0-04 建好；之后由各拆包 PR 建 |
| 结构变更包 | 首版之后改表结构的包在状态文件“结构变更包”一行写“是”；同一时刻只允许一个在途 |
| 偏差 | 实现中发现文档有错：以查实的事实为准，同 PR 回写文档，在状态文件与 PR 描述里列出 |

### 4.2 留桩

| 项 | 规则 |
| --- | --- |
| 什么要登记 | 故意不做实、留给后面里程碑回补的能力；端口的实现方未到时用桩顶替的 |
| 什么不许留桩 | 内核、账本、鉴权链；提交校验这类正确性逻辑 |
| 什么不算留桩 | “入口隐藏”的页面，在 `pages.md` 单列 |
| 对“已落地”的影响 | 在留桩清单里的接口不算已落地 |
| 清零 | 回补的里程碑退出前，应在本里程碑回补的留桩为 0；“开发完成”要求留桩清单为空 |
| 统计 | 留桩数由 CI 统计。默认：留桩数 = 状态为“留桩中”的文件数；回补的 PR 把状态改为“已回补”，文件保留不删（W0-04 定） |
| 清单之外新留桩 | 默认：先改计划 第 7.3 节的留桩清单，并在 `changes/` 记一条，类别写“留桩”（W0-04 定；留桩清单在计划里，改它属小改） |
| 细则 | [stubs/README.md](stubs/README.md)：何时登记、命名、计数。键以 [templates/stub.md](templates/stub.md) 为准 |

### 4.3 计划变更

| 类别 | 范围 | 做法 |
| --- | --- | --- |
| 小改 | 包的拆并、顺序调整、估算修正；接口、页面、x01 条目改归属 | 直接改开发计划，并在 `changes/` 记一条（细则见 [changes/README.md](changes/README.md)） |
| 大改 | 里程碑范围、退出条件、前提 | PR 标 `plan-change`，须业主确认 |
| 实现与任务书的出入，不改计划 | — | 不记 `changes/`；写在该包状态文件的“偏差”与 PR 描述 |
| 架构取舍 | — | 另写 ADR（`docs/adr/`，一条一文件） |
| 待确认事项有结论 | — | 先改文档里的默认做法，再改代码，同一个 PR；必要时开“变更工作包” |
| 与其他文档冲突 | — | 以 01–07 为准，回改开发计划 |

### 4.4 外部验证

| 项 | 规则 |
| --- | --- |
| 范围 | 计划 第 8.6 节两张表的每一行 |
| 记什么 | 结论、证据、最晚关闭点 |
| 到点未关闭 | 依赖它的工作包不开工；第 8.6 节写了到点退路的按退路 |
| 里程碑退出 | 到期的项已关闭；未到期的记入台账 |
| 可上线 | 两张表全部有结论（V9 不做、V16 试点前） |
| 技术验证包 | X-01–X-04 的结论写成 ADR，并更新计划 第 8.6 节与本台账 |
| 谁来改 | 做验证的工作包 PR 改对应文件；业主实测的，业主回传结果后按第 4.5 节“谁来改”代记 |
| 汇总表 | 默认：README 里的两张表是 W0-04 给的初始快照。汇总脚本到位前各 PR 不改它；与单项文件不一致时以单项文件为准（W0-04 定） |
| 细则 | [external-verification/README.md](external-verification/README.md)：文件名、状态取值、两张汇总表 |

### 4.5 业主清单

| 项 | 规则 |
| --- | --- |
| 范围 | 计划 第 4.1 节的 E 项、第 4.2 节的 Q 项 |
| 文件 | [owner-checklist.md](owner-checklist.md) |
| 记什么 | 状态与结论，含默许日期 |

## 5. 里程碑结束时

## 1. 一页结论

- **做法**：先搭最小地基（M0），再用替身打通一条“登录 → 成片上线”的主路径（M1），然后沿业务链路逐域加厚（M2–M7），最后做上线准备（M8）。M0 起每个里程碑结束都能演示。
- **规模**：9 个里程碑，约 199 个工作包（下表各行相加），一个工作包一个 PR。M0 的 37 个、M1 的 27 个、技术验证的 4 个已展开到工作包；M2–M8 列到工作包组，进入前由拆包 PR 拆细。比初稿多约 29 个：评审后拆开了过大的甲类包，补了测试支架、服务装配、限流、内容安全、生产最小集与拆包 PR；提交前核查与复核又补了 6 个（素材理解的驱动接入、交付侧的体检接入、G7-A 的早拆包 PR、探针与告警最小集、月结补建的两包）。
- **并行**：M2、M3、M4 除共享面外互不依赖，可同时推进（共用前置与共享面见第 6.2 节）；技术验证的任务书随 W0-04 交付，与 M0、M1 并行（各自依赖合并后即可做）。瓶颈是业主评审，不是会话数：待评审的 PR 上限默认 5 个。
- **不等外部**：全部业务先在替身上开发与测试。里程碑分两级退出：代码侧退出即可进入下一个里程碑；外部验证项各有最晚关闭点（第 8.6 节）。硬卡点：M6 的预发与真机闭环演示、M8；试提审（V2）另需预发就绪与备案（第 6.5 节；指向预发是会话建议、待业主定，生产最小集随生产，ADR-041）。
- **防漂移**：M0 由文档底稿一次接管表结构与路由元数据。之后代码为准，文档同 PR 跟随，CI 对账（第 5.7 节）。
- **业主现在要做的**：前提（Q1）、Q7、Q12 已答复，其中 Q7 的 AppID 一项与原默认相反（[ADR-041](adr/0041-预发先行-单机预发-共用AppID.md)），Q12 的“谁合并”一项后来也改为与原默认相反（合并由调度会话做，第 5.3 节“合并条件”行）；四个 PR 标签、参考工程登记、E15 的三步与 main 的保护规则都已办完；参考工程已停用。还剩：ADR-041 里待业主定的事项（单环境阶段接不接真实商家、参考工程的线上版本与数据怎么处置、镜像仓库、内容域、试提审指向哪里等）；继续办第 4.1 节的 E5–E11、E16、E17；答复第 4.2 节的 Q2、Q3、Q5、Q6（Q4 已按默认记默许），不答复即按默认，到“最迟”记默许日期。逐项的状态、默认与最晚时点见[业主清单](plan/owner-checklist.md)第 4 节。
- **日历**：不排日期。快慢取决于评审节奏与外部事项（备案、认证、云资源、法务结论）。
- **来源**：骨架取自“主链路纵向切片优先”提案，嫁接了“风险优先”与“依赖拓扑”两份提案的做法（附录）。

### 5.3 分支与 PR 规范

| 项 | 规则 |
| --- | --- |
| 分支 | `feat/<工作包编号>-<短名>`，修复用 `fix/*`，验证用 `spike/*`；从最新 main 切；不直接推 main |
| 粒度 | 一个工作包一个 PR。L 包按“契约 → 服务 → 接口与任务 → 测试”组织提交，PR 描述给出阅读顺序。可评审体量的上限（默认值，业主可改）：甲类一个 PR 只含一个机制，非生成、非测试代码不超过约 600 行；乙类不超过 20 条接口；丙类不超过 8 页。超过即拆成 a、b 两个可独立合并的 PR。例外：W0-13（幂等、单号）、W0-14（审计、加密与脱敏）、W0-17（定时器、时限、端口）各含两到三个强相关的小机制，拆开后互相等接口，不预先拆；PR 里按机制分提交、逐机制附证据。这三包与其余甲类包开工后若超过体量上限，按 a、b 拆并记一条计划变更 |
| 契约先行 | 一个域的 Zod 结构随该域第一个后端 PR 合入；页面包在契约合入后即可开工，联调等接口包 |
| 提交 | conventional commits：`type(scope): 中文一句话` |
| 任务书 | 每个工作包开工前有一份自包含的任务书：目标、依据（文件 第 N 节）、依赖、允许改动的目录、不做什么、验收命令。会话不带记忆，只凭任务书、`CLAUDE.md` 与状态汇总开工。S、M 包的任务书可以是“清单行 + 模板补全”；L 与甲类包单独成文，业主过目。任务书写明本包允许新增的依赖。谁写、何时写：首批 13 个包（第 12 节）、M0 其余 L、甲类包与四个 X 包（X-04 属甲类，单独成文）的随 W0-04 交付；M0 其余 S、M 包由开工的会话按第 7.2 节的清单行与模板补全，随 PR 提交；M1 的由 W0-31 交付；环境泳道提前开工的包也由 W0-31 交付拆包与任务书：G2-D 的环境包（G2-E 随生产，它的拆包与任务书默认并入 M7 交 M8 的拆包 PR，ADR-041）；之后每个里程碑的拆包 PR 交下一批，G7-A 的拆包 PR 挂在 M2 合流包之后（第 7.5 节） |
| PR 描述 | 固定模板，各节几句话：工作包；改了什么（含依据）；怎么验（命令 + 判据；证据就是 CI 运行，给链接，不贴文本、不另写证据文件；演示步骤或截图）；留给业主事后看的（用到的默认项编号、留桩、偏差、回写了哪些文档、借用清单：源路径@提交 → 目标路径）；门禁改动清单（CI 自动列出） |
| 合并条件 | 合并 PR 由调度会话做（业主的结论，Q12）；作者会话、复审会话、维护会话不推送、不开 PR、不合并，新开的会话要代合并，须业主在那个会话里明说。2026-10-05 晚按业主的话精简过：条文是调度会话照业主的话归纳的，业主可以随时纠正；全文与业主的原话在 [plan/README.md](plan/README.md) 第 3.5 节，这里是缩写，有出入时以那一节为准。三项齐了调度会话就合并，不等业主：CI 的汇总任务 `required` 在“已与 main 同步”的提交上为绿，`gate-classify` 任务自己也为绿；有一轮独立复审且没有未处理的阻断项（阻断项修完由 CI 把关，不再补复审，修得对不对由调度会话判断；并排加行的冲突变基靠调度会话的变基自查与 CI）；PR 不是草稿。甲类、看样、门禁放松、计划小改、体量超限、任务书偏差、边界情况都由调度会话定并合并，合并评论里用几句话列出留给业主事后看的事项；要看样的包先合并，业主看了再提意见、另开 PR 改。仍然先问业主的只有：动服务器的每一步；部署与发布；用到真实密钥或账号；花钱；删数据或别的不可逆操作；改 main 的保护规则与必过检查的名单。合并不等于业主已确认：业主事后的结论与已合并的做法相反时开变更 PR。合并提交，合并后删远端分支；一次合一个；不用平台的自动合并 |
| 复审 | PR 就绪后由调度会话启动一个复审会话，每个 PR 一轮、一份（甲类也是），限时。输入：PR 差异、任务书、`CLAUDE.md` 第 6 节。输出：按半页的模板写（复审的提交、结论、阻断项、备注至多 5 条、没看的范围），由调度会话贴到 PR 评论。只找真问题，阻断项只有四种：bug；违反硬性规则；验收核心没做到；放松门禁而理由站不住。不整套重跑。复审与作者意见不一时由调度会话定。模板在 [plan/templates/review.md](plan/templates/review.md) |
| 评审分级 | 甲（内核、账本、入账、权限与字段裁剪、迁移、回调验签）：不与其他改动混合，附性质或并发测试输出，业主事后看证据。乙（一般服务与接口）：看验收输出、对账差异与默认项清单。丙（页面、配置型增删改查、生成物）：看截图与清单。各包的级别见第 7.1 节 |
| 门禁改动 | 分两类，由 `infra/ci` 的脚本判定（随 W0-03 交付）。“只增”类：新增依赖、黄金文件新增条目、待落地数减少、新增 CI 步骤、新迁移附带的结构快照更新、重新生成的生成物。随工作包 PR 走，CI 自动打 `gate-touch` 标签并在 PR 描述顶部列出差异；不用等业主，业主事后看差异。“放松”类：删改已有规则或已有黄金条目、调高基线、删 CI 步骤、改 `layers.json` 白名单、改锁序常量。只在单独的 PR 里改，标 `gate-change`；不用等业主，调度会话合并并在合并评论里写明放松了什么、为什么（“合并条件”行） |
| 单独成 PR | 依赖升级；首版之后的结构变更（第 9.3 节的结构变更包）；契约的破坏性变更。种子迁移、授权迁移属于所在工作包 |
| 会话 | 一个会话一个工作包，在独立 worktree 里做；只改任务书允许的目录；拿不准的、须小幅超出范围的，照最贴近 01–07 的做法做并在“偏差”里记一句，由调度会话定，做不下去才停下报告；先交付可读的中间成果 |
| 怎么运转 | 业主（或业主授权的调度会话）开会话，提示语固定：“读 `CLAUDE.md` 与 `docs/plan/tasks/<编号>.md`，完成工作包 <编号>”。下一个包从状态汇总里取“依赖已全部合并”的，同泳道按编号先后。待评审数 = 仓库里打开的非草稿 PR 数，到上限不开新包 |
| 维护会话 | 一个常驻会话负责在途 PR 的变基、重新生成、重跑门禁，不改业务代码。每合并一个 PR，它把其余在途 PR 同步一遍；合并前看的是同步后的 CI 结果 |
| 禁止 | 提交或读取 `.env`、密钥、证书（`.env.example` 只放占位，可提交；唯一的例外是调度会话读参考工程的 `.env`，范围见第 3 节前提 ⑦）；用 `prisma migrate dev` 的自动产物；跳过钩子；事务内调外部服务；绕过 `flow.transition()` 改状态；应用层直接查库 |

### 5.7 文档与代码不漂移的机制

### 9.3 冲突面控制

| 冲突面 | 控制办法 |
| --- | --- |
| schema.prisma 与迁移 | 首版之后改结构只走“结构变更包”，单独成 PR，同一时刻只允许一个在途，在状态文件里登记；领域包原则上不改结构 |
| 契约注册表与路由清单 | M0 一次生成全量。领域 PR 只写自己接口的 Zod 结构，不动别人的元数据；接口是否落地由 CI 判定，不手工打标。被两个以上里程碑同时写的五份（a01、a03、a09、m03、h01）按资源分文件 |
| 登记表：订阅者、周期任务、服务装配、菜单与路由、小程序页面清单、种子、端到端脚本、演示种子 | 一个模块（或一个里程碑）一个文件，汇总由脚本生成或自动收集。收集机制在 W0-07b 一处定义 |
| 中间件装配 | 装配顺序在 W0-22b 一处定义；两条鉴权链与之后的包只加自己的中间件文件 |
| 生成物（OpenAPI、类型、结构快照、登记文档、黄金文件、四个计数） | 冲突时一律变基后重新生成，不手工合并。文本上能自动合并不等于生成物与源码一致：合并前必须与 main 同步并重新生成，由维护会话做，合并前看的是同步后的 CI 结果 |
| 台账（状态、留桩、变更记录、外部验证） | 一包（一项、一条）一个文件；汇总表由脚本生成，不手改。状态汇总不入库，需要时现生成，CI 只核对状态文件合不合规；其余汇总表按生成物处理 |
| `layers.json`、锁序常量 | 只在单独的 `gate-change` PR 里改 |
| 锁文件 | 新增依赖随工作包走（`gate-touch`，任务书写明允许新增哪些）；升级单独成 PR |
| 通用构件与页面骨架 | 要看样的包先合并，业主看了再提意见；业主提过意见并改完后冻结。页面包要改构件，走单独的构件 PR |
| 端口 | 定义方先合并接口与空实现；实现方后到，用桩顶替并登记到留桩清单 |
| 测试库 | 每个会话、每个 Vitest worker 一个 `lyx_test_<包>_<n>` 库；Redis 按会话分库号或键前缀；Compose 只起一份共享实例（第 5.4 节） |
| 在途 PR | 待评审超过上限就停开新包；上游包未合并时，下游包不得基于其分支开工 |

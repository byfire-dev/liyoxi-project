# 预发固定旧订阅日快照恢复

用户于 2026-11-27 明确批准恢复此前暂缓的一条历史事件。此入口只接受
`01a208c1-2019-743b-bef2-a9759ad59412`，重建策略 `legacy_activation_v1`。
原写入版本 `6c8a8498ac4540843c7e906157bb336d0438c4a4`，初次离线证明来源
`13f485def43857afda19dc58303ff687099bb2ca`。不推广到其他旧事件，不改写原 payload。

## 恢复证据

单条 SQL 读取原事件、完整事件清单、原 activated outbox、订单内容/履约快照、
真实成功收款、周期、连续发放计划、首月批次与发放/履约账本。正式 Schema、
日期与金额分摊函数重建首期之后的 pendingGrants；不读取现价，不靠当前余额推测历史。
任何额外订阅历史、退款/延期、缺期、支付金额或归属矛盾都会拒绝。

恢复事务按 staff → billing_order → payment_txn → billing_account 锁序保护读取。
默认只输出 eventId、证据和候选 SHA256；实际追加要求传回这两项指纹并重新读取证据，
变化即拒绝。完整证据冻结在只增补充表，不对 HTTP 或命令输出暴露。

授权员工必须是有效超管；记录明确分开授权员工、运维执行者、实际恢复时间与原因。
系统审计 `billing.subscription.recover_snapshot` 和补充行同事务提交；原事件操作人和时间不变。
相同事件/证据/候选重放返回 already_applied，冲突拒绝。禁止 UPDATE、DELETE、TRUNCATE。

## 运维步骤

1. 正常评审合入 main，构建同一完整 SHA；取得新鲜加密备份并验证可恢复。
2. 使用正式迁移安装空补充表、同源部署读取器与命令。发布仍保留原 P1 门禁；
   若修复本身必须越过已知告警，只能通过既有逐 ID override 和明确原因留下发布审计，
   不改告警状态、不删任务、不关闭门禁。
3. 在受控 worker 环境运行 `node apps/worker/dist/legacy-snapshot-recovery.js`：
   `--event-id <固定事件> --authorizing-staff-id <真实超管> --operator <运维执行者>`
   `--reason <本次授权依据> --source-sha <完整构建SHA>`。预发构建版本必须匹配该 SHA，生产环境禁用。
4. 核对只读预览与已批准候选后，用相同参数追加 `--apply --evidence-hash <预览值> --payload-hash <预览值>`。
   不接受由文件直接指定候选，候选始终由受保护的当前证据重建。
5. 经正式后台重试 daily；正式任务写派生表。核对收款、余额、积分批次与原流水指纹不变，
   I11/I13 无违规，P1 连续健康采样自然恢复。已有补充记录不重写，也不倒删回滚。

## 读取与测试

每日投影和 I13 共用 computeEntityDaily。只有缺原 payload 的固定 activated 事件才使用补充；
每次读取校验原事件指纹、复合归属、证据/候选摘要，并从冻结证据重建后比较候选。
未来正常消费、退款或积分发放不改变冻结证据，已有正常快照不会被覆盖。

真实数据库回归由正常收款与履约产生全部事实，仅在首次插入事件时模拟旧写者缺字段。
覆盖 12 类证据反例、预览零写入、指纹过期/缺确认拒绝、3 轮两连接幂等、单条审计、
补充内容/归属篡改拒绝，以及正式日投影、I11/I13 与原财务事实不变。
